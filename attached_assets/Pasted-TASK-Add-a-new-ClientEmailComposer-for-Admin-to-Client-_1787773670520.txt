# IMPORTANT — APPROVAL FLOW

We want one more step when Admin approves a job.

Current concept:

Admin clicks Approve
→ job becomes approved
→ notification appears

New desired flow:

Admin clicks Approve
→ ClientEmailComposer opens
→ preloaded "Job Post Approved" email
→ Admin can review/edit
→ Admin confirms
→ job approval is persisted
→ existing in-app notification is created
→ email is sent to Client

But transactional safety is critical.

Do NOT allow email delivery failure to undo a valid approval.

Preferred sequence:

1. Admin clicks Approve.
2. Open ClientEmailComposer in approval mode.
3. Admin reviews/edits email.
4. Admin clicks:
   `Approve & Send`
5. Backend performs job approval transaction.
6. Existing in-app notification is created.
7. Email send is attempted.
8. UI reports:

   * approval successful
   * email sent
     OR
   * approval successful, but email delivery failed

Do not leave the job pending just because Graph failed.

# CANCEL BEHAVIOR

Do not approve/reject the job.

Return to the existing job approval UI unchanged.

This makes the email composer part of the confirmation step.

# PREVIEW ENDPOINT

ApplicantEmailComposer currently uses an application-specific preview route.

Do not force Client emails through:

`/api/admin/job-applications/:id/email/preview`

Add/reuse an appropriate Client/job preview endpoint.

Example:

`POST /api/admin/jobs/:jobId/client-email/preview`

It should:

* require Admin auth
* load job
* resolve Client
* resolve permitted template variables
* render subject/body
* return unresolved variables

Do not mutate job state during preview.

# SEND ENDPOINT

Use a job/Client-specific Admin endpoint.

Example:

`POST /api/admin/jobs/:jobId/client-email/send`

Payload concept:

{
"templateId": "...",
"subject": "...",
"bodyHtml": "...",
"senderEmail": "[hiretalent@onspotglobal.com](mailto:hiretalent@onspotglobal.com)",
"eventType": "job_approved"
}

Server must independently resolve recipient.

Do NOT trust a frontend-provided arbitrary recipient email for normal approval flow.

Frontend may display recipient, but backend should derive it from job ownership.

# APPROVAL + SEND ENDPOINT

To prevent race conditions, consider a focused endpoint such as:

`POST /api/admin/jobs/:jobId/approve-with-email`

It may accept:

* subject
* bodyHtml
* templateId
* senderEmail

Then:

1. validates Admin
2. validates current job approval state
3. approves job using existing approval logic
4. creates existing notification
5. attempts email
6. returns both results

Example response:

{
"approved": true,
"email": {
"status": "sent"
}
}

or:

{
"approved": true,
"email": {
"status": "failed",
"message": "..."
}
}

Do not duplicate approval logic.

Extract/reuse existing approval service/function if needed.

Do NOT implement a second inconsistent status transition.
