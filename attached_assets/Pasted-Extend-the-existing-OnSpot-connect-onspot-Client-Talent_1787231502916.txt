Extend the existing OnSpot / `connect-onspot` Client ↔ Talent messaging system with **application-based chat entry points on both sides**.

The underlying messaging feature already exists and works.

Do NOT build a second chat system.

Do NOT create separate messages for applications.

Everything must reuse the existing canonical:

* `message_threads`
* `messages`
* `/messages`
* `/messages/:threadId`
* participant authorization
* unread/read state
* message notifications
* Talent candidate/profile auth resolution
* Client auth resolution

The goal is to make it easy for both Client and Talent to start or open the SAME conversation directly from an application/submission.

---

# REQUIRED CLIENT-SIDE CHANGE

On the Client Portal, in the existing:

**Job Submissions**

table, each applicable Talent submission should get a messaging action.

Current actions include things such as:

* Offer
* View

Add a button such as:

**Message**

or:

**Talk to Talent**

Preferred label:

`Message`

with a `MessageSquare` icon.

Example:

```text
APPLICANT      POSITION               STATUS          ACTIONS

Valu Testu     Social Media Manager   NEW             Message  View
```

or:

```text
Valu Testu     Social Media Manager   REVIEWED        Offer  Message  View
```

Use the existing button styling.

Do not redesign the table.

---

# CLIENT MESSAGE BUTTON BEHAVIOR

When Client clicks:

`Message`

on a specific submission:

1. Authenticate Client.
2. Identify the exact `job_submission`.
3. Resolve the exact Talent linked to that submission.
4. Resolve canonical Client `users.id`.
5. Resolve canonical Talent `users.id`.
6. Find the existing canonical conversation between those participants in the correct application/job context.
7. If one exists, reuse it.
8. If none exists, create it idempotently.
9. Return canonical `threadId`.
10. Navigate Client to:

`/messages/:threadId`

Do NOT create another thread every time the button is clicked.

---

# IMPORTANT — CLIENT MUST MESSAGE THE EXACT APPLICANT

The Client table may contain multiple applications, possibly even multiple submissions from the same Talent.

The Message action must use the exact selected:

`applicationId`

Do not guess based only on Talent name.

Do not search by email from the frontend.

Derive the Client/Talent relationship server-side from the canonical submission/job records.

---

# REQUIRED TALENT-SIDE CHANGE

On the Talent:

**My Applications**

page, add a messaging action inside each eligible job/application card.

Use a label such as:

**Reach the Client**

Preferred wording:

`Reach the Client`

with a `MessageSquare` icon.

Example:

```text
Social Media Manager
OnSpot · Remote

Submitted · Applied Aug 20, 2026

View submission · Timeline · Reach the Client
                              Withdraw
```

or align it neatly with the existing actions.

Do not remove:

* View Job
* View submission
* Timeline
* Withdraw

---

# TALENT BUTTON BEHAVIOR

When Talent clicks:

`Reach the Client`

for a specific application:

1. Authenticate Talent.
2. Support BOTH:

   * main Talent JWT
   * Talent candidate/profile JWT
3. Resolve authenticated Talent to canonical `users.id`.
4. Load that exact application.
5. Confirm Talent owns the application.
6. Resolve the Client who owns the job.
7. Find/reuse existing canonical thread.
8. If none exists and contact is allowed, create it idempotently.
9. Return canonical `threadId`.
10. Navigate to:

`/messages/:threadId`

The Talent must land in the SAME conversation the Client sees.

---

# TALENT NOTIFICATION CLICK FLOW

Current Talent notifications such as:

`Application update`

redirect Talent to:

`/my-applications`

Keep that behavior.

Do NOT change every application notification to open Messages.

Instead:

1. Talent clicks application notification.
2. Talent arrives at `/my-applications`.
3. Relevant application card is visible.
4. That card includes:
   `Reach the Client`
5. Talent can then open the chat directly.

This is the intended UX.

---

# OPTIONAL APPLICATION HIGHLIGHT AFTER NOTIFICATION

If the existing notification includes an application/submission ID, improve the UX by passing it through navigation.

For example:

`/my-applications?application=<id>`

or equivalent existing routing style.

Then on the Talent application page:

* scroll/highlight the relevant card briefly
* do not break normal direct `/my-applications` access

This is optional but preferred if safely supported.

Do not create fragile routing just for animation.

---

# USE ONE CANONICAL APPLICATION-CHAT BACKEND FLOW

Do not implement Client and Talent thread creation separately with different rules.

Prefer a shared helper.

Conceptually:

```ts
getOrCreateApplicationMessageThread({
  applicationId,
  authenticatedUserId,
  role
})
```

or reusable lower-level helpers such as:

```text
resolveMessagingUserId
resolveApplicationParticipants
getOrCreateCanonicalThread
assertApplicationParticipant
```

The important point is:

Client and Talent must resolve to the SAME thread.

# SUGGESTED ENDPOINT DESIGN

First inspect existing messaging routes.

Reuse an existing secure route if possible.

If new endpoints are needed, use application-scoped routes such as:

### Client

`POST /api/client/applications/:applicationId/message-thread`

### Talent

`POST /api/talent/applications/:applicationId/message-thread`

Both should internally call the SAME canonical thread helper.

OR use a single endpoint:

`POST /api/applications/:applicationId/message-thread`

and infer role from authentication.

Choose whichever best fits the existing API architecture.

Do not trust role/user IDs supplied from frontend.

# THREAD PARTICIPANTS

Thread participants must contain canonical:

* Client `users.id`
* Talent `users.id`

Never:

* candidate ID
* application ID
* email
* profile ID

The application/job is context, not participant identity.

# THREAD REUSE RULE

This is critical.

Before creating a thread, check for an appropriate existing thread created by:

* Client direct messaging
* accepted invitation
* existing application chat
* previous Message click
* previous Reach the Client click

Do not create duplicates.

Repeated:

`Message`

or:

`Reach the Client`

must return the same thread ID.

---

# JOB / APPLICATION CONTEXT

`job_id`

or subject,

use the application job as context.

For example:

subject:

`Social Media Manager`

Do not overwrite a valid existing thread's context unnecessarily.

If the current architecture uses one direct Client↔Talent thread regardless of job, preserve that rule.

Do not invent a new identity rule without checking current messaging behavior.

* authenticated
* role Client
* application belongs to Client's job

### Talent

* authenticated
* application belongs to Talent
