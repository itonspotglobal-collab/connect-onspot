# Implement Unified Manual Wise Payment and Receipt Verification Across OnSpot

## Project

Repository: `itonspotglobal-collab/connect-onspot`

Implement a unified manual Wise payment and administrator verification workflow across all applicable OnSpot payment flows.

**Important:** We do not have a payment gateway integration yet. Do not implement the Wise API, Stripe, PayPal, automatic payment processing, automatic bank verification, or automated transfers.

The intended process is:

1. The customer sees the correct amount due and OnSpot's Wise payment instructions/QR code.
2. The customer makes the payment externally using Wise.
3. The customer submits a payment reference and uploads their receipt.
4. The system marks the submission as **Pending Verification**, not Paid.
5. An authorized administrator reviews the receipt and independently confirms that the payment actually arrived in the correct Wise account.
6. Only after successful admin verification does the relevant payment become **Paid**.
7. If the submission is rejected, the customer can submit corrected proof.

The Wise QR code will be provided later. **Do not invent, generate, or hardcode a real Wise QR code, recipient account, payment URL, or bank details.**

Implement the complete workflow now, with a configurable QR code and payment instructions that can be populated later.

## 3. Shared manual payment architecture

Implement a reusable manual payment proof and verification capability that attaches to existing financial obligations.

Prefer a normalized model containing:

- Unique payment submission ID
- Payment category / obligation type
- Existing obligation ID
- Payer identity derived from authenticated ownership
- Expected amount and currency, obtained from the server
- Submitted payment reference
- Receipt attachment metadata
- Submitted timestamp
- Verification status
- Verifying administrator ID
- Verified timestamp
- Rejection reason
- Audit history

Use the repository's existing tables and naming conventions where possible.

Do not duplicate invoices or store separate, conflicting paid balances.

If creating new tables, use proper foreign keys, indexes, constraints, and a safe association design that avoids orphaned or cross-tenant payment records.

The shared proof system should be usable by different financial modules while allowing each module to retain its own domain-specific payment status and lifecycle.

## 4. Payment statuses

Implement or map these concepts to existing compatible statuses:

- `awaiting_payment`
- `verification_pending`
- `paid`
- `rejected`

Retain existing invoice states such as issued, overdue, void, refunded, invalidated, or payment_failed where applicable.

Do not replace an established status model blindly.

Rules:

- Uploading a receipt must NEVER automatically mark a payment Paid.
- Entering a payment reference must NEVER automatically mark a payment Paid.
- Only an authorized server-side admin verification operation can confirm payment.
- Rejected payment proofs must remain in the audit history.
- Users may resubmit proof when permitted.
- Duplicate submissions or repeated verification requests must not create duplicate financial credits.
- Already verified payments must not be marked paid again.
- Voided or invalidated obligations must not accept new payment proofs unless explicitly allowed by existing business rules.
- Preserve partial-payment handling if already supported; do not silently treat partial settlement as full payment.

For manual transfers, the receipt is evidence submitted by the payer, not independent evidence of settlement.
