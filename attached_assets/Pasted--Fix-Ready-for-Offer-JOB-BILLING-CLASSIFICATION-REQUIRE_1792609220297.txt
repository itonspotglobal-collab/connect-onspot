# Fix Ready for Offer — JOB_BILLING_CLASSIFICATION_REQUIRED (409)

## Problem

When a client opens the **Extend an Offer** modal on the Job Submissions page and clicks **Ready for Offer**, the application returns:

POST `/api/client/hiring-invoices/ready`

HTTP 409 Conflict

Error code: `JOB_BILLING_CLASSIFICATION_REQUIRED`

Error message:
"The job needs a valid engagement type and billing mode before a hiring invoice can be issued."

The frontend currently displays the raw API error JSON in the modal.

Please fix the underlying job classification issue and improve the user experience without bypassing any financial safeguards.

## 1. Investigate the root cause

Inspect the current implementations of:

- `server/services/hiringPaymentService.ts`
- `client/src/components/hiring-payments/ClientHiringPayments.tsx`
- `client/src/components/hiring-payments/paymentTypes.ts`
- Job creation and editing forms
- Job Submissions and Extend an Offer components
- Job schema, database migrations, and existing billing validation

Trace how `engagement_type` and `billing_mode` are initially captured, persisted, updated, and retrieved.

Determine why the test job, **Testing Job Kime**, lacks a valid classification.

Check whether the issue is caused by:
- Missing fields during job creation
- Incorrect frontend-to-backend field mapping
- Existing legacy job records with null or invalid values
- Incorrect casing or enum normalization
- Job editing not saving the classification
- The offer workflow reading stale or incorrect job data

Do not assume the cause without checking.

## 2. Preserve billing validation

The current backend validation is intentional.

Valid classifications are:

`engagement_type`:
- `Lite`
- `Standard`

`billing_mode`:
- `tracked`
- `guaranteed`

Do not remove this validation.

Do not automatically assign Standard, Lite, Tracked, or Guaranteed just to make the error disappear.

Do not bypass invoice creation, payment verification, or the pre-offer payment gate.

## 3. Fix job creation and editing

Ensure that the active job creation and editing workflows correctly capture and persist the required engagement type and billing mode.

Requirements:

- Use clear user-facing labels.
- Provide the valid options.
- Ensure values match the backend enum requirements.
- Validate required selections before submission.
- Persist the values correctly.
- Ensure editing an existing job updates the intended record.
- Avoid introducing duplicate fields or conflicting billing classifications.

If classification can legally change after a job has been used for contracts or financial records, enforce existing restrictions and preserve immutable financial snapshots.

Do not silently alter previously issued invoices or contracts.

## 4. Handle existing jobs missing classification

For legacy jobs with missing or invalid classification:

- Detect the missing values.
- Show the client which classification information needs to be completed.
- Provide an authorized route to update the job when permitted.
- If the job cannot be edited due to its lifecycle, show a clear explanation and the appropriate administrative resolution path.
- Preserve existing job submissions and applicant relationships.
- Do not delete or recreate jobs.
- Do not run a bulk migration that guesses classifications.

For the specific test job, identify its current stored classification values and explain how to correct them through the supported application workflow.

## 5. Improve Ready for Offer error handling

Update the frontend so the raw JSON error is not shown directly to users.

When the API returns `JOB_BILLING_CLASSIFICATION_REQUIRED`, display:

**Job billing setup required**

"This job needs an engagement type and billing mode before a hiring invoice can be prepared. Please complete the job's billing settings and try again."

Provide a **Review Job Billing Settings** action when an authorized edit route is available.

If no safe edit route exists, provide clear guidance to contact the appropriate administrator.

Handle other known billing errors separately, including:

- `HIRING_BILLING_POLICY_REQUIRED`
- Authorization errors
- Ineligible workflow stages
- Existing invoice conflicts
- Unexpected server errors

Preserve structured error codes in the API client so the UI can handle them reliably rather than parsing raw JSON strings.

## 6. Preserve payment and offer safeguards

After the job classification is corrected:

1. Client clicks Ready for Offer.
2. Backend validates job classification and hiring fee policy.
3. An eligible hiring invoice is created or the existing invoice is returned.
4. Client sees the configured Wise payment instructions when applicable.
5. Client uploads the receipt.
6. Invoice becomes Pending Verification.
7. Super Admin independently verifies settlement.
8. Only then may the existing offer workflow proceed.

Do not automatically mark invoices paid.

Do not change billing formulas, commission rates, security deposits, or talent payout rules.

Do not create duplicate invoices when Ready for Offer is clicked repeatedly.

## 7. Tests

Add regression tests for:

1. Job creation with valid Lite + tracked classification.
2. Job creation with valid Standard + guaranteed classification.
3. Missing classification rejected with a clear validation error.
4. Existing unclassified job can be corrected through an authorized workflow.
5. Unauthorized users cannot change another client's job classification.
6. Ready for Offer succeeds in preparing the invoice when all prerequisites are satisfied.
7. Ready for Offer displays a friendly message for missing classification.
8. Missing hiring fee policy remains independently guarded.
9. Repeated Ready for Offer requests do not duplicate invoices.
10. An unverified invoice does not unlock sending an offer.
11. Verified payment continues to unlock only the existing eligible offer workflow.
12. Previously issued financial records remain unchanged.

Test the actual Job Submissions → Extend an Offer → Ready for Offer flow using an authenticated development client account if available.

If authenticated testing is unavailable, distinguish automated tests from actual user acceptance testing.
