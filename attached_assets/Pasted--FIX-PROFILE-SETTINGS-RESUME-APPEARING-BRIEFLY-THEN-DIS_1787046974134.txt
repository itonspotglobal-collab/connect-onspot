# FIX PROFILE SETTINGS RESUME APPEARING BRIEFLY THEN DISAPPEARING

There is still a specific resume synchronization bug in the Talent Profile / Profile Settings flow.

Do NOT make another broad refactor.

Investigate and fix this exact behavior.

---

# Reproducible Bug

The Candidate already has a resume.

It is visible correctly on:

**Talent Profile**

Example:

```text
Legaspi_CV.pdf
```

But on:

**Profile Settings → Documents**

it shows:

```text
No resume uploaded yet.
```

There is an even more important clue:

When a resume is uploaded/replaced, the resume may briefly appear inside Profile Settings for a few seconds and then disappear again.

This indicates that the upload/candidate cache is initially correct, but a later server refetch is overwriting the cache with Candidate data that does not contain:

```ts
resumeUrl
resumeFileName
```

Fix the actual refetch/data-response problem.

---

# LIKELY FAILURE SEQUENCE

The current flow appears to behave like this:

```text
POST /api/candidates/:id/resume
          ↓
backend saves resumeUrl + resumeFileName
          ↓
frontend updates React Query cache
          ↓
resume appears correctly
          ↓
candidate query is invalidated
          ↓
GET /api/candidates/:id refetches
          ↓
response does not contain resume metadata
          ↓
React Query replaces cached Candidate
          ↓
resume disappears
```

That is why the resume briefly shows and then becomes:

```text
No resume uploaded yet.
```

Do not patch over this with local state.

Find out why the Candidate refetch loses the resume fields.

# 2. PROFILE SETTINGS MUST FETCH THE CANDIDATE AS THE AUTHENTICATED OWNER

Inspect:

```text
client/src/hooks/useCandidateProfileSettings.ts
```

The current candidate query uses:

```ts
fetch(`/api/candidates/${candidateId}`)
```

but apparently does not send the Talent JWT.

This is suspicious.

Profile Settings is an **owner/private screen**.

The request should identify the logged-in talent so the server can return private owner fields.

Change the Settings candidate query to use the authenticated Talent token.

Conceptually:

```ts
const auth = loadTalentAuth();

const res = await fetch(`/api/candidates/${candidateId}`, {
  headers: auth?.token
    ? {
        Authorization: `Bearer ${auth.token}`,
      }
    : undefined,
  credentials: "include",
});
```

Do not blindly copy this if the project has a shared authenticated fetch helper.

Use the existing supported authentication architecture.

# 7. PROFILE SETTINGS QUERY SHOULD LOOK CONCEPTUALLY LIKE THIS

Refactor:

```ts
useQuery({
  queryKey: ["candidate-profile", candidateId],

  queryFn: async () => {
    if (!candidateId) return null;

    const auth = loadTalentAuth();

    const res = await fetch(
      `/api/candidates/${candidateId}`,
      {
        headers: auth?.token
          ? {
              Authorization: `Bearer ${auth.token}`,
            }
          : {},
        credentials: "include",
      },
    );

    if (!res.ok) {
      ...
    }

    return res.json();
  },
});
```

Again, use a project-wide helper if one already exists.

Do not introduce another authentication implementation.

# 9. IMPORTANT: TALENTPROFILE AUTH LOAD TIMING

TalentProfile currently restores `talentAuth` after component mount.

Check this carefully.

Possible race:

```text
Render
   ↓
talentAuth = null
   ↓
candidate GET fires as public
   ↓
public sanitized candidate cached
   ↓
talentAuth loads
```

If so, make the owner/private candidate query respond correctly when auth becomes available.

Possible solution:

Include owner-auth state in the query behavior or explicitly refetch once `talentAuth` is restored.

Do not create an infinite query loop.

A conceptual approach:

```ts
const ownerToken =
  talentAuth?.candidateId === id
    ? talentAuth.token
    : null;
```

Then the query function sends auth when available.

If necessary:

```ts
useEffect(() => {
  if (ownerToken) {
    qc.invalidateQueries({
      queryKey: ["/api/candidates", id],
    });
  }
}, [ownerToken, id]);
```

Only do this if the current query architecture requires it.
