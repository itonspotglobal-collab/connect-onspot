Please adjust the newly updated Create/Edit Job Posting form.

This change must apply to BOTH:

* Admin Create/Edit Job Posting
* Client Account Create/Edit Job Posting

Do not fix only one account type.

The current overall 4-step form structure is correct, but the validation and Required Skills behavior need to be corrected.

# 1. Make these fields OPTIONAL

Do NOT require the following fields anymore:

* Work Setup
* Duration
* Company Name
* Job Description on Step 2
* Minimum Educational Attainment on Step 3
* Required Skills

Remove the red required `*` indicator from all of these labels.

Also remove any frontend validation that blocks Continue/Submit when these fields are empty.

Remove any corresponding backend/Zod validation that incorrectly requires them for new job creation or updates.

Do not introduce database `NOT NULL` constraints for these fields.

## Work Setup

Change:

`Work Setup *`

to:

`Work Setup — optional`

or simply:

`Work Setup`

The only visible option may still be:

`Remote`

But users must be allowed to leave Work Setup unselected.

Do not automatically force `Remote` if the user leaves it empty unless the backend absolutely requires a location value.

If the existing database has a default such as `Remote`, inspect the current behavior first. Prefer preserving an intentionally blank selection in the form rather than pretending the user selected Remote.

For create/update payloads, handle an empty Work Setup safely.

## Duration

Change:

`Duration *`

to:

`Duration — optional`

Users may leave it blank.

Keep the current duration options, but remove validation requiring a selection.

## Company Name

Change:

`Company Name *`

to:

`Company Name — optional`

Do not block submission when Company Name is blank.

Do not force `"OnSpot"` simply because the field is empty unless that is an existing intentional backend business rule.

Inspect current payload construction. If code currently does something like:

```ts
company: formData.company.trim() || "OnSpot"
```

review whether that still matches the new requirement.

If blank Company Name should remain blank/null, update the create/edit payload safely.

Preserve existing company values when editing old jobs.

## Job Description — Step 2

Change:

`Job description *`

to:

`Job description — optional`

The Description step should still show the same single large editor from the HTML mockup.

However:

* user may click Continue with it empty
* user may submit the job with it empty
* frontend validation must not reject it
* server validation must not reject it solely because it is empty

Important:

The current database schema may have `description NOT NULL`.

Inspect this before changing behavior.

If PostgreSQL requires a non-null description, make a safe schema/migration decision rather than causing another 500 error.

Preferred outcome:

* make `jobs.description` nullable if the new product requirement says Job Description is truly optional

If changing nullability has wider compatibility risks, document them and implement the safest consistent solution.

Do not silently submit fake placeholder text just to satisfy a NOT NULL constraint.

## Minimum Educational Attainment

Change:

`Minimum educational attainment *`

to:

`Minimum educational attainment — optional`

The dropdown should allow no selection.

Do not block Continue or Submit if it is blank.

Store `null` / empty appropriately.

## Required Skills

The entire Required Skills section is optional.

A job can have:

* zero skills
* one skill
* multiple skills

Do not require any skill to be added.

Do not show validation errors when no skills exist.

# 2. Remove all hardcoded skills

The current implementation is wrong because it renders these predefined skills automatically:

* Graphic design
* Customer support
* Sales / cold outreach
* Bookkeeping / accounting
* Copywriting

REMOVE ALL OF THESE DEFAULT/HARDCODED SKILL ROWS.

The HTML mockup only showed those entries as examples of what added skills could look like. They are not intended to be default values.

When the user first opens Step 3, the Required Skills section should be EMPTY.

It should look conceptually like:

```text
REQUIRED SKILLS

Tick each skill and set how many years of experience you'd like.

+ Add another skill
```

There should be no skill cards until the user adds one.

# 3. Add skill behavior

When the user clicks:

`+ Add another skill`

add one editable skill row.

That row should contain:

* skill name input
* years of experience dropdown
* remove/delete control

Example:

```text
[ Skill name __________________ ] [ Any experience ▼ ] [Remove]
```

Years options:

* Any experience
* 1+ years
* 2+ years
* 3+ years
* 5+ years

The newly added skill should NOT require a separate checkbox.

Because the user explicitly clicked Add another skill, the row itself represents a selected/required skill.

This is cleaner than showing an unchecked skill row.

Allow the user to add multiple rows.

Allow the user to remove any row.

If every row is removed, the skills list should return to the empty state.

# 4. Do not save blank skill rows

If the user clicks `+ Add another skill` but leaves the skill name blank:

* do not save that blank skill
* do not add it to `skillTags`
* do not persist an empty structured skill object

On payload construction, filter out blank skill names.

Example logic:

```ts
skills
  .filter((skill) => skill.name.trim())
```

Do not block the whole form just because an unfinished blank skill row exists.

# 5. Preserve structured skill experience

If the recent implementation introduced a structured field such as:

```json
[
  {
    "name": "Graphic design",
    "years": "2+"
  }
]
```

keep that approach.

But the initial value must be:

```json
[]
```

not a predefined list.

If the platform also uses `skillTags` for search/matching, derive it from the entered skill names.

Example:

```text
Structured requirements:
[
  { name: "HubSpot", years: "2+" },
  { name: "Cold calling", years: "1+" }
]

skillTags:
["HubSpot", "Cold calling"]
```

Do not hardcode any skills.

# 6. Edit mode behavior

For existing jobs:

* Load saved skills if they exist.
* Show only the actual saved skills.
* Do not append Graphic design, Customer support, or any other default skills.
* If an existing job has no skills, show an empty Required Skills section.
* Existing saved years-of-experience values must load correctly.

When editing, removing all skills should intentionally save an empty skill list if the user actually removed them.

Do not confuse this with unrelated hidden legacy fields.
