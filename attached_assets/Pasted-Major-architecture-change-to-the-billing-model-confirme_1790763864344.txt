Major architecture change to the billing model — confirmed business
rules below. This EXTENDS the already-built Payments engine (Phases
1-3), it does not throw it away, but several existing assumptions need
to be re-examined given this reverses who initiates invoicing and
changes the billing cadence.

CONFIRMED MODEL:

1. Talent → OnSpot: the Talent creates and submits their OWN invoice
   from their account, every 15 days. This is a CLAIM, not an automatic
   payment trigger.

2. OnSpot reviews/approves each Talent invoice against the platform's
   own real attendance/billing data before payment is authorized. Flag
   discrepancies between the Talent's claimed amount and what the
   platform's own computed billing would show — do not silently accept
   whatever the Talent submits.

3. Once approved, a SEPARATE payout record is created to confirm the
   actual third-party payment execution — the Talent invoice and the
   payout are two distinct steps, not one record. This connects directly
   to the payment_provider_accounts framework just built (still no real
   SDK/API call yet, same scaffolding-only discipline as before).

4. OnSpot → Client: a separate, monthly invoice, generated by OnSpot
   (never by the Talent), covering a 30-day period. This invoice equals
   the SUM of that Talent's two 15-day invoices falling within that
   calendar month. Commission is bundled into this invoice as one all-in
   number, exactly as already designed — the Talent never sees this
   Client-facing invoice at all.

AUDIT FIRST, this is critical given how much already exists:
1. The existing billing.ts computes hourly-equivalent and commission
   math on a MONTHLY basis (160hrs Standard / 80hrs Lite). This needs to
   run at 15-DAY granularity now, as the new base unit the Talent
   actually invoices against. Propose exactly how this changes -
   including how Extended Hours and Deductions get computed at the
   15-day level rather than monthly.
2. Confirm how the existing invoice_periods table relates to this new
   model - does it become the 15-day unit directly, or does a new table
   sit alongside it?
3. Propose the exact mechanism for aggregating two 15-day periods into
   one 30-day Client invoice, including how to handle a Talent whose
   engagement doesn't cleanly align to calendar-month boundaries (e.g.,
   started mid-month).

PROPOSE SCHEMA for a new talent_invoices table (or equivalent), covering
at minimum: talent identification (via users.id, consistent with the
just-built payment_provider_accounts anchoring), the 15-day period it
covers, the Talent's claimed amount, status (submitted / under_review /
approved / rejected / disputed), what the platform's own computed amount
was for comparison, reviewer/admin identification, and a link to the
resulting payout record once approved.

Confirm the existing payouts table gets a new FK linking it to the
approved talent_invoice that triggered it, rather than being created
directly from an admin action as before.

Report the full audit findings and a proposed schema/migration plan
before implementing anything - this touches core, already-shipped
billing logic and needs to be gotten right the first time, not
discovered mid-build.
