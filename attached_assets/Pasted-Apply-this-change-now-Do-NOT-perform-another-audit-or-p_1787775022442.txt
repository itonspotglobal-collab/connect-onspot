# GOAL

Currently:

* Clicking `Unapprove` changes the job posting status immediately.
* Clicking `Reject` changes the job posting status immediately.

Change both flows so they require:

1. Confirmation.
2. Open `ClientEmailComposer`.
3. Let Admin review/edit and send the Client email.

Do not change the existing working Approve flow.

# UNAPPROVE FLOW

Current:

Admin clicks `Unapprove`
→ status changes immediately

New:

Admin clicks `Unapprove`
→ show confirmation dialog

Suggested copy:

Title:
`Unapprove this job post?`

Message:
`This will remove the job from approved status. The Client will be notified and you can review the email before sending.`

Buttons:

`Cancel`
`Confirm Unapprove`

If Admin clicks Cancel:

* do nothing
* keep current status
* do not open email composer

If Admin clicks Confirm Unapprove:

1. Persist the unapprove transition using the existing backend logic.
2. Preserve existing in-app notification behavior.
3. Open `ClientEmailComposer`.
4. Preload the appropriate Unapproved email template.
5. Admin can review/edit.
6. Admin sends email manually through the existing composer.

Important:

The job status should already be changed before the email is sent.

If email sending fails:

* keep the job unapproved
* show email failure
* do not roll back status

# REJECT FLOW

Current:

Admin clicks `Reject`
→ rejection/status changes immediately

New:

Admin clicks `Reject`
→ show confirmation first

If a rejection reason is already required, preserve that existing reason input.

Preferred flow:

Admin clicks Reject
→ existing rejection reason input
→ confirmation dialog
→ Confirm Reject
→ persist rejection
→ preserve in-app notification
→ open ClientEmailComposer
→ preload Job Post Rejected template with rejection reason
→ Admin reviews/edits
→ Send Email

Do not remove the rejection reason field.

Do not change rejection business rules.

# IMPORTANT ORDER

For both Unapprove and Reject:

Confirmation
→ persist status change
→ in-app notification
→ ClientEmailComposer opens
→ email send

Do NOT make the status transition wait on successful email delivery.
