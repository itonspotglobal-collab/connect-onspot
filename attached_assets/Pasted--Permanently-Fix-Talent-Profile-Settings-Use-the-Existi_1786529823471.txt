## Confirmed architecture problem

There are currently TWO different Talent/profile systems in this repository:

### Legacy user/profile system

Uses:

* `users`
* `profiles`
* `/api/profiles/me`
* `useTalentProfile()`
* `AuthContext`
* `onspot_jwt_token`
* JWT claims such as:

  * `userId`
  * `email`
  * `role`

### Current Talent Profile system

Uses:

* `candidates`
* Talent Profile page
* `/api/candidates/:id`
* `/api/candidates/:id/photo`
* `/api/talent-auth/login`
* `TalentLoginModal`
* `talent_profile_token`
* JWT claims:

  * `type: "candidate"`
  * `candidateId`
  * `email`

The Talent Profile page already uses the candidate system successfully.

The `/settings` page is still wired to the legacy `/api/profiles/me` system.

This is the main bug.

That hook performs:



This is wrong for the current Talent Profile architecture.

`/api/profiles/me` uses the normal user JWT and the `profiles` table.

The logged-in Talent profile system uses `candidateId` and the `candidates` table instead.

Refactor Talent Profile Settings so it loads/saves the authenticated Talent candidate.

# 5. Save Settings through `/api/candidates/:id`

Use the existing candidate update route.

The backend already supports:

```text
PATCH /api/candidates/:id
```

and understands candidate ownership.

Make Settings send:

```http
Authorization: Bearer <talent_profile_token>
```

Do not use the generic API client unless you modify it in a safe way that explicitly understands both JWT systems.

It is acceptable and probably safer to create a dedicated Talent API helper.

Example:

```ts
export async function talentApiRequest(
  url: string,
  options: RequestInit = {}
) {
  const auth = loadTalentAuth();

  if (!auth?.token) {
    throw new Error("Talent session not found");
  }

  return fetch(url, {
    ...options,
    headers: {
      ...options.headers,
      Authorization: `Bearer ${auth.token}`,
    },
  });
}
```

Do not globally overwrite the normal Client/Admin authentication behavior.
