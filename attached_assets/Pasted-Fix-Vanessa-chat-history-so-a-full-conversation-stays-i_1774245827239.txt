Fix Vanessa chat history so a full conversation stays in one thread and appears as complete chat history on /admin/vanessa-responses.

Problem:
- Right now, Vanessa history is getting split into separate small threads.
- In the admin Vanessa Responses page, I only see 1 user message + 1 Vanessa reply per thread instead of the full conversation.
- These should be grouped as one continuous conversation thread.

Likely cause:
- In client/src/components/VanessaChat.tsx, threadId is stored only in local component state:
  const [threadId, setThreadId] = useState<string | null>(null)
- That makes the OpenAI thread fragile and easy to lose/reset.
- When threadId is lost, new messages start a brand new thread instead of continuing the old one.
- Backend logging in server/services/openaiService.ts and server/storage.ts already supports full multi-turn history by threadId, so the problem is likely frontend thread persistence/reuse.

Please make these changes:

1. Move Vanessa thread state into the shared Vanessa context
   - Update client/src/contexts/VanessaContext.tsx
   - Add:
     - threadId: string | null
     - setThreadId
   - Optionally persist threadId in localStorage or sessionStorage so refreshes do not break the conversation unexpectedly.
   - Make resetConversation() also clear threadId.

2. Update client/src/components/VanessaChat.tsx
   - Remove the local useState for threadId.
   - Use threadId and setThreadId from VanessaContext instead.
   - Make sure every send action always reuses the current threadId if it exists:
     - handleSendMessage
     - handleTopicSelect
   - When SSE returns parsed.type === "threadId", save it to context immediately.
   - Add console logs for debugging:
     - when a message is sent
     - whether an existing threadId is reused
     - when a new threadId is received from the backend

3. Preserve conversation continuity properly
   - Ensure that once the first Vanessa reply creates a thread, all later user messages reuse that same threadId until resetConversation is called.
   - Do not start a new thread unless there is truly no threadId yet.

4. Keep backend logging as-is unless needed
   - Review server/services/openaiService.ts and confirm it already logs each turn with:
     storage.createVanessaLog({ threadId, userMessage, assistantResponse })
   - Review server/storage.ts and confirm getVanessaLogsByThread(threadId) is already capable of returning the full conversation.
   - Only change backend code if you find a real bug, not just for refactoring.

5. Add a small safeguard
   - If messages already exist in VanessaContext but threadId is missing, add a warning log so this problem is easier to catch in the future.

6. After changes, summarize:
   - what files were changed
   - what caused the history to split
   - how the fix ensures the whole conversation now stays under one thread
   - whether threadId is persisted only in memory, sessionStorage, or localStorage

Important:
- Do not change the database schema unless absolutely necessary.
- Prefer the smallest safe fix.
- The goal is: one ongoing Vanessa conversation = one threadId = one complete history in /admin/vanessa-responses.
