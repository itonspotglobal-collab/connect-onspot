Before making any changes, inspect the existing implementation and identify exactly how production email and object storage currently work.

- which application workflows depend on this storage

Pay particular attention to:

- resumes
- video introductions
- candidate media/documents
- any other production uploads using the same storage layer

# PHASE 3 — Perform a Real Email Test

Using the existing production Microsoft Graph email implementation, send a harmless test email to an approved test inbox that can actually be checked.

Do not create a fake/mock email service.

Do not bypass the application's Graph implementation merely to prove Microsoft Graph itself works.

The purpose is to prove that the application's actual email transport can successfully send email in the deployed environment.

Use an obvious test subject, for example:

`OnSpot Production Email Verification`

The message should clearly state that it is a test and requires no action.

Verify BOTH:

1. Microsoft Graph accepted/sent the message successfully.
2. The destination mailbox actually received the message.

A successful API response alone is useful evidence, but the strongest PASS requires confirming receipt at the destination mailbox.

Record safe evidence such as:

- test timestamp
- recipient address with sensitive portions redacted if appropriate
- test subject
- application/Graph success response without tokens or secrets
- evidence that the message arrived

Do NOT expose authentication headers or credentials.

### Microsoft Graph PASS criteria

Mark:

`PASS`

only if a real email was successfully sent through the application's actual Microsoft Graph implementation and received by the destination mailbox.

If credentials exist but sending fails:

`FAIL — configured but email delivery failed`

If required configuration is missing:

`FAIL — Microsoft Graph email is not fully configured`

If sending succeeds but mailbox receipt cannot be verified:

`INCONCLUSIVE — send accepted, receipt not independently verified`

Do not call this PASS.

# PHASE 5 — Perform a Real Object Storage Test

Perform an actual end-to-end object-storage test through the application's real storage implementation.

Create a harmless temporary test file such as:

`onspot-storage-verification.txt`

with simple content such as:

`OnSpot object storage verification test.`

Include a timestamp if useful.

Then test the actual storage flow.

### Required test

1. Request/create an upload through the application's existing object-storage implementation.
2. Upload the test file.
3. Confirm the upload succeeds.
4. Retrieve/read the same stored object using the application's supported retrieval mechanism.
5. Verify that the retrieved file contents match the uploaded contents.

Do not consider generation of an upload URL by itself a successful test.

Do not consider an HTTP upload response by itself sufficient.

The object must be retrieved again successfully.

If appropriate and safe, delete the temporary verification object after successful testing.

Do not delete real user files.

### Object Storage PASS criteria

Mark:

`PASS`

only if:

`create/request upload`
→ `upload actual file`
→ `retrieve stored file`
→ `verify matching contents`

all succeed against the production/deployed storage configuration.

If configuration exists but upload fails:

`FAIL — configured but upload failed`

If upload succeeds but retrieval fails:

`FAIL — upload succeeded but retrieval failed`

If required configuration is missing:

`FAIL — object storage is not fully configured`
