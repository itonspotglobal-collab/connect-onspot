# IMPORTANT EXISTING PRODUCT RULES TO PRESERVE

The current product has deliberate messaging/security behavior.

Do not accidentally remove it.

## 1. Participant-only access

Only users who belong to a message thread may:

* see the thread
* read its messages
* send messages
* mark it read

A third-party authenticated user must receive an appropriate 403/404 response and must not learn private thread/message information.

---

## 2. Server-controlled sender identity

Never trust a frontend-provided `senderId`.

The sender must always be derived from the authenticated identity.

A malicious user submitting somebody else's `senderId` must not be able to spoof another participant.

---

## 3. Support both authentication paths

Messaging must work correctly for:

### Main account JWT

Examples:

* Client
* Talent using normal user account

### Talent portal/candidate authentication

The candidate-oriented token may identify a candidate record rather than directly exposing the canonical `users.id`.

The server must normalize the authenticated identity to the correct `users.id` before participant checks, notifications, read state, etc.

Do not fix Client messaging while breaking Talent portal messaging.
