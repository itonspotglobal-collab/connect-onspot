CRITICAL DESIGN REQUIREMENT — resolve before writing any code:
Anonymous, unauthenticated search must NOT create a persisted scaffold job
row per request. The current /api/client/talent-search flow writes a real
row to `jobs` on every call — if that's made public with no auth gate, it
becomes a denial-of-service and data-pollution vector (anyone could loop it
and flood the jobs table with zero accountability).

Propose a design for this before implementing — options to consider:
(a) A separate, read-only anonymous preview endpoint that computes match
    scores WITHOUT persisting any job row — pure computation against the
    scorer, no DB write, until the visitor actually converts (signs up or
    logs in).
(b) Rate-limiting the existing endpoint aggressively for unauthenticated
    callers plus an aggressive cleanup job for anonymous-origin scaffold
    rows.
(c) Something else you think fits the existing architecture better.

Report back with your recommendation and reasoning before implementing —
this is a real security/abuse design decision, same weight as the earlier
passwordHash and participant-gate work, not a detail to default silently.
