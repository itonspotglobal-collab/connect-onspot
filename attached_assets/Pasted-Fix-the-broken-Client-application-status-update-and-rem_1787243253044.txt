Fix the broken Client application status update and remove the duplicate Client/Admin status-change implementations.

## IMPORTANT PRODUCT DECISION

Client and Admin should now use the SAME core application status update workflow.

For BOTH roles:

```text
Choose new status
        ↓
Email Applicant
        ↓
Choose email template
        ↓
Review/edit email
        ↓
Send Email
        ↓
ONLY if email succeeds:
    update application status
    write status history
    notify Talent
    notify other required role(s)
```

The Client status selector must no longer use its separate broken PATCH implementation.

There should be ONE shared backend application-status-with-email service used by:

* Admin
* Client

with role-specific authorization and notifications.

---

# CURRENT CLIENT FAILURE

The Client Profile / Job Submissions Application Details modal still returns:

`500 Internal Server Error`

when changing application status.

Do NOT keep patching that broken Client route independently.

Find it, remove its duplicated transition implementation, and route Client status changes through the same tested shared transition service used by Admin.

---

# PRIMARY ARCHITECTURE

Create/reuse one shared service conceptually like:

```ts
changeApplicationStatusWithEmail({
  applicationId,
  newStatus,
  actorUserId,
  actorRole,
  emailPayload,
})
```

or an equivalent existing service.

The service owns:

1. application lookup
2. authorization
3. current-status lookup
4. status transition validation
5. applicant recipient resolution
6. email send
7. canonical status update
8. status history
9. notifications
10. final response

Do not implement these separately in Client and Admin routes.

# SHARED WORKFLOW, DIFFERENT AUTHORIZATION

## Admin

Admin may update applications according to the existing Admin-settable status rules.

## Client

Client may update an application ONLY when:

```text
application.job_id
→ job
→ job.client_id
=== authenticated Client users.id
```

or according to the existing canonical job ownership relation.

Client must never update applications belonging to another Client.

The shared service must receive actor context but authorization remains role-aware.

# DO NOT UPDATE STATUS BEFORE EMAIL


# ROW LOCKING

The shared status service should preserve concurrency safety.

Lock only the canonical application row:

```sql
SELECT *
FROM job_submissions
WHERE id = $1
FOR UPDATE;
```

Do not apply unrestricted:

`FOR UPDATE`

to nullable `LEFT JOIN` results.

After locking the submission:

fetch separately:

* job
* Client
* Talent/candidate
* other related information

This prevents the PostgreSQL error previously seen.

---

# DO NOT MAKE OPTIONAL RELATIONSHIPS BREAK STATUS CHANGE

Some application relations may be nullable.

For example:

* Talent account not linked yet
* candidate optional data
* optional Client profile metadata

Do not use an INNER JOIN just to avoid locking errors.

Preserve nullable behavior.
