Implement the first foundation of a **Company / Organization feature for Client users** in the existing OnSpot application.

Use the existing repository and architecture. **Inspect the current implementation before modifying anything. Do not rewrite working authentication, navigation, client profile, hire talent, messages, or settings functionality.**

### Important Context

The existing Client account represents an individual user who logs in with their own credentials.

A Client user may be:

1. An **independent client / contractor** who does not belong to a company yet.
2. The **owner of a company/organization**.
3. Later, a **member of another organization** after being invited.

For this task, implement only the initial organization creation foundation.

Do **not** force every existing Client user to create an organization.

Existing Client accounts with no organization must continue working exactly as they do now.

# 4. Add an organizations table

Inspect `shared/schema.ts` and follow the existing Drizzle/PostgreSQL conventions.

Add a new table named:

`organizations`

Suggested structure:

```ts
export const organizations = pgTable(
  "organizations",
  {
    id: varchar("id")
      .primaryKey()
      .default(sql`gen_random_uuid()`),

    name: text("name").notNull(),
    website: text("website"),
    industry: text("industry"),
    companySize: text("company_size"),
    location: text("location"),
    about: text("about"),
    timezone: text("timezone"),

    createdBy: varchar("created_by")
      .notNull()
      .references(() => users.id),

    createdAt: timestamp("created_at").defaultNow(),
    updatedAt: timestamp("updated_at").defaultNow(),
  },
  (table) => [
    index("idx_organizations_created_by").on(table.createdBy),
    index("idx_organizations_created_at").on(table.createdAt),
  ],
);
```

Adjust naming/types if necessary to match the repository's established schema patterns.

Also add appropriate insert/select schemas and TypeScript types using the project's current Drizzle/Zod conventions.

# 5. Add organization membership table

Also create:

`organization_members`

This table connects individual Client users to organizations.

Suggested structure:

```ts
export const organizationMembers = pgTable(
  "organization_members",
  {
    id: varchar("id")
      .primaryKey()
      .default(sql`gen_random_uuid()`),

    organizationId: varchar("organization_id")
      .notNull()
      .references(() => organizations.id),

    userId: varchar("user_id")
      .notNull()
      .references(() => users.id),

    role: text("role")
      .notNull()
      .default("member"),

    status: text("status")
      .notNull()
      .default("active"),

    invitedBy: varchar("invited_by")
      .references(() => users.id),

    joinedAt: timestamp("joined_at").defaultNow(),
    createdAt: timestamp("created_at").defaultNow(),
    updatedAt: timestamp("updated_at").defaultNow(),
  },
  (table) => [
    uniqueIndex("organization_member_unique").on(
      table.organizationId,
      table.userId,
    ),

    index("idx_org_members_org").on(table.organizationId),
    index("idx_org_members_user").on(table.userId),
  ],
);
```

For this first version, valid organization roles may simply be:

* owner
* admin
* member

Do not build the full permissions system yet.

# 6. Organization creation transaction

When a Client user creates an organization, the backend should perform these actions atomically:

```text
1. Validate authenticated user
2. Confirm user.role === "client"
3. Create organization
4. Set organizations.createdBy = current user.id
5. Create organization_members record
6. organization_members.userId = current user.id
7. organization_members.organizationId = new organization.id
8. organization_members.role = "owner"
9. organization_members.status = "active"
```

Prefer a database transaction so that organization creation and owner membership cannot become inconsistent.

The user creating the organization automatically becomes its **owner**.

# 11. Important account model

Maintain this distinction throughout the implementation:

```text
USER
= the individual person who logs in

CLIENT ROLE
= their system account type

ORGANIZATION
= a shared company/workspace

ORGANIZATION MEMBERSHIP
= relationship between a Client user and an organization
```

Example:

```text
Val Client
role = client

        │
        ├── personal Client Profile
        │
        └── membership
              ↓
            OnSpot
            role = owner
```

Another Client user can later be invited:

```text
Anna
role = client

membership:
Anna → OnSpot → member
```

Each user must keep their own login/session.

Never create shared organization credentials.
