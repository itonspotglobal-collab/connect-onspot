# Implement Talent Application List for Talent Accounts

You are working inside the existing **OnSpot Global / connect-onspot** codebase.

Implement a new **Talent Application List** feature that is available **only to authenticated Talent accounts**.

Before making changes, inspect the current implementation and reuse existing architecture, authentication, database schema, components, API patterns, styling, and application-status logic. Do **not** create a duplicate application system.

Important existing files/components to inspect first:

* `client/src/pages/TalentProfile.tsx`
* `client/src/components/TopNavigation.tsx`
* `client/src/App.tsx`
* `client/src/pages/AdminJobApplications.tsx`
* `shared/schema.ts`
* relevant server routes/services/storage dealing with `jobApplications`
* existing Talent authentication logic, including both the Talent-specific auth token flow and the normal JWT Talent user flow

The Admin Job Applications feature already manages the authoritative application records and status values. The Talent Application List must display those **same application records** and immediately reflect status changes made by Admin.

---

## Feature 1 — New Talent Application List Page

Create a new Talent-only page, preferably:

`client/src/pages/TalentApplications.tsx`

Route suggestion:

`/talent/applications`

or, if the existing routing conventions indicate a more appropriate Talent route, follow the existing convention.

### Access control

This page must be accessible **only to the Talent account that owns the applications**.

Do not expose another talent's applications.

Support the existing Talent authentication mechanisms already used in the project.

The backend must determine the current Talent from authenticated identity such as:

* Talent JWT / authenticated user ID
* candidate ID associated with the Talent account

Do **not** trust a candidate ID, email, or talent ID supplied by the frontend query string to determine ownership.

Client and Admin accounts must not be able to access the Talent Application List through this Talent route.

If an unauthorized user attempts to access it, follow the project's existing redirect/authorization behavior.

---

# Backend / API

Create or reuse a Talent-facing API that returns only the logged-in Talent's applications.

Suggested endpoint:

`GET /api/talent/applications`

If a suitable existing endpoint already exists, reuse it instead.

Do NOT call the Admin Job Applications endpoint directly from the Talent page if it requires admin privileges.

The Talent endpoint should derive the authenticated Talent/candidate from the session/token and query the existing `jobApplications` records.

Return enough information for the UI, for example:

```ts
{
  id: string;
  jobId: string;
  jobTitle: string;
  jobCompany?: string;
  status: string;
  submittedAt?: string;
  updatedAt?: string;
}
```

Include additional existing job metadata when readily available, such as:

* employment type
* work setup/location
* department/category
* job slug or route needed to open the role

Do not add redundant database fields if this information can already be obtained from existing application/job relationships.

### Critical data requirement

The Talent page must use the **same application record/status source** that powers:

`client/src/pages/AdminJobApplications.tsx`

Therefore, if Admin changes an application from:

* `submitted`
* `under_review`
* `shortlisted`
* `interview`
* `offered`
* `hired`
* `rejected`
* `withdrawn`

the Talent must see the corresponding new status.

Also preserve compatibility with any legacy status aliases already supported by the existing implementation, such as `new` or `reviewed`, if they still exist in stored data.

# Data association requirements

A Talent's application list must be based on the actual existing Job Application records.

Inspect `shared/schema.ts` and the application submission flow to determine how applications currently associate to Talent/Candidate records.

Use the strongest existing relationship available, preferably:

1. `talentId` / candidate relationship if already stored
2. authenticated candidate ID
3. existing normalized relationship used by Admin Job Applications

Avoid relying only on raw email matching if a proper Talent/candidate relation exists.

Email can be used only as a backwards-compatible fallback for older application records if the existing system requires it.

If you implement fallback matching, ensure it cannot allow one account to read another account's applications.

# Important implementation rule

Before coding, trace the current application lifecycle end-to-end:

**Find Work application submission → jobApplications storage → Talent/candidate linking → Admin Job Applications → Admin status update**

Then build the Talent-facing feature on top of that same data flow.

Do not create mock application data.

Do not create a separate `talentApplications` table unless the current architecture absolutely requires it.

The existing Job Application record must remain the single source of truth.
