# IMPORTANT DEFINITIONS

For this application, define status accurately.

## Delivered

`Delivered` means:

> The message was successfully persisted by the OnSpot backend/database and is available to the recipient.

Do NOT claim device-level push delivery because this application does not currently have that infrastructure.

After:

`POST /api/messages`

successfully commits the message:

sender may display:

`Delivered`

## Read

`Read` means:

> The other participant has opened/read the conversation and their canonical `users.id` exists in the message's `readBy` state.

Do not fake Read based on elapsed time.

# ONE SOURCE OF TRUTH FOR UNREAD

Do not calculate unread based only on notification rows if actual message read state can disagree.

Preferred canonical definition:

A message is unread for user X when:

```text
X belongs to thread
AND message.senderId != X
AND X is NOT in message.readBy
```

Ideally expose server-calculated unread counts from:

`GET /api/me/message-threads`

or a dedicated authenticated unread endpoint.

For example, each thread may return:

```json
{
  "id": "...",
  "unreadCount": 2
}
```

and optionally response-level:

```json
{
  "totalUnreadCount": 3
}
```

Then navigation badges can use the same canonical value.

If the current notification system remains the source of the global badge, ensure it is reconciled perfectly with message read state.

Do not have two independent counts that disagree.

# READ STATUS LOGIC

For a two-party Client↔Talent thread:

```ts
const otherParticipantId =
  thread.participants.find(id => id !== meId);

const isRead =

  message.readBy?.includes(otherParticipantId);
```

```text
isRead ? "Read" : "Delivered"
```
