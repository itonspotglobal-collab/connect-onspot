TASK: Fix ALL OnSpot email CTA/deep links so they use the correct
application domain and navigate to the exact authenticated destination.

This issue was confirmed during real manual UAT.

============================================================
OBSERVED BUG
============================================================

Emails are successfully being delivered.

Examples:

1. Offer email:
   "You have a new offer"
   CTA: "Review Offer"

2. Contract email:
   "Your contract has been executed"
   CTA:
   "Review the contract and required signatures in OnSpot"

However, clicking these links does NOT navigate to the intended
Offer/Contract page.

Instead, the user is redirected to the public website/homepage.

Additionally, the generated URL is using the WRONG domain:

talent.onspotglobal.com

This must be fixed SYSTEM-WIDE.

Do NOT patch only the Offer and Contract templates.

Audit every transactional email that generates an OnSpot application URL.

============================================================
2. CREATE ONE CANONICAL URL BUILDER
============================================================

Do NOT allow individual email templates to construct application URLs
independently.

Create/reuse one server-side helper such as:

getAppBaseUrl()

and:

buildAppUrl(path)

or equivalent.

Example conceptual behavior:

buildAppUrl("/talent/offers/123")

→

https://<CANONICAL_APP_DOMAIN>/talent/offers/123

The actual implementation must match the project's routing architecture.

All transactional emails should use this centralized URL builder.

============================================================
3. ENVIRONMENT CONFIGURATION
============================================================

The canonical application origin should come from trusted server-side
configuration.

For example:

APP_BASE_URL=https://<correct-production-app-domain>

Use the project's existing environment-variable naming if one already
exists.

Do NOT hardcode:

talent.onspotglobal.com

inside templates.

Do NOT derive security-sensitive URLs from arbitrary request Host headers.

Production should have one explicitly configured canonical application
origin.

Development/staging may use their corresponding configured origins.

Validate and normalize the configured origin.

Avoid malformed URLs such as:

https://domain.com//path

============================================================
4. OFFER EMAIL DEEP LINK
============================================================

The "Review Offer" button must navigate to the actual offer experience.

Prefer a specific destination when supported:

/talent/offers/:offerId

or the existing equivalent.

If the application currently handles offers inside My Applications rather
than a dedicated route, deep-link using the existing routing/state model,
for example:

/talent/applications/:applicationId?offer=<offerId>

DO NOT invent a route that the frontend does not support.

Audit the router first.

The important requirement is:

Review Offer
→ exact actionable offer
→ Talent can Review / Accept / Decline

NOT:

Review Offer
→ homepage

and preferably NOT:

Review Offer
→ generic dashboard requiring the Talent to search manually.

============================================================
6. AUTHENTICATION + RETURN-TO DESTINATION
============================================================

This is critical.

Email links will frequently be opened when the user is NOT logged in.

The application must preserve the requested destination through login.

Expected behavior:

User clicks:

https://<app>/contracts/ABC123

If authenticated:
→ immediately open ABC123.

If unauthenticated:
→ redirect to Login
→ authenticate
→ return to /contracts/ABC123

NOT:

email link
→ login
→ generic dashboard

Implement/reuse a safe returnTo/redirect mechanism.

Example concept:

/login?returnTo=%2Fcontracts%2FABC123

After successful login:

validate returnTo
→ navigate there

============================================================

//evil.example
javascript:...

The redirect target must remain inside the configured OnSpot application.
