# Fix Admin → Talent Application Status Notifications

You are working inside the existing **OnSpot Global** React + TypeScript + Express + PostgreSQL/Drizzle codebase.

## Problem

There is an existing Admin Job Applications feature.

Current behavior:

1. A Talent applies to an open job.
2. The application appears under **Admin → Job Applications**.
3. Admin changes the application status, for example:

   * Submitted
   * Under Review
   * Shortlisted
   * Interviewing
   * Offer Extended
   * Rejected
4. The status update is saved successfully.
5. On the Talent side, **My Applications** correctly shows the new application status.
6. However, the Talent's notification bell still shows:

   **"No notifications yet"**

The Talent should receive an in-app notification whenever an Admin changes their application status.

## Important: inspect the existing implementation before changing anything

Do not create a second notification system.

First inspect the existing notification architecture and reuse it.

Relevant existing files include:

* `client/src/components/NotificationBell.tsx`
* `client/src/hooks/useUnreadNotificationsCount.ts`
* `client/src/pages/AdminJobApplications.tsx`
* `server/storage.ts`
* `shared/schema.ts`
* the server route/service responsible for Admin Job Application status changes
* the existing Talent notification endpoints

The frontend already supports this notification type:

```ts
job_application_status_changed
```

`NotificationBell.tsx` already has UI configuration for it and sends the Talent to:

```txt
/my-applications
```

`useUnreadNotificationsCount.ts` already includes:

```ts
"job_application_status_changed"
```

for Talent notification counting.

Therefore, **do not redesign the notification bell unless you discover a genuine frontend bug.**

The primary objective is to make sure a persisted notification record is created for the correct Talent user when an Admin status change succeeds.

---

# Required behavior

When an Admin changes an application from one status to another, create a notification for the Talent linked to that application.

Example:

```txt
Under Review → Shortlisted
```

Talent notification:

```txt
Title:
Application Shortlisted

Message:
Your application for IT Administrator at OnSpot Technologies Inc. has been shortlisted.
```

The persisted notification should use:

```ts
type: "job_application_status_changed"
```

Recommended fields:

```ts
{
  userId: talentUserId,
  type: "job_application_status_changed",
  title: "...",
  message: "...",
  relatedId: applicationId,
  relatedType: "job_application",
  isRead: false
}
```

Use the actual existing InsertNotification/database structure rather than inventing incompatible fields.

---

# Critical requirement: resolve the correct user ID

Investigate how Job Applications relate to:

```txt
job application
    ↓
candidate
    ↓
linked Talent account
    ↓
users.id
```

The notification `userId` must be the canonical:

```txt
users.id
```

that the Talent notification endpoints query.

Do NOT blindly use:

* application ID
* candidate ID
* profile ID
* email address
* admin ID
* client ID

as the notification user ID.

This is especially important because the existing Talent notification endpoint resolves candidate accounts to their linked `users.id`.

Use the same account-linking rules that the existing Talent/My Applications implementation uses.

If the application already contains something such as:

```ts
talentId
candidateId
userId
```

verify what that ID actually represents before using it.

---

# Trigger location

Notification creation must happen on the **server**, in the same backend workflow that persists the status change.

Do NOT rely on the Admin React page to create the notification.

Desired sequence:

```txt
Admin selects status
        ↓
email is sent successfully if required by current workflow
        ↓
server updates application status
        ↓
server writes status history
        ↓
server creates Talent notification
        ↓
response returned to Admin frontend
```

Respect the current rule in Admin Job Applications that the applicant email must be successfully sent before certain status changes are saved.

Do not weaken or remove that behavior.

The notification should only represent a status change that actually succeeded.

# Do not create duplicate notifications

A notification should only be created when the status actually changes.

For example:

```txt
under_review → under_review
```

must NOT produce another notification.

Compare the previous status and new status before inserting.

Also ensure retries do not accidentally produce obvious duplicate notifications if the same request is submitted more than once.

If the existing API already prevents no-op status updates, reuse that protection.

---

# Unlinked applicants

Some applications may not yet be linked to an OnSpot Talent account.

If no canonical `users.id` can be found:

* do not fail the status update
* do not create an invalid notification
* log a useful server-side warning
* continue the existing email/status workflow

Example:

```ts
console.warn(
  "[job-application-status] Notification skipped: no linked talent user",
  { applicationId, candidateId, email }
);
```

Do not expose sensitive information unnecessarily.

# Transaction / failure handling

Do not leave the application status in a broken or inconsistent state because notification creation fails.

Follow the codebase's existing transaction/error-handling style.

Preferred behavior:

* status/history update remains authoritative
* attempt notification creation immediately afterward or within the same service workflow
* log notification failures clearly
* avoid returning a misleading success if the main status update itself failed

If the project already uses database transactions for this operation, integrate appropriately rather than introducing a conflicting transaction pattern.
