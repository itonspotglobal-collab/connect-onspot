# CHANGE 1 — Make “Finish Setting Up” the primary Talent Profile action

On the Talent Profile page, incomplete Talent profiles currently show a banner like:

```text id="j4a6cz"
Finish setting up your profile
Upload your resume and complete your information...
```

with a `Finish Setting Up` button.

The button is currently too visually secondary.

## Goal

When the Talent profile is incomplete, the first obvious action on the page should be:

```text id="fsuv42"
Finish Setting Up
```

## Requirements

Make the CTA more prominent without redesigning the whole profile.

Preferred behavior:

* place it in a highly visible location near the top of the Talent Profile;
* use the primary brand button styling;
* visually prioritize it over `Contact`, `Back to Pool`, tabs, and other secondary actions when the profile belongs to the logged-in Talent;
* keep the completion percentage visible;
* CTA should clearly communicate that completing the profile is the next action.

If practical, use text such as:

```text id="9x34se"
Complete Your Profile
50% complete
Finish Setting Up
```

The CTA should navigate to:

```text id="brxxq2"
/settings
```

or the correct Talent Profile Settings route.

Do not show this CTA for profiles that are actually 100% complete.

Use the shared persisted profile completion logic, not a separate hardcoded condition.

# CHANGE 2 — Resume parsing must populate Address / Location

The `Find Best Matches` flow parses uploaded CVs but currently fails to populate Address/Location even when the resume contains a valid address.

Inspect:

```text id="kwm9jl"
client/src/lib/resumeParser.ts
client/src/pages/FindBestMatches.tsx
```

and the relevant server-side resume parsing/extraction if any.

## Goal

If a CV contains an identifiable residential/current address or location, automatically populate the corresponding Address/Location input.

Examples that should be recognized:

```text id="eav451"
Cebu City, Philippines
Makati City, Metro Manila
Manila, Philippines
123 Example Street, Quezon City, Philippines
Davao City, Philippines
```

## Requirements

Extend the existing resume parser instead of creating a completely separate parser.

The parsed result should expose something explicit, for example:

```ts id="hqnk81"
{
  fullName,
  email,
  phone,
  address,
  ...
}
```

or:

```ts id="m25fvt"
location
```

depending on the existing data model.

Populate Find Best Matches with this parsed value.

Do not overwrite a value the user manually edited after parsing.

Use confidence/sanity checks so random resume text is not treated as an address.

Look for common resume labels such as:

```text id="0aez7y"
Address:
Location:
Current Address:
City:
Based in:
```

Also support common unlabelled city/country patterns where the parser already has sufficient confidence.

If no reliable address is found, leave the field blank.

Do not invent an address.

# CHANGE 3 — Standardize and validate every Phone Number field

Find every Talent-facing phone input across the application, especially:

* Profile Settings
* Talent signup / account creation
* Find Best Matches
* Job Application
* Onboarding
* any account/profile form that contains `Phone Number`

Create or reuse ONE shared phone validation utility/component.

Do not duplicate regex logic across pages.

## Goal

Phone numbers must be validated for the selected/inferred country.

A phone input must not be considered valid simply because it is non-empty.

Example:

For Philippines:

```text id="0d06dy"
Local mobile:
09123456789
```

contains 11 digits.

International equivalent:

```text id="gmeo2i"
+639123456789
```

must also be accepted.

A 10-digit PH mobile such as:

```text id="utizgy"
9123456789
```

must not be silently accepted as a complete local-format number unless it is explicitly normalized as an international number using the +63 country context.

## Implementation

Prefer using a proven phone-number parser/validator already installed in the project.

If none exists, add a lightweight standard library such as `libphonenumber-js` rather than maintaining country regexes manually.

Use functionality equivalent to:

```ts id="wu9n71"
parsePhoneNumberFromString
isValidPhoneNumber
```

Do not rely only on string length.

Normalize saved phone numbers consistently.

Preferred canonical DB format:

```text id="k5nwgb"
E.164
```

Example:

```text id="57ec9v"
+639123456789
```

Display formatting may be localized, but stored data should be normalized if this can be done without breaking existing records.

# Phone input UX

Phone validation should provide clear inline feedback.

Examples:

```text id="ww6apg"
Please enter a valid Philippine phone number.
```

```text id="6u0y0g"

```

```text id="24ocjl"

```

Do not wait until submission if validation can happen safely on blur/change.

Do not show an error while the user has only typed the first few digits; validate once there is sufficient input or on blur/submission.

# Profile Settings timezone ↔ phone country validation

This is specifically required.

The Profile Settings page contains both:

```text id="n4xedk"
Phone Number
Timezone
```

Add a consistency check.

Example:

```text id="ek2ifz"
Timezone: Asia/Manila
```

should normally correspond to:

```text id="xb389g"
Country calling code: +63
```

## Important

A timezone does not always uniquely determine a country.

Therefore do NOT create a globally rigid `timezone = exact phone prefix` rule for every timezone.

Instead:

1. build a mapping for unambiguous/common supported Talent timezones;
2. where the timezone clearly maps to a country, validate the phone country;
3. where a timezone spans multiple countries or is ambiguous, do not block the user based solely on timezone.

For current supported values, at minimum ensure:

```text id="p9c4q8"
Asia/Manila -> PH -> +63
```

If the selected timezone is `Asia/Manila` and the number resolves to a non-PH country, display an error and block Save until corrected.

Example message:

```text id="neua4l"
Your selected timezone is Philippines (Asia/Manila), but this phone number appears to use a different country code.
```

Do not automatically rewrite a valid international number without the user's knowledge.

# CHANGE 4 — Redesign Job Application flow around Talent Account first

This is the largest change.

Current application flow for new users is approximately:

```text id="1kmcg4"
Apply Now
→ Application Form
→ Account Creation
→ Submit
```

Change it to:

```text id="e5yv8j"
Apply Now
→ Account Creation / Sign In
→ Prefilled Application Review
→ Submit Application
```

For users who already have a Talent account:

```text id="1i5dxr"
Apply Now
→ Load Talent profile
→ Prefilled Application Review
→ Submit Application
```

The form should become primarily a **review/confirmation step**, not a duplicate data-entry process.

# A. Detect Talent session immediately

When a user clicks `Apply Now`, determine whether there is an active Candidate/Talent session using the existing Talent authentication system.

Use:

```text id="0sba2x"
talent_profile_token
loadTalentAuth()
candidateId
```

Do not use only legacy `AuthContext` / `onspot_jwt_token`.

## Logged-in Talent

If a valid Talent session exists:

1. resolve the Candidate using `candidateId`;
2. fetch fresh persisted Candidate profile data;
3. fetch persisted resume;
4. fetch persisted video introduction if present;
5. prefill the application;
6. open the review form directly.

Do not ask them to create an account again.

---

# B. New user / no Talent account

If no valid Talent account/session exists:

Clicking:

```text id="jmi1zr"
Apply Now
```

must first show:

```text id="g4qc5n"
Create Talent Account
```

with a secondary:

```text id="ly2knm"
Already have an account? Sign in
```

The user must establish Talent identity before the application form is generated.

After successful account creation/login:

1. create/fetch Candidate record;
2. prefill any known account/profile data;
3. proceed automatically to application review.

Do not discard the selected job during account creation.

Preserve:

```text id="h1llbs"
jobId
job slug
return URL
application context
```

throughout auth.

After auth success, return them to the same role they clicked Apply Now for.

# C. Prefill application from Talent profile

For logged-in Talent, prefill all available application fields from the canonical persisted Candidate profile.

At minimum:

```text id="wnppw0"
First Name
Last Name
Email Address
Phone Number
CV / Resume
Video Introduction
Cover Letter / Message
```

Also use job/application-specific data where relevant.

## Name

Use persisted separate:

```text id="kxn7ro"
firstName
lastName
```

Do not split `fullName`.

## Email

Use Candidate/Talent authenticated email.

Because this is identity data, consider making Email read-only on the application review form unless the product intentionally supports changing account email there.

## Phone

Use the canonical validated Candidate phone.

Run the same shared phone validator.

## Resume

If the Talent already has a valid current resume:

* show the filename/current uploaded document;
* do not force them to upload it again;
* allow `Replace` if desired.

If no resume exists and resume is required for the job:

* clearly highlight it as missing;
* require upload before submit.

## Video Introduction

This is situational.

Determine whether the job requires a video introduction.

If the job does NOT require one:

* do not block submission when missing;
* if Candidate already has one, it can still be displayed/attached if appropriate.

If the job DOES require one:

* use the Candidate's existing video introduction if available;
* otherwise require upload.

Do not mark every job's video introduction required globally.

## Cover Letter

If there is previously saved/general cover-letter content suitable for reuse, prefill it.

Otherwise leave it editable.

Cover letter should remain application-specific and editable.

# Acceptance criteria

## Talent Profile CTA

* [ ] Incomplete profiles have a visually dominant `Finish Setting Up` CTA.
* [ ] CTA goes to Profile Settings.
* [ ] Complete profiles do not show the incomplete CTA.

## Resume Address Parsing

* [ ] Address/location is parsed from a CV when reliably present.
* [ ] Find Best Matches auto-populates it.
* [ ] User manual edits are not overwritten.
* [ ] Parser does not invent addresses.

## Phone Validation

* [ ] Shared phone validation is used everywhere.
* [ ] PH 10-digit incomplete numbers are rejected.
* [ ] PH 11-digit local mobile works.
* [ ] +63 format works.
* [ ] Data is normalized consistently.
* [ ] Profile Settings detects clear timezone/phone country mismatch.
* [ ] Backend validation protects persisted data too.

## Job Application

* [ ] Existing Talent -> Apply Now -> prefilled review form.
* [ ] Existing Talent does not create another account.
* [ ] New Talent -> Apply Now -> Create Account first.
* [ ] After account creation -> prefilled review form.
* [ ] Existing Talent email during signup redirects to Sign In instead of duplicate account.
* [ ] Name, email, phone, resume are prefilled from Candidate data.
* [ ] Video requirement is job-specific.
* [ ] Cover Letter remains application-specific/editable.
* [ ] Mismatches are detected before submit.
* [ ] Authenticated Candidate owns the application.
* [ ] Job context survives login/signup.
* [ ] Database records are verified.
