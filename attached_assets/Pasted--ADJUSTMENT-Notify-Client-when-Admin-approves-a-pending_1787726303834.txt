# Required workflow

The expected job approval lifecycle is:

```text
Client submits job
        ↓
approval status = pending
        ↓
Admin reviews job
        ↓
Admin clicks Approve
        ↓
approval status changes pending → approved
        ↓
create notification for the Client who owns the job
        ↓
Client notification bell/unread count updates
```

The notification must be created on the BACKEND when the Admin approval succeeds.

Do NOT have the Admin frontend separately call a notification endpoint.

Do NOT have the Client frontend infer that a job was approved and generate its own notification.

The backend approval action is the authoritative event.

---

# Notification recipient

The notification must go to the Client/user that owns the approved job.

Do not send it to:

```text
the approving Admin
all Clients
the talent
an unrelated organization member
```

Resolve the owner using the existing job/client/user relationship in the database.

For example:

```text
job
→ client_id / clientId
→ corresponding Client user
→ notification.user_id
```

Use the actual schema relationships in this project.

Do not guess field mappings.

# Trigger only on an actual approval transition

This is important.

Create the notification ONLY when the job transitions:

```text
pending → approved
```

Do not create another notification when:

```text
approved → approved
```

Do not create duplicates when:

* the Admin reloads the page
* React Query retries
* the job is edited after approval
* an already-approved job is saved again

Example logic:

```ts
const previousApprovalStatus = job.approvalStatus;

updateJob(...);

if (
  previousApprovalStatus !== "approved" &&
  newApprovalStatus === "approved"
) {
  create client notification;
}
```

Prefer an atomic/backend-safe implementation based on the actual database update flow.

---

# If Admin unapproves and approves again

Inspect the intended existing behavior.

Recommended behavior:

If Admin explicitly performs:

```text
Approved → Pending → Approved
```

again, it is reasonable to send a new approval notification because this is a real new approval event.

However:

```text
Approved → save/edit while Approved
```

must NOT create a new notification.

---

# Preserve current job approval behavior

Do NOT alter these existing states:

```text
pending
approved
rejected
linked_to_existing
```

Do not auto-approve Client-created jobs.

Do not change public visibility rules.

The notification must happen AFTER a successful Admin approval, not instead of approval.

Expected result:

```text
Before Admin approval:
Client job = Pending Approval
Public job = hidden
No approval notification

After Admin approval:
Client job = Approved
Public job = visible
Client gets approval notification
```

# Notification and email are separate

For this adjustment, the required feature is the IN-APP notification.

Do not automatically add an email unless the existing job-approval workflow already specifies one.

The required behavior is:

```text
Admin approves Client job
→ Client receives in-app notification
```

If an approval email already exists, preserve it.

Do not remove or duplicate it.

---

# Failure handling

The approval operation should remain reliable.

Preferred behavior:

```text
1. Admin approves job
2. DB approval update succeeds
3. Notification record is created
```

Use the existing project's transaction/service conventions.

Do not return "Approval failed" if the job actually became approved but only a non-critical notification side effect failed, unless the existing architecture treats both operations transactionally.

At minimum, log notification creation failures clearly.

Example:

```text
[JobApproval] Job <id> approved by admin
[JobApprovalNotification] Created notification for client <id>
```

Failure:

```text
[JobApprovalNotification] Failed for job <id>: <safe error>
```

Do not log secrets or auth tokens.
