We need to add a working Forgot Password feature for development/testing accounts.

Context:
We currently have login/signup portal work in progress. Authentication is not fully ready for production yet, but we already have account records and password_hash fields in the database from earlier login/signup work.

Problem:
When we forget the password of a testing account, we currently delete the database record just to reuse the email. This is inconvenient.

Goal:
Implement a convenient Forgot Password / Reset Password flow for testing accounts.

Important:
This should be development-friendly for now.
Do NOT implement a full production email delivery system yet unless one already exists.
Do NOT delete existing auth code.
Do NOT break current login/signup flow.
Clearly mark temporary development-only behavior with comments.

Suggested approach:
Add a simple forgot-password flow that allows resetting the password by email.

Frontend requirements:

1. Access from Sign In form
- In the Sign In step/modal, add a “Forgot password?” link or button.
- Clicking it should switch the modal to a Forgot Password step.

2. Forgot Password step
Show:
- Title: “Reset Password”
- Description: “Enter the email used for your account.”
- Email input
- New Password input
- Confirm New Password input
- Button: “Reset Password”
- Back to Sign In button

3. Validation
- Email is required and must look valid.
- New password is required.
- Confirm password must match.
- Password should follow the same validation rules already used in auth-utils if possible.
- Show clear toast/error messages.

Backend requirements:

1. Add a development reset password endpoint
Add an endpoint like:

POST /api/dev/reset-password

Request body:
{
  "email": "user@example.com",
  "newPassword": "newpassword123"
}

Behavior:
- Find the user by email in the users table.
- If user does not exist, return 404 with a clear message.
- Hash the new password using the existing hashPassword function from server/auth-utils.
- Update users.password_hash for that email.
- Update users.updated_at.
- Return success response.

Example response:
{
  "success": true,
  "message": "Password reset successfully. You can now sign in with your new password."
}

2. Development-only safety
This endpoint should be clearly marked as dev-only:
- Add comment:
  // DEV ONLY: temporary password reset endpoint for testing accounts
- If possible, only enable it when NODE_ENV !== "production" or when an env flag is enabled, for example:
  ENABLE_DEV_PASSWORD_RESET=true

Recommended condition:
Allow the route only if:
- process.env.NODE_ENV !== "production"
OR
- process.env.ENABLE_DEV_PASSWORD_RESET === "true"

If not enabled, return 403:
{
  "success": false,
  "message": "Password reset is disabled in this environment."
}

3. Do not send emails yet
Do not implement email sending for now.
Do not create reset tokens yet unless necessary.
This is only for dev/testing convenience.

4. Security note
Add a clear code comment saying this should be replaced before production with:
- one-time reset token
- email verification
- token expiration
- rate limiting
- no user enumeration

5. Reuse existing utilities
Inspect and reuse:
- server/auth-utils.ts
- server/routes.ts
- shared/schema.ts
- client/src/components/LoginDialog.tsx
- client/src/components/TopNavigation.tsx
- client/src/lib/api.ts
- client/src/hooks/use-toast.ts

Frontend API call:
- Add a function in client/src/lib/api.ts if appropriate:
  devResetPassword(email, newPassword)
- It should POST to /api/dev/reset-password.

6. Integrate with current portal modal
If the current login/sign-up flow is inside the Access Portal popup, keep the same futuristic popup shell.
Do not create a plain white modal.
Forgot Password should appear as another step inside the same modal/popup.

7. Expected UX flow
Access Portal → Sign In → Forgot password? → Reset Password form → Reset Password button → success toast → return to Sign In.

8. Acceptance criteria
- Forgot password link appears in the Sign In form.
- User can enter email and new password.
- Password confirmation is validated.
- Backend updates the password_hash for the matching users.email.
- User can sign in afterward using the new password.
- No database record deletion is needed.
- Endpoint is disabled in production unless explicitly enabled.
- Existing auth code remains intact.
- UI remains consistent with the existing Access Portal popup design.
