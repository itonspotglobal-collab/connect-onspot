NON-REGRESSION IS THE HIGHEST PRIORITY.

We want a Talent-facing popup notification whenever the Talent becomes officially Hired.

The Hired state may currently be reached through:

1. Contract workflow
2. Application/status workflow
3. Any existing centralized hiring transition

Regardless of which valid path causes the hire, the Talent should receive ONE clear popup notification.

Do not create duplicate popups if multiple connected workflows update during the same hire.

# GOAL

When a Talent becomes officially Hired:

→ preserve the existing Hired state transition
→ preserve existing application history
→ preserve contract behavior
→ preserve existing notifications/emails
→ create/reuse the Talent Hired notification
→ show a congratulatory popup to the Talent

Suggested popup:

Title:

`Congratulations — you're hired!`

Message:

`You've been hired for {{job_title}} with {{company_name}}.`

Secondary message:

`You can review your application, contract, and next steps in OnSpot.`

Primary action:

`View Details`

Secondary:

`Close`

# IMPORTANT — ONE CANONICAL HIRE EVENT

Do NOT independently create a popup in:

- contract-signing code
- Admin status code
- offer code

if they may all represent the same final hiring event.

Use the canonical transition into:

`hired`

as the source of truth.

Conceptually:

previous application status != hired
→ application transitions to hired
→ create Hired event
→ Talent notification
→ Talent popup

If the contract workflow causes the application to become hired, use the same event.

If an Admin/status workflow causes it to become hired, use the same event.

Do not create another popup if the application is already hired.

# DUPLICATE PREVENTION

This is critical.

Possible bad flow:

Contract signed
→ Hired notification

Then application status updater also runs:
→ Hired notification again

Result:
two popups

Do NOT allow that.

Use the existing notification event-key/idempotency system.

Suggested conceptual event key:

`talent-hired:{submissionId}`

or the existing canonical equivalent.

One submission may produce only one final Hired notification event.

Repeated API calls, retries, page refreshes, or contract hooks must not create another one.

# EXISTING HIRE NOTIFICATION

Before adding a new notification record, check whether the existing notification system already creates something like:

- `hired`
- `application_hired`
- `talent_hired`
- `welcome_to_team`

If one already exists, REUSE IT.

Do not create a duplicate notification type merely for the popup.

The popup should preferably be driven from the same canonical Hired notification.

# POPUP BEHAVIOR

When Talent is logged in and the Hired event arrives:

show the popup.

If Talent was offline when hired:

on their next login/session, if the Hired notification has not yet been presented as a popup, show it once.

Do not require the Talent to be online at the exact moment the Admin/Client changes the status.

# DO NOT SHOW POPUP ON EVERY REFRESH

The popup must not repeatedly appear on:

- page reload
- query refetch
- navigating between pages
- opening Notifications
- login every time

Track popup presentation safely.

Preferred:

use the notification/event record plus an existing acknowledgement/read/presented mechanism if available.

If notification `read` state is the only existing persistence mechanism, do not abuse it if opening the popup would incorrectly mark the bell notification read before the user interacts with it.

If necessary, add a minimal additive `popupPresented`/event acknowledgement mechanism, but only if no existing mechanism can support one-time display.

Do not use localStorage as the sole source of truth for critical cross-device behavior unless the existing notification architecture already uses it.
