# TASK — Implement Organization-Aware Timesheets for Hired Talent

Extend the existing OnSpot Timesheet system so that Timesheets are available specifically to **Talent who have actually been hired by a Client and are part of that Client/organization engagement**, and so the corresponding Client can securely view the Timesheets for their hired Talent.

This is an **extension of the existing Timesheet, Clock, Hiring Contract, Client Team, and Organization functionality**.

DO NOT create a second or parallel timesheet system.

DO NOT replace existing working Timesheet functionality.

The implementation must reuse and safely extend the current application architecture.

---

# PRIMARY PRODUCT REQUIREMENT

Timesheets should become available to Talent only when that Talent has been successfully hired through the Client hiring workflow.

Conceptually:

Client hires Talent
→ valid signed hiring contract exists
→ Talent becomes part of the Client's active hired workforce / organization context
→ Talent gains access to Timesheets
→ Talent records work through the existing Clock system where applicable
→ existing Timesheet periods are generated
→ Talent can review/submit their Timesheet
→ Client can view the Timesheet for that hired Talent
→ existing Admin review / billing workflow continues unchanged

A Talent account that has NOT been hired must NOT gain access to functional Timesheets merely because they have a Talent account.

# SOURCE OF HIRE ELIGIBILITY

A Talent should be considered eligible for Timesheets only when there is a legitimate completed Client hiring relationship.

Use the existing canonical hiring state.

The current modern flow already uses `hiring_contracts`, and Timesheets currently load contracts whose status is effectively active/signed.

Verify the actual hiring lifecycle and preserve it.

A Talent MUST NOT receive Timesheet access based only on:

- being registered as Talent
- applying for a job
- being shortlisted
- receiving an invitation
- receiving an interview
- receiving an offer
- accepting an offer without a completed hiring contract
- being manually associated with an organization without a valid hire

The canonical eligibility should be tied to the successfully signed/countersigned hiring contract or whatever exact existing state represents a completed hire.

Do not create a new duplicate `isHired` flag if the hiring contract already provides the canonical state.

# ORGANIZATION INTEGRATION

Timesheets must work correctly for Clients operating inside an Organization.

The system already has:

- `organizations`
- `organization_members`

Do not confuse Client organization membership with hired Talent employment/engagement.

First determine how the existing system currently associates a hired Talent with:

1. the Client who hired them;
2. the Client's organization/workspace;
3. the hiring contract;
4. the job/submission.

If the organization relationship can already be derived reliably from the Client/hiring/job relationship, reuse it.

If an explicit organization reference on the hiring relationship is required, make the smallest safe schema change necessary.

Do NOT simply insert hired Talent into `organization_members` unless that table is genuinely intended to contain Talent workforce members.

`organization_members` currently represents organization/workspace users such as owners/members. Preserve that semantic unless the existing architecture clearly establishes otherwise.

Prefer distinguishing:

Organization account members
vs.
Organization's hired Talent/workforce

if they are separate concepts.

# DO NOT DOUBLE COUNT HOURS

`clock_session`
→ `timesheet revision`

or:

clock sessions + invoice hours

or:

multiple Timesheet revisions

Reuse the existing serializer's effective/current Timesheet representation.
