When Client opens Application Details and changes an applicant's status, the frontend now receives:

`500 Internal Server Error`

The actual PostgreSQL error shown in the UI/console is:

```text
FOR UPDATE cannot be applied to the nullable side of an outer join
```

This started after the recent application status / notification workflow changes.

The status update currently fails completely.

# ROOT CAUSE

The new backend flow likely runs a query conceptually similar to:

```sql
SELECT ...
FROM job_submissions js
LEFT JOIN jobs j ...
LEFT JOIN candidates c ...
LEFT JOIN users u ...
WHERE js.id = $1
FOR UPDATE;
```

PostgreSQL rejects this because `FOR UPDATE` is being applied across an outer join where one or more joined tables are nullable.

The canonical row that needs locking is:

`job_submissions`

not every optionally joined relation.

---

# REQUIRED FIX

Refactor the transaction so the application/submission row is locked independently.

Preferred pattern:

```sql
BEGIN;

SELECT *
FROM job_submissions
WHERE id = $1
FOR UPDATE;
```

Then fetch related records separately:

```sql
SELECT ...
FROM jobs
...
```

or:

```sql
SELECT ...
FROM candidates/users
...
```

without trying to lock nullable outer-join rows.

Then:

* verify authorization
* validate transition
* update application
* write status history
* create notifications

COMMIT.

---

# ALTERNATIVE SAFE POSTGRESQL FORM

If the existing query genuinely needs joins while locking, use PostgreSQL's table-specific locking syntax where appropriate:

```sql
FOR UPDATE OF js
```

where `js` is the non-nullable `job_submissions` base table.

But only use this if the ORM/query builder supports it correctly and it is clear that only the application row needs locking.

Preferred solution is still:

**lock the base row first, fetch relations second.**

---

# DO NOT REMOVE LOCKING

Do not “fix” this by simply deleting:

`FOR UPDATE`

The lock was likely added to prevent status race conditions.

Preserve the requirement that concurrent actions cannot blindly overwrite each other.

Example:

Client changes:

`New → Reviewed`

at the same time Admin changes:

`New → Shortlisted`

The backend should serialize or reject conflicting transitions rather than silently clobbering one.

# TRANSACTION STRUCTURE

Preferred conceptual flow:

```ts
await db.transaction(async (tx) => {
  // 1. Lock only canonical application row
  const application = await getSubmissionForUpdate(tx, applicationId);

  if (!application) {
    throw notFound();
  }

  // 2. Fetch related Job separately
  const job = await getJob(tx, application.jobId);

  // 3. Authorize Client
  assertClientOwnsJob(job, authenticatedUserId);

  // 4. Validate transition
  validateApplicationTransition(
    application.status,
    requestedStatus
  );

  // 5. Fetch Talent/user information separately
  const talentRecipient = await resolveApplicationTalent(...);

  // 6. Update canonical row
  await updateSubmissionStatus(...);

  // 7. History
  await createStatusHistory(...);

  // 8. Talent notification
  if (talentRecipient) {
    await createNotification(...);
  }

  // 9. Admin notification(s)
  await createAdminStatusNotification(...);
});
```

Adapt this to existing storage/query abstractions.

# DRIZZLE / ORM NOTE

If using Drizzle:

avoid applying `.for("update")` to a query that contains nullable `leftJoin(...)` relations unless explicitly locking only the base table is supported.

A safer implementation is two queries inside the same transaction.

Do not convert optional LEFT JOINs into INNER JOINs merely to satisfy `FOR UPDATE`, because that can break valid legacy/unlinked applications.
