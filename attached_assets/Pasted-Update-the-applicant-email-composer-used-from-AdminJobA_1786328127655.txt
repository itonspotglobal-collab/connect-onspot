5. Send selected sender to backend

When calling the existing send-email endpoint, include a sender identifier, preferably:

{
  "senderEmail": "findwork@onspotglobal.com",
  "subject": "...",
  "body": "..."
}

However, do not allow the backend to blindly trust arbitrary sender addresses from the frontend.

The backend must validate senderEmail against an allowlist containing only:

careers@onspotglobal.com
findwork@onspotglobal.com
hiretalent@onspotglobal.com

Reject any other sender value.

6. Backend sender configuration

Keep sender mailbox configuration server-side.

Use environment/configuration values such as:

APPLICATION_EMAIL_CAREERS=careers@onspotglobal.com
APPLICATION_EMAIL_FIND_WORK=findwork@onspotglobal.com
APPLICATION_EMAIL_HIRE_TALENT=hiretalent@onspotglobal.com

If the project already has a better email configuration pattern, follow that instead.

Do not expose Microsoft Graph credentials to the frontend.

The frontend may know the three allowed email addresses, but:

MICROSOFT_TENANT_ID
MICROSOFT_CLIENT_ID
MICROSOFT_CLIENT_SECRET

must remain backend-only.

7. Microsoft Graph behavior

Use the existing Microsoft Graph integration.

The selected sender should determine which mailbox endpoint is used for sending.

Conceptually:

POST /users/{selectedSender}/sendMail

Do not create separate Graph applications for each sender unless technically required.

Before changing authentication architecture, first verify whether the existing Entra application with Mail.Send Application permission can send from all three mailboxes.

unless the existing backend has a specific reason to use a different Reply-To.
