# IMPLEMENT SIGNUP EMAIL VERIFICATION — CLIENT + TALENT

Implement the approved signup email-ownership verification architecture from the completed audit.

The objective is a production-ready signup system where new Client and Talent users cannot receive usable application credentials until they prove access to their email inbox.

This is an approved feature implementation.

Do NOT publish automatically.

Do NOT use production customer data for testing.

Do NOT send real verification emails until explicitly performing approved UAT.

Do NOT broaden this into a general authentication/security rewrite.

---

# APPROVED PRODUCT DECISIONS

## New accounts

New Client/Talent identities must prove email ownership before receiving usable application credentials.

This applies to normal new signup and other new-account/first-credential paths identified by the audit.

Do not silently exempt provider/Admin/import-created identities unless trustworthy verified-email evidence is explicitly established and validated by the application.

For the current MVP, use the OnSpot email-verification flow.

## Existing accounts

Grandfather established historical authenticated users.

Do NOT:

- lock existing established users out;
- revoke existing sessions merely because this feature launches;
- falsely populate `email_verified_at` for historical users who never completed inbox verification.

Historical established accounts may have an explicit grandfathered exemption.

Passwordless/unclaimed imported Talent identities must prove inbox ownership before establishing credentials for the first time.

# CORE ARCHITECTURE

Implement:

```text
Signup details
→ validate
→ create pending registration
→ generate verification OTP
→ send verification email
→ user enters OTP
→ server verifies OTP
→ atomic account activation
→ create role records
→ record verified email
→ consume challenge
→ COMMIT
→ issue authentication token(s)
→ continue onboarding
```

No usable Client/Talent account credential may be issued before successful verification for new identities covered by this policy.

# 2 — EMAIL OWNERSHIP STATE

Implement distinct email-ownership state.

At minimum support the concepts:

- verified timestamp;
- exact normalized verified email;
- whether verification is required versus historical/grandfathered access.

IMPORTANT:

Establish ONE authoritative ownership source for a normal user-linked identity.

For a normal Talent that has a `users` identity plus candidate/profile records:

`users`

should be the canonical source of email ownership unless the existing schema makes this demonstrably unsafe.

Do NOT duplicate mutable verification state across `users` and `candidates` in a way that can disagree.

Candidate-only ownership state may exist only where a legitimate authentication identity has no linked `users` record.

Document the invariant in code/tests.

Verification of email ownership must NOT grant Talent professional:

- Verified;
- Vetted;
- identity-review;

status.

Those concepts remain separate.

---

# 3 — OTP GENERATION

Generate a six-digit numeric code using cryptographically secure randomness.

Preserve leading zeros.

Example:

`004271`

Never use `Math.random()`.

Store only an HMAC representation using the dedicated verification secret.

Bind the HMAC to sufficient context to prevent substitution, including:

- registration ID;
- normalized email;
- role;
- purpose;
- generation;
- code.

Recommended algorithm:

HMAC-SHA-256.

Never put plaintext OTPs in:

- database logs;
- request logs;
- console logs;
- analytics;
- error messages;
- email delivery ledger bodies;
- tracing.

---

# 4 — EXPIRY AND ABUSE CONTROLS

Implement the audited defaults unless an existing repository convention provides a stronger compatible setting:

- OTP expiry: 10 minutes.
- Pending registration lifetime: 24 hours.
- Incorrect attempts: maximum 5 per code generation.
- Resend cooldown: 60 seconds.
- Start/send/resend normalized-email budget: 5/hour and 10/day.
- Existing signup IP budget: preserve 10/hour where currently configured.
- Additional resend IP budget: 20/hour.
- Verification IP budget: 50 attempts/15 minutes.
- Verification email budget: 20 attempts/hour across generations.

Rate limiting that must work across production instances should use persistent/shared state rather than relying exclusively on process-local memory.

Use existing infrastructure where appropriate rather than inventing unnecessary parallel systems.

Ensure counters/resend reservations/consumption are concurrency-safe.

# 5 — START SIGNUP

Modify the canonical:

`POST /api/signup`

behavior.

For a new normal registration it must NO LONGER:

- immediately create the usable user;
- immediately create usable role credentials;
- immediately issue the user JWT;
- immediately issue the candidate JWT.

Instead:

1. Normalize and validate signup information.
2. Validate Client/Talent role.
3. Apply password requirements.
4. Handle duplicate-account behavior without unsafe enumeration.
5. Store pending registration.
6. Generate OTP.
7. Select server-controlled sender from role.
8. Attempt Graph delivery.
9. Record honest delivery state.
10. Return pending verification information.

Successful start should conceptually return:

`202 Accepted`

with only safe information such as:

- challenge identifier;
- masked destination;
- expiration timing;
- resend timing.

Do not return OTP/HMAC/password hash.

Do not claim account creation.

# 6 — GRAPH VERIFICATION EMAIL

Reuse:

`server/services/microsoftGraphEmailService.ts`

where safe.

Create a dedicated verification-email wrapper/template.

The wrapper MUST inspect the existing `{ success, error }` result.

Do not interpret a swallowed/caught Graph error as successful delivery.

Use appropriate OnSpot branding.

The email should clearly contain:

- six-digit verification code;
- short expiration statement;
- notice that the code should not be shared;
- context indicating Client or Talent signup where appropriate.

Do not put passwords or unnecessary personal information in the email.

Graph acceptance means only accepted for sending.

It does NOT mean:

- delivered;
- inbox received;
- email ownership verified.

Only successful OTP submission establishes ownership.

# 7 — VERIFY ENDPOINT

Implement an endpoint equivalent to:

`POST /api/signup/verify`

Request should contain only the required challenge/code information.

Email and role must come from trusted pending-registration state—not browser claims.

Verify:

- pending capability;
- challenge exists;
- correct purpose;
- not expired;
- not superseded;
- not consumed;
- attempts remain;
- HMAC matches;
- bound email/role/generation match.

Incorrect attempts must increment atomically.

Do not expose whether a guessed code was “close.”

---

# 8 — ATOMIC ACCOUNT ACTIVATION

Successful OTP verification must activate the account transactionally.

Within ONE transaction:

1. Lock/validate pending registration.
2. Recheck email/username/account conflicts.
3. Create the real `users` record.
4. Create required role-specific records.
5. For Client, create required Client profile state.
6. For Talent, create/link required profile and candidate state.
7. Record ownership of the exact normalized email.
8. Consume the verification challenge.
9. Commit.

If any required activation write fails:

ROLL BACK THE ENTIRE ACTIVATION.

Do not preserve the existing normal-Talent behavior where candidate creation may fail while signup still reports success.

Issue JWT/session/candidate credentials only AFTER successful commit.

---

# 9 — RESEND

Implement an endpoint equivalent to:

`POST /api/signup/resend`

Requirements:

- pending capability required;
- server obtains email/role from pending registration;
- enforce cooldown;
- enforce shared budgets;
- create a new generation;
- invalidate/supersede old code;
- generate new secure OTP;
- send from correct role sender;
- record honest send state.

After successful resend:

OLD CODE MUST FAIL.

# 10 — STATUS / REFRESH RECOVERY

It must NOT expose:

# 11 — CHANGE EMAIL

If the user changes their signup email:

- invalidate/supersede the old challenge;
- normalize and validate the new email;
- create a new bound challenge;
- require verification of the new address.

Verification for email A can never activate registration for email B.
