# CRITICAL SAFETY RULE

Prefer a safe staging/development deployment using test accounts and test data.

Do NOT:

- terminate real customer contracts;
- modify real financial records;
- generate real payouts;
- alter real invoices;
- upload test files into customer accounts;
- send test emails to arbitrary real users;
- bypass authentication;
- disable authorization;
- use development-login bypasses as evidence of production authentication;
- fabricate screenshots or verification;
- treat configuration presence as runtime proof.

If safe prerequisites are unavailable, report the affected check as:

`BLOCKED`

Do not manufacture a PASS.

# RELEASE BLOCKERS

Treat any of the following as a release blocker:

### BLOCKER

- production build fails;
- application cannot start safely;
- authentication is broken;
- authorization regression exposes another user's data;
- uploaded files cannot be persisted/retrieved;
- fake LinkedIn data can still be written;
- fake assessment result still appears;
- contract-ending operation corrupts or misattributes data;
- Team Dashboard materially double-counts modern work;
- critical navigation leads to broken application state.

### HIGH

Report separately for review before publishing:

- required transactional email cannot be delivered;
- major Client/Talent workflow cannot complete;
- persistence works only optimistically until reload;
- major role workflow is inaccessible.

Do not automatically decide to publish around a BLOCKER/HIGH finding.
