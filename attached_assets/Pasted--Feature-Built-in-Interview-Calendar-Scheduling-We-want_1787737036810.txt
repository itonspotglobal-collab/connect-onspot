## Feature: Built-in Interview Calendar & Scheduling

We want to simplify interview scheduling and keep it completely inside the existing OnSpot platform.

Do **NOT** add Calendly, Google Calendar, Microsoft Calendar, or another third-party scheduling provider as a required dependency.

The system already has an interview/invitation workflow, interview timezone handling, notifications, emails, hiring pipeline statuses, and client/talent views.

### FIRST: AUDIT THE EXISTING IMPLEMENTATION

Before changing anything, inspect the current codebase and identify:

1. Existing `interviews` table and its fields.
2. Existing `interview_proposals` table and negotiation logic.
3. Existing `/api/client/invitations` flow.
4. Existing Client interview scheduling UI.
5. Existing Talent accept / decline / counter-propose UI.
6. Existing Admin interview-related functionality.
7. Existing timezone utilities:

   * `server/lib/interviewTime.ts`
   * `client/src/lib/formatInterviewTime.ts`
8. Existing notification infrastructure.
9. Existing email notification/template infrastructure.
10. Existing hiring pipeline/status transitions associated with interviews.

**Do not create duplicate interview or scheduling tables if the existing tables can support this feature.**

Extend/refactor the current interview system instead.

---

# GOAL

Create a simple built-in interview scheduling/calendar experience for:

* Admin
* Client
* Talent/Candidate

The platform itself should be the source of truth for interview schedules.

The basic experience should feel like a lightweight internal Calendly, but only for interviews within OnSpot.

---

# CORE SCHEDULING FLOW

## Option A — Client/Admin proposes a date and time

Admin or Client can open an interview scheduling dialog and choose:

* Date
* Start time
* Optional duration
* Timezone
* Interview type/round if applicable
* Optional meeting link
* Optional notes

Example:

**August 28, 2026**
**10:00 AM – 10:30 AM**
**Asia/Manila**

The Talent then receives the interview request.

Talent can:

* Accept
* Decline
* Propose another time

---

## Option B — Client prefers their own date/time

The Client should NOT be forced to choose from predefined availability slots.

Include an option such as:

**Choose another date & time**

or

**Pick my own time**

This opens the same date/time picker and allows the Client to manually propose any valid future date/time.

This is important because some Clients may already know exactly when they want the interview.

---

# BUILT-IN CALENDAR VIEW

Create a simple calendar/schedule page using the existing interview records.

Do not create another independent calendar-event database unless there is a genuine data-model requirement that cannot be represented by the interview tables.

Suggested routes:

### Admin

`/admin/interviews`

or integrate it into the existing Admin hiring pipeline.

### Client

`/client/interviews`

or integrate it into the existing Client dashboard/profile hiring area.

The page should support:

### Calendar views

* Upcoming
* Calendar

For the first version, a simple:

* Month view

is enough.

Do NOT over-engineer this into a full Google Calendar clone.

[Join Interview]

---

# IMPORTANT: TIMEZONE HANDLING

The repo already contains interview timezone normalization and timezone-aware interview storage.

Reuse it.

Do NOT regress to naive timestamps.

Store the actual scheduled instant consistently in UTC/timestamptz and preserve the agreed/source timezone where the current schema supports it.

On display, show interview times in the logged-in user's local timezone.

Examples:

Client in New York:

**August 27 · 10:00 PM EDT**

Talent in Manila:

**August 28 · 10:00 AM PHT**

Both must refer to the exact same instant.

Never display a bare date/time without a timezone indicator.

Use the existing interview time formatting helpers where possible rather than creating separate conflicting timezone logic.

---

# RESCHEDULING

Admin, Client, or Talent should be able to initiate rescheduling where permissions allow.

Rescheduling should reuse the existing interview proposal/counter-proposal mechanism instead of creating another scheduling workflow.

Example:

Client selects:

**Reschedule**

Then chooses:

August 29
2:00 PM

The other party sees:

**New interview time proposed**

and can:

* Accept
* Decline
* Suggest another time

Do not create a new interview round just because the same interview is being rescheduled.

A new round is only for an actual second-stage interview such as:

* Initial interview
* Technical interview
* Final interview

---

# DOUBLE-BOOKING PROTECTION

Before confirming an interview time, check the platform's existing confirmed interviews.

Prevent obvious conflicts for the participants.

At minimum check:

### Client/Admin interviewer

Do they already have a confirmed interview overlapping this time?

### Talent

Do they already have another confirmed interview overlapping this time?

If there is a conflict:

Do not silently save it.

Show:

**This time conflicts with another scheduled interview.**

Then allow the user to choose another time.

Use confirmed interview records as the source of truth.

---

# OPTIONAL AVAILABILITY

Keep this simple.

Do not build a complicated recurring availability engine unless one already exists and can be reused safely.

For V1:

Client/Admin can simply choose a date/time directly.

Talent can accept it or counter-propose another date/time.

Later, availability windows can be added.

The current goal is scheduling interviews, not recreating Calendly.

# CALENDAR COMPONENT

Prefer an existing calendar/date library already installed in the project.

Audit `package.json` before adding dependencies.

If the project already has suitable calendar/date components, use them.

---

# DATABASE

Do not immediately add a new `calendar_events` table.

First determine whether:

* `interviews`
* `interview_proposals`
* existing interview fields

already contain everything required.

Only propose a migration for genuinely missing fields, for example if absent:

* duration
* meeting URL
* cancelledAt
* cancellationReason

If changes are necessary:

1. Report the current schema.
2. Explain exactly why each new field is required.
3. Keep the migration backward compatible.
4. Preserve existing interview records.

---

# SECURITY / AUTHORIZATION

Enforce server-side authorization.

A Client may only schedule/manage interviews associated with their own jobs/applications.

Talent may only respond to interviews belonging to their own submission/invitation.

Admin may manage all interviews.

Never rely on frontend filtering for authorization.

---

# API DESIGN

Reuse existing interview APIs wherever possible.

Do not duplicate endpoints if the existing invitation/interview negotiation routes already perform the operation.

If additional endpoints are genuinely required, keep them RESTful and scoped appropriately.

Examples only:

`GET /api/client/interviews`

`GET /api/admin/interviews`

`GET /api/talent/interviews`

`PATCH /api/interviews/:id/reschedule`

`PATCH /api/interviews/:id/cancel`

But audit existing routes first and extend them instead when practical.

---

# EDGE CASES

Handle:

* Past dates cannot be proposed.
* Invalid timezone.
* Invalid meeting URL.
* Double booking.
* Cancelled job.
* Withdrawn/rejected talent.
* Application belonging to another Client.
* Interview already cancelled.
* Two users responding to the same proposal at nearly the same time.
* Rescheduling after confirmation.
* Email failure must NOT roll back an otherwise valid interview schedule.

Persist the interview first.

Treat notifications/email as side effects.
