# Update Talent Job Application Flow — Allow Editing Pre-Filled Details

You are working inside the existing **OnSpot Global / connect-onspot** codebase.

Update the existing logged-in Talent job application flow so that information pre-filled from the Talent account/profile remains convenient, but the Talent can **edit the application details before submitting the job application**.

Use the screenshot supplied with this request as the UI reference.

The current page is implemented in:

`client/src/pages/JobApplyPage.tsx`

Before changing anything, inspect the current implementation and preserve the existing:

* job application flow
* Talent authentication
* account/application linking
* CV upload
* video introduction upload
* validation
* application submission endpoint
* account conflict handling
* email mismatch/security handling
* Admin Job Applications integration

Do not redesign or rebuild the application page.

This is specifically an adjustment to how **pre-filled Talent details behave**.

---

# Current Behavior

When an authenticated Talent applies for a job, the page pre-fills information from their Talent account/profile.

Current fields include:

* First Name
* Last Name
* Email Address
* Phone Number
* CV / Resume
* Video Introduction when required
* Cover Letter where applicable

The page currently communicates that the Talent is:

**“Applying with your OnSpot Talent account.”**

This behavior should remain.

However, the Talent should be allowed to adjust their personal application details before submitting.

---

# Required New Behavior

## 1. Pre-Fill First, But Keep Fields Editable

When an authenticated Talent opens the application page:

Pre-fill the available information from their Talent account/profile.

For example:

```text
First Name
Val Testing

Last Name
Legaspi

Email Address
val.testtalent@onspotglobal.com

Phone Number
+639675456756
```

These values should act as **defaults for this application**.

The Talent must be able to edit the application information before clicking Continue/Submit.

### Editable fields

Allow editing of:

* First Name
* Last Name
* Phone Number
* application-specific Cover Letter
* any other normal application field that is not security-sensitive

Also allow editing of the displayed email according to the rules defined below.

Do not render these values as static text-only rows.

Use the existing form Inputs and design system.

---

# 2. Email Address Behavior

The current implementation makes the email field `readOnly` for authenticated Talent users.

Change this behavior carefully.

The Talent should be able to edit the email **displayed on the application**, but changing the application contact email must NOT change which Talent account owns the application.

The authenticated Talent/candidate ID must remain the authoritative application owner.

### Important

Do NOT use the edited email to determine Talent ownership when the user is already authenticated.

For authenticated Talents:

```text
authenticated Talent ID / candidate ID
```

must remain the authoritative identity.

The application may contain a different contact email if the Talent edits it.

Example:

Talent account email:

```text
val.testtalent@onspotglobal.com
```

Application contact email:

```text
val.personal@gmail.com
```

The application must still belong to the authenticated Val Talent account.

---

# 3. Remove Incorrect Email Mismatch Blocking for Authenticated Talent

Inspect the existing backend logic for:

`POST /api/jobs/:jobId/apply`

The current application flow appears to contain an `email_mismatch` safeguard.

That safeguard made sense when email was being used to determine application/account ownership.

For an already authenticated Talent, do NOT reject the application simply because the application contact email differs from the Talent account's login email.

Instead:

```text
Authenticated Talent
    ↓
Talent/candidate ID establishes ownership
    ↓
Application email is application contact information
```

Do not allow changing the form email to reassign the application to another Talent.

### Security requirement

Editing:

* email
* name
* phone

must never allow the application to become associated with another Talent account.

For authenticated Talent users, ownership must always come from the authenticated token/session.

---

# 4. Do Not Automatically Update Talent Profile

Changes made inside the job application form are **application-specific**.

For example, if Talent changes:

```text
Phone:
+639675456756
```

to:

```text
+639171234567
```

that new phone number should be saved to the submitted Job Application.

It should NOT automatically overwrite the Talent Profile phone number.

Likewise:

* editing First Name should not modify the Talent Profile
* editing Last Name should not modify the Talent Profile
* editing Email should not modify login/account email
* editing Phone should not modify the Talent Profile

Unless the project already intentionally updates profile values during an application, do not introduce that behavior.

The application record and Talent Profile must remain separate concerns.

The current authenticated Talent pre-fill logic in `JobApplyPage.tsx` appears to pre-fill:

* email

but phone may be coming from another profile source or separate application step.

Inspect the existing Talent profile/candidate API.

Do not rely only on the general authenticated `user` object if it does not contain all Talent profile fields.

Use the same authenticated Talent/candidate data source already used by:

* Talent Profile
* Talent Profile completion
* candidate data fetching

Preferred behavior:

```ts
form.firstName = talentProfile.firstName
form.lastName = talentProfile.lastName

```

Use the actual existing field names in the repository.

# 8. Do Not Overwrite User Edits After Initial Pre-Fill

This is important.

If Talent starts editing a field, a later React Query refresh or user/profile state update must NOT overwrite what they typed.

For example:

1. Page loads.
2. Phone is pre-filled with `+639675456756`.
3. Talent edits it to `+639171234567`.
4. Talent candidate query refetches.
5. Form must remain `+639171234567`.

Implement pre-fill as an **initialization**, not continuous synchronization.

Possible approaches:

* initialization flag
* `useRef`
* populate only while the form is still untouched
* initialize once when authenticated profile data first becomes available

Do not repeatedly call `setForm()` in a way that resets user input.

# Important Implementation Rule

Treat Talent profile information as:

**pre-fill/default application data**

not:

**immutable application data**

and not:

**automatic profile update data**.

For authenticated Talent users, always keep these concepts separate:

```text
Authentication identity
        ≠
Application contact information
        ≠
Talent Profile data
```

The authenticated Talent/candidate ID owns the application.

The editable form values belong to that specific application.

Do not use editable contact information to determine application ownership.
