Fix the existing **Invite Talent to Apply** flow in the Client portal.

There are three issues:

```text
1. The talent search inside the Invite Talent dialog is not filtering/searching correctly.
2. When a Client invites a Talent, the Talent does not receive an in-app notification.
3. The Talent must also receive an invitation email from findwork@onspotglobal.com.
```

Do NOT redesign or replace the existing invitation system.

Do NOT create another talent-search page.

Do NOT create another notification subsystem.

Do NOT create another email provider/service.

Reuse the existing Client invitation, notification, and email infrastructure.

---

# EXISTING FLOW TO PRESERVE

The existing formal invitation flow already uses:

```text
POST /api/client/invitations
```

with data such as:

```ts
{
  jobId,
  talentUserId,
  proposedTimes
}
```

Preserve that endpoint and its existing behavior, including:

```text
job ownership validation
MSA / Terms acceptance
duplicate invite protection
interview proposedTimes
existing application/submission creation
existing talent privacy rules
```

Do not create a parallel invite endpoint unless the existing one genuinely cannot support the required behavior.

# ISSUE 1 — Talent search inside Invite Talent modal does not work

Current UI:

```text
Invite Talent to Apply

Search talent for Data Entry.

[ Search by role, skill, or experience... ] [Search]
```

The modal initially shows talent results.

But when a Client enters a known talent/search term, for example:

```text
Val
```

the result becomes:

```text
No matching talent found.
```

even though talent matching that term visibly exists in the system.

This search must be fixed.

# Search requirements

The Client should be able to search by safe professional fields, including where available:

```text
masked/display name
target position
headline
category
skills
core skills
secondary skills
experience/seniority
location
```

Do NOT search or expose hidden PII such as:

```text
email
phone
resume URL
LinkedIn
GitHub
portfolio
personal website
```

---

# Important privacy requirement

Client-facing search results must continue to use the server-side talent sanitizer.

Do NOT bypass:

```text
server/lib/clientSearchSanitize.ts
```

The search endpoint may use internal/raw data for matching on the server, but the RESPONSE must remain sanitized.

That means:

```text
backend can search internal candidate data
↓
match candidates
↓
sanitize matched candidates
↓
return safe Client-facing response
```

Do not sanitize before searching if doing so removes fields required for proper matching.

---

# Case-insensitive matching

Search must be case-insensitive.

Examples:

```text
val
Val
VAL
```

should produce the same matches.

Trim whitespace.

Example:

```text
"  Val  "
```

must be treated as:

```text
"Val"
```

---

# Partial matching

Support practical partial text matches.

Example talent:

```text
Valerie
```

Search:

```text
Val
```

should match.

Example role:

```text
Technical Specialist
```

Search:

```text
technical
```

should match.

Example skill:

```text
Customer Service
```

Search:

```text
customer
```

should match.

---

# Token matching

For a multi-word query:

```text
customer support
```

match candidates where those words appear across relevant searchable professional fields.

Do not require the entire query to match one field exactly unless the existing search architecture intentionally does so.

---

# Do not search only the current visible page

If the current dialog initially loads a paginated subset of candidates, do not filter only that subset.

Search must query the actual eligible talent dataset.

Bad:

```ts
visibleResults.filter(...)
```

when only 20 candidates have been loaded.

Preferred:

```text
search query
→ backend
→ all eligible candidates
→ rank/filter
→ paginated sanitized results
```

---

# Verify search eligibility filters

Do not accidentally exclude valid Talent due to incorrect eligibility logic.

Inspect filters such as:

```text
candidate active status
availability
talent profile completeness
verified/vetted status
role
job match threshold
application state
already invited
```

A candidate should not disappear merely because the match score is low unless that is an intentional existing requirement.

The screenshot shows candidates with:

```text
0% match
5% match
```

which proves the modal already permits low match scores.

Therefore a valid talent should not be excluded just because search produces a low score.

---

# Search and ranking are separate

The text query determines whether a Talent is a relevant result.

The AI/job match score can still be displayed separately.

Example:

```text
Val T.            5% match
```

A result matching `Val` should be returned even if the job match score is low.

Do NOT use something like:

```ts
if (matchScore < threshold) exclude
```

unless the existing system explicitly requires it.

---

# Search button and Enter key

Verify both:

```text
click Search
press Enter
```

run the same query.

Prevent stale search state.

If the query is cleared and searched again, return the default eligible talent list.

# ISSUE 2 — Talent must receive an in-app notification when invited

When the Client successfully sends:

```text
Invite to Apply
```

the Talent being invited must receive a notification through the EXISTING notification system.

Do not create a special new notification UI.

Use the same notification bell/list infrastructure already used elsewhere.

---

# Notification trigger

Create the notification on the BACKEND after the formal invitation has been successfully created.

Correct architecture:

```text
Client clicks Invite to Apply
        ↓
POST /api/client/invitations
        ↓
backend validates Client/job/talent
        ↓
backend creates invitation/submission
        ↓
backend creates Talent notification
        ↓
backend sends Talent email
```

Do NOT:

```text
Client frontend manually POST notification
```

The backend invitation action must be authoritative.

---

# Notification recipient

The recipient is the invited Talent's user account.

Resolve:

```text
talentUserId
```

from the invitation payload to the actual notification user ID.

Do not notify:

```text
the Client
Admin
another Talent
all Talent users
```

# Invitation success handling

The DB invitation is the primary action.

Recommended handling:

```text
1. Create formal invitation
2. Create Talent notification
3. Attempt email
4. Return result
```

If invitation succeeds but email fails, do NOT create another invitation on retry.

Return useful metadata if compatible with the current API:

```json

  "success": true,
  "invitationCreated": true,
  "notificationCreated": true,
  "emailSent": false
}
```

The Client UI may show:

```text
Invitation sent, but the email notification could not be delivered.
```

If both succeed:

```text
Invitation sent successfully.
```

Do not tell the Client the email was sent if the mail transport failed.
