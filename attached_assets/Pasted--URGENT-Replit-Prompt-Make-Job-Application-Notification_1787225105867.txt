# URGENT Replit Prompt — Make Job Application Notifications Work for Client, Talent, and Admin Status Changes

The existing navbar Notification Bell is currently only handling OFFER notifications.

We now need proper **JOB APPLICATION notifications**.

This needs to work end-to-end on the backend and frontend.

Do not just change the bell text.

Do not fake notifications from frontend state.

Notifications must be persisted in the existing `notifications` table/system and appear for the correct authenticated user.

---

# REQUIRED BEHAVIOR

There are TWO main notification flows.

## FLOW 1 — Talent applies → Client gets notified

When a Talent successfully submits an application to a job:

```text
Talent applies
→ application/job_submission row created successfully
→ Client who owns that job receives notification
→ Client bell badge increases
→ Client opens bell
→ sees application notification
```

Example:

```text
New application received

Valu Testu applied for Social Media Manager.
```

Clicking it should take the Client to the relevant Client job/application area.

Prefer a route where they can actually inspect the submission.

---

## FLOW 2 — Client/Admin changes application status → Talent gets notified

Whenever the application status is changed by either:

```text
Client
OR
Admin
```

the Talent who owns that application must receive a notification.

Examples:

```text
Application update

Your application for Social Media Manager is now Under Review.
```

```text
Application update

Your application for Social Media Manager has been Shortlisted.
```

```text
Application update

Your application for Social Media Manager is now Interviewing.
```

```text
Application update

Your application for Social Media Manager was not selected.
```

Talent bell badge should increase immediately/on refresh.

Clicking the notification should navigate to:

```text
/my-applications
```

or preferably the relevant application/timeline if an existing direct route exists.

# TRANSACTION / FAILURE BEHAVIOR

The application/status update is the primary action.

Preferred behavior:

```text
DB application/status update succeeds
notification insert succeeds
response succeeds
```

If practical, use the same DB transaction.

If the existing architecture does not support this cleanly, do not make the primary status update fail solely because a secondary notification failed.

At minimum:

```ts
try {
  await storage.createNotification(...)
} catch (err) {
  console.error(...)
}
```

But log enough details to diagnose recipient-resolution failures.

Do not silently swallow everything.
