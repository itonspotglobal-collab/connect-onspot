# Fix Remaining Job Application Flow + Resume Address Parsing

Two bugs remain after the recent Talent application-flow changes.

Do not revert the new desired flow.

The intended flow remains:

```text
NEW USER:
Apply Now
→ Create Talent Account / Sign In
→ Prefilled Application Review
→ Submit Application

EXISTING TALENT:
Apply Now
→ Prefilled Application Review
→ Submit Application
```

## BUG 1 — “Create Talent Account & Apply” leads to Link Unavailable

Current behavior:

1. Logged-out visitor opens a job.
2. Clicks Apply Now.
3. Sees:

   * Create Talent Account & Apply
   * Sign In to Existing Account
4. Clicks `Create Talent Account & Apply`.
5. Lands on:

```text
Link unavailable
No application token found.
Please apply for a job first.
```

This is wrong.

---

# Confirmed root cause

Inspect:

```text
client/src/pages/TalentSignupFromApplication.tsx
client/src/pages/JobApplyPage.tsx
client/src/pages/FindWorkJob.tsx
client/src/App.tsx
server/routes.ts
```

The existing `TalentSignupFromApplication.tsx` still assumes the OLD flow.

It currently expects:

```ts
const applicationToken =
  searchParams.get("applicationToken") ?? "";
```

and then immediately fails when it is missing.

That page was originally designed for:

```text
Application submitted first
→ backend creates continuationToken
→ redirect to signup with applicationToken
```

But the product flow has now changed to:

```text
Account first
→ Application second
```

Therefore the signup page must no longer require a previously-created application token for the new-user Apply flow.

---

# 1. Preserve JOB context, not APPLICATION context

When the user clicks:

```text
Create Talent Account & Apply
```

pass the selected job identifier to account creation.

For example:

```text
/talent/signup?jobId=<job-id>&intent=apply
```

or use a safe route/state/session mechanism already established in the project.

The important thing is:

```text
jobId must survive account creation
```

Do NOT require:

```text
applicationToken
submissionId
```

because no application should exist yet.

---

# 2. Support two signup entry modes temporarily

`TalentSignupFromApplication.tsx` may still be used by old continuation links.

Do not break existing historical links unnecessarily.

Support:

### New account-first mode

Input:

```text
jobId
intent=apply
```

Behavior:

```text
Create Talent account
→ authenticate
→ create/fetch Candidate
→ return to /jobs/:jobId/apply
→ show prefilled application
```

### Legacy continuation mode

Input:

```text
applicationToken
```

If this old workflow is still needed anywhere, preserve it separately.

Do not make `applicationToken` mandatory when `jobId` exists.

Conceptually:

```ts
if (applicationToken) {
  // legacy application-first continuation
} else if (jobId) {
  // new account-first flow
} else {
  // truly invalid link
}
```

---

# 3. After account creation, establish the correct Talent session

The active Talent system uses the Candidate/Talent authentication architecture.

Inspect the current signup response and Talent login flow.

After creating a new Talent account, make sure the same auth state used by the Talent Profile is established.

That may include:

```text
talent_profile_token
candidateId
TalentAuthState
```

Do NOT only set:

```text
onspot_jwt_token
onspot_user
```

if the current Candidate-based pages require `talent_profile_token`.

Avoid creating another auth split.

After signup, verify:

```ts
loadTalentAuth()
```

returns the newly-created Candidate session if that is now the canonical Talent auth mechanism.

---

# 4. Redirect back to the SAME job

After successful signup:

Do NOT redirect the user to Find Best Matches.

For an Apply flow, return them directly to the selected job application:

```text
/find-work/job/<jobId>/apply
```

or the correct existing application route.

The application page should then see the Talent session and load the Candidate profile.

Expected:

```text
Create account
→ authenticated
→ application review page
```

with no extra navigation required.

# 5. Existing Talent Sign In flow

The button:

```text
Sign In to Existing Account
```

must also preserve:


After successful sign-in:

```text
return to the same application
```

Do not send them to a generic dashboard.

Example desired flow:

```text

→ Sign In

```

---

# 6. Do not create an application record before account creation

This is essential.

For a new visitor, clicking Apply Now should NOT yet call:

```text
POST /api/jobs/:jobId/apply
```

because the user has not reviewed the application form yet.

Application creation should happen only after:

1. account exists;
2. Candidate profile is loaded;
3. application is prefilled;
4. user reviews it;
5. user clicks Submit Application.

The backend application record should therefore be created at the final submission step.

Refactor `JobApplyPage.tsx` to use an explicit flow.

Conceptually:

```ts
type ApplyStage =
```

Do not let old continuation-token logic control the new primary flow.

# 11. Improve location extraction

Inspect the current location extraction inside:

```text
client/src/lib/resumeParser.ts
```

Support clearly-labeled formats such as:

```text
Address: Cebu City, Philippines
Address: 123 Example Street, Cebu City, Philippines
Location: Manila, Philippines
Current Address: Makati City, Metro Manila
Current Location: Davao City, Philippines
Based in: Cebu, Philippines
Residence: Quezon City, Philippines
```

Case-insensitive labels.

Conceptually:

```ts
const labeledLocationPatterns = [
  /(?:current\s+)?address\s*[:\-]\s*(.+)/i,
  /(?:current\s+)?location\s*[:\-]\s*(.+)/i,
  /based\s+in\s*[:\-]?\s*(.+)/i,
  /residence\s*[:\-]\s*(.+)/i,
];
```

But adapt this to the actual parser structure.

---

# 12. Handle PDF line reconstruction

The PDF extractor rebuilds text by Y-coordinate.

Addresses may be fragmented into lines such as:

```text
Cebu City
Philippines
```

or:

```text
123 Sample Street
Cebu City, Philippines
```

Add logic to examine nearby contact/header lines when appropriate.

The parser should not require the full address to exist on one line if PDF extraction splits it naturally.

---

# 13. Prefer header/contact region

Address/location is normally found near:

```text
Name
Email
Phone
Address
LinkedIn
```

Prioritize early resume/contact lines before Work Experience or Education.

Do not accidentally treat employer locations as the candidate's home/current location.

Examples to avoid:

```text
Software Engineer — Cebu City
ABC Company — Manila
University of Cebu
```

Those are not necessarily the Talent's address.

---

# 14. Location confidence rules

Use strong candidates first:

### High confidence

Explicit:

```text
Address:
Location:
Current Address:
Current Location:
Based in:
Residence:
```

### Medium confidence

A city/province/country line appearing in the contact/header block beside email/phone.

### Reject

Locations found only inside:

```text
Work Experience
Education
Projects
References
```

unless another strong signal indicates personal location.

# 16. Find Best Matches mapping

After parsing, make sure:

```ts
parsed.location
```

actually populates the Location input state.

Example:

```ts
setProfile(prev => ({
  ...prev,
  location:
    userHasManuallyEditedLocation
      ? prev.location
      : parsed.location || prev.location,
}));
```

Use the actual state architecture.

Do not overwrite manually edited Location after the user changes it.

---

# 17. Watch for state reset

Inspect `FindBestMatches.tsx` for effects that may do:

```ts
setLocation("")
```

or restore Candidate/default data after parsing.

A common failure pattern is:

```text
parser fills location
→ async Candidate fetch completes
→ useEffect resets form
→ location becomes blank
```

Fix ordering/race conditions.

Candidate/server data should win initially, but resume parsing should fill missing fields when the Candidate profile is incomplete.

Recommended precedence:

```text
manual user edit
> persisted Candidate value
> parsed resume value
> empty/default
```

But for a new Candidate with no location:

```text
parsed resume location
```

should populate the field.

---

# 18. Verify extractedFields

If Location is successfully parsed, ensure:

```text
extractedFields
```

contains:

```text
location
```

if the rest of the parser uses that array to decide which fields to populate.

A parser can correctly assign `result.location` yet still fail UI mapping if `extractedFields` does not include it.
