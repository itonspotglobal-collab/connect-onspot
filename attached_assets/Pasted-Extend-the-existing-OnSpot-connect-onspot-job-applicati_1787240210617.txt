Extend the existing OnSpot / `connect-onspot` job application workflow so application status changes are coordinated with email delivery and notifications.

## GOAL

There are two related workflows to support:

### A. Admin changes a Talent application status

Admin must:

1. choose the new status
2. choose/review an email template
3. compose/confirm the email
4. send the email
5. ONLY AFTER successful email send:

   * commit the new application status
   * write status history
   * notify the Talent

### B. Client changes a Talent application status

When a Client changes the status of an application to their own job:

* Talent receives an application-status notification
* Admin receives a notification describing the Client's change
* existing Talent email behavior should remain consistent with product rules

Do not create duplicate application records.

Do not create a parallel notification system.

Use the existing canonical application/submission record and existing email/notification infrastructure.

# ADMIN WORKFLOW — TWO STEP PROCESS

When Admin selects a new application status, DO NOT immediately persist the status.

The flow should become:

```text
Admin selects new status
        ↓
Pending status change
        ↓
Email Applicant modal opens
        ↓
Admin chooses email template
        ↓
Admin reviews/edits subject + body
        ↓
Admin clicks Send Email
        ↓
Email successfully sends
        ↓
Application status is committed
        ↓
Status history written
        ↓
Talent notification created
```

If the email fails:

```text
status must remain unchanged
```

This is critical.

# STATUS SHOULD COMMIT ONLY AFTER SUCCESSFUL EMAIL

This must be enforced server-side, not only in React.

Do not implement:

1. PATCH status
2. try to email
3. rollback visually if email fails

Instead create an atomic/coordinated workflow endpoint.

Preferred conceptual endpoint:

`POST /api/admin/job-applications/:applicationId/status-with-email`

Payload conceptually:

```json
{
  "newStatus": "shortlisted",
  "templateId": "...",
  "subject": "...",
  "htmlBody": "...",
  "textBody": "..."
}
```

The exact schema should follow existing email composer contracts.

# SERVER PROCESS FOR ADMIN CHANGE

Conceptually:

```text
1. authenticate Admin
2. load application
3. validate requested status transition
4. load Talent recipient
5. validate email address
6. render/validate chosen email content
7. send email
8. if email fails → STOP, no status update
9. update job_submissions.status
10. write status history
11. create Talent notification
12. return updated application
```

If DB transaction cannot include external email delivery, handle carefully:

* email must succeed first
* then perform DB status/history/notification transaction
* if DB commit fails after email succeeds, log a high-priority consistency error and return failure

Do not pretend external email can participate in a normal SQL transaction.

# IF TALENT HAS NO VALID EMAIL

Admin should not be able to accidentally commit an email-required status change without a deliverable address.

If email is missing/invalid:

show:

`Applicant does not have a valid email address. Status was not changed.`

If product later supports override, that should be a separate explicit feature.

Do not silently skip email.

---

# IF TALENT ACCOUNT IS NOT LINKED

If application exists but no linked Talent user exists:

email may still be possible using application email.

But in-app notification requires a linked/canonical user.

Handle gracefully:

* email can send if valid
* status may commit after email
* log/skips in-app Talent notification only if no canonical account exists

Do not crash.

Clearly report this case in completion notes.
