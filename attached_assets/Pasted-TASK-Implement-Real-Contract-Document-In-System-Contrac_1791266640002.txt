TASK: Implement Real Contract Document + In-System Contract Signing Workflow

IMPORTANT:
Audit the existing contract, offer, organization, object-storage, email,
notification, and hiring pipeline implementation FIRST.

Then implement this feature using the existing architecture.

Do NOT replace the existing hiring contract system with an unrelated
parallel contract system.

Do NOT create fake signing states.

Do NOT mark a Talent as Hired until the required contract-signing workflow
has actually completed.

============================================================
GOAL
============================================================

Implement an end-to-end contract signing workflow between:

1. Client → Talent
2. OnSpot Admin → Talent
3. Authorized Organization representative → Talent

After an offer has been accepted, an authorized Client/Admin should be
able to prepare the employment/contractor agreement by uploading a PDF.

The Talent then receives the contract inside OnSpot and can review and
sign it.

After all required signatures are completed, the existing hiring contract
should become active and the Talent/application can transition to Hired
according to the existing signed-contract workflow.

============================================================
EXPECTED FLOW
============================================================

Offer
→ Talent accepts offer
→ Prepare Contract
→ Upload PDF
→ Review contract
→ Send to Talent
→ Talent receives notification/email
→ Talent opens contract
→ Talent reviews PDF
→ Talent signs
→ Client/Admin/Organization countersigns if required
→ Contract becomes fully executed
→ Existing hiring workflow activates contract
→ Application becomes Hired

Do not bypass the accepted-offer requirement.

============================================================
2. PRIVATE CONTRACT STORAGE
============================================================

Contracts contain sensitive information.

Contract PDFs MUST NOT be publicly accessible.

Use authenticated/authorized retrieval.

Only authorized parties should be able to retrieve the contract:

- relevant Talent
- authorized Client
- authorized Organization member with appropriate permission
- authorized OnSpot Admin

Client A must never retrieve Client B's contract merely by knowing an
object ID or contract ID.

Organization A must never retrieve Organization B's contract.

Do not expose raw storage credentials or permanent public URLs.

If signed/temporary download URLs are used, generate them server-side
after authorization.

============================================================
6. SIGNATURE RECORD
============================================================

Do not only update:

talent_signed = true

Create/preserve an auditable signature record.

Audit existing signature fields/tables first.

Each signature should capture at minimum:

- contract/document ID
- signer user ID
- signer role
- signer display/legal name used
- signature method
- signed_at
- contract document version/hash
- relevant audit metadata already supported by the platform

Where legally/privacy appropriate within the existing system architecture,
record security/audit information required to establish who performed the
action.

Do not expose sensitive audit information in ordinary UI.

IMPORTANT:

The signature MUST be bound to the exact PDF/version that was reviewed.

Compute and persist a cryptographic hash such as SHA-256 for the contract
document/version.

When signing, associate the signature with that document hash.

If document bytes change, the existing signatures must not remain valid
for the changed document.

14. SECURITY REQUIREMENTS
============================================================

Treat contract documents as confidential.

Required protections:

- authentication
- authorization
- organization scoping
- Client ownership checks
- Talent identity checks
- private object storage
- immutable signed versions
- signature audit trail
- document hash/version binding
- server-side signing authorization
- CSRF/security protections already used by the application
- safe filename handling
- safe PDF validation

Never trust:
- client-provided signer role
- client-provided organization ID without authorization
- client-provided Talent ID without relationship validation
- object-storage key without contract authorization
- "signed=true" from frontend

Server determines all canonical relationships.
