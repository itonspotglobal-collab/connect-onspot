BUILD STAGE-BASED APPLICANT EMAILS IN THE JOB APPLICATION DASHBOARD

Work inside the existing OnSpot application. Do not create a separate app,
database, authentication system, or email platform.

TARGET PAGE

`/admin/job-applications`

PURPOSE

Recruiters need to send stage-specific emails to applicants directly from the
Job Applications dashboard.

The feature should feel similar to the existing Admin Insights editor:

- editable content;
- reusable saved templates;
- preview mode;
- draft/published state where appropriate;
- a clear send action.

The actual email must be sent using the existing Microsoft 365 / Outlook
environment through Microsoft Graph.

CURRENT ADMIN ACCESS

Admin authentication is intentionally not implemented yet.

Keep this feature consistent with the current temporary public admin pages.

Do not introduce `AdminProtectedRoute` or backend admin authorization only for
this feature.

Add clear code comments:

`TODO: Protect applicant email features with admin authorization before production.`

Inspect:

- `client/src/pages/AdminJobApplications.tsx`
- `client/src/pages/AdminInsights.tsx`
- `client/src/pages/AdminInsightEditor.tsx`
- `client/src/App.tsx`
- `client/src/components/TopNavigation.tsx`
- existing Dialog, Drawer, Tabs, Select, Textarea, Input, Button, Badge, Toast
  and rich-text components;
- `shared/schema.ts`
- `server/routes.ts`
- `server/storage.ts`
- existing job-application APIs;
- application stage/status-history implementation;
- existing email or Microsoft integration services;
- Replit environment-variable conventions.

Reuse existing components, layouts, request helpers, error handling, database
patterns, and UI styles.

Do not duplicate existing email functionality if it already exists.

PART 6 — MICROSOFT GRAPH SERVICE
==================================================

Create or extend a backend service such as:

`server/services/microsoftGraphEmailService.ts`

Use server-side Microsoft Graph authentication.

Required environment variables:

- `MICROSOFT_TENANT_ID`
- `MICROSOFT_CLIENT_ID`
- `MICROSOFT_CLIENT_SECRET`
- `APPLICATION_EMAIL_FROM`
- `APPLICATION_EMAIL_FROM_NAME`
- optional `APPLICATION_EMAIL_REPLY_TO`
- `PUBLIC_APP_URL`

Never expose these values in React code or API responses.

Use the Microsoft OAuth client-credentials flow.

Obtain an access token server-side.

Send the email through the configured Microsoft 365 mailbox.

Do not use the applicant's email as the sender.

Do not store Microsoft access tokens permanently in the database.

Cache an access token in memory only until shortly before expiration if useful.

Handle token refresh safely.

SEND-MAIL IMPLEMENTATION

Build a service method conceptually similar to:

`sendApplicantEmail({ to, subject, htmlBody, textBody, replyTo })`

Return a structured result:

{
  success: true,
  provider: "microsoft_graph",
  providerMessageId: "..."
}

or:

{
  success: false,
  provider: "microsoft_graph",
  errorCode: "...",
  errorMessage: "..."
}

Do not expose raw Microsoft credentials or token responses.

PART 7 — API ENDPOINTS
==================================================

Use project conventions, but support functionality equivalent to:

TEMPLATES

GET `/api/admin/email-templates`

GET `/api/admin/email-templates/:templateId`

POST `/api/admin/email-templates`

PATCH `/api/admin/email-templates/:templateId`

POST `/api/admin/email-templates/:templateId/publish`

POST `/api/admin/email-templates/:templateId/duplicate`

DELETE or archive:

`/api/admin/email-templates/:templateId`

Prefer archive over permanent deletion for published templates that have
communication history.

PREVIEW

POST `/api/admin/job-applications/:applicationId/email-preview`

Request:

{
  "templateId": "...",
  "subject": "...",
  "htmlBody": "...",
  "textBody": "...",
  "variables": {
    "assessmentLink": "...",
    "interviewDate": "...",
    "interviewTime": "...",
    "interviewTimezone": "...",
    "interviewLink": "..."
  }
}

The backend must:

- load the application;
- resolve applicant/job variables;
- merge allowed supplemental variables;
- sanitize the output;
- return rendered subject/body;
- identify unresolved variables.

SEND TEST

POST `/api/admin/job-applications/:applicationId/email-test`

Request:

{
  "testRecipient": "recruiter@onspotglobal.com",
  "subject": "...",
  "htmlBody": "...",
  "textBody": "...",
  "variables": {}
}

Requirements:

- validate test email;
- clearly prefix the subject with `[TEST]`;
- do not record the test email as an applicant communication;
- optionally record it in technical logs without applicant PII.

SEND APPLICANT EMAIL

POST `/api/admin/job-applications/:applicationId/send-email`

Request:

{
  "templateId": "...",
  "subject": "...",
  "htmlBody": "...",
  "textBody": "...",
  "replyTo": "...",
  "variables": {},
  "updateStage": false,
  "newStage": null,
  "newStatus": null,
  "note": null
}

Backend behavior:

1. Validate request with Zod.
2. Load the application by application ID.
3. Confirm it has a valid recipient email.
4. Resolve variables server-side.
5. Reject or warn about unresolved required variables.
6. Create a `job_application_emails` row with `sending`.
7. Send through Microsoft Graph.
8. Update row to `sent` or `failed`.
9. Return a safe result.

Never trust recipient email supplied by the browser.

The recipient must come from the selected application.

COMMUNICATION HISTORY

GET `/api/admin/job-applications/:applicationId/emails`

Return:

- subject;
- template;
- stage;
- sent/failed status;
- sent date;
- provider;
- retry count;
- error summary;
- safe preview.

RETRY

POST `/api/admin/job-applications/:applicationId/emails/:emailId/retry`

Retry only failed emails.

Do not duplicate successful communications unless the recruiter intentionally
chooses Resend.

PART 9 — COMBINED “UPDATE & SEND” FLOW
==================================================

The preferred recruiter workflow is:

1. Select a stage action.
2. Open email composer.
3. Load the mapped template.
4. Edit the email.
5. Preview it.
6. Confirm.
7. Update stage/status.
8. Send email.
9. Record both actions.

Example:

`Assessment Passed → Initial Interview`

opens:

Title:
`Advance to Initial Interview`

Template:
`Initial Interview Invitation`

The recruiter can fill:

- interview date;
- interview time;
- timezone;
- meeting link;
- recruiter name.

Primary button:

`Advance & Send Email`

Use a database transaction for the local database changes where practical.

However, Microsoft Graph is an external service and cannot be part of a normal
database transaction.

Handle this reliably:

1. Save intended stage transition and outgoing communication record.
2. Send email.
3. Mark communication sent or failed.
4. Clearly show the final result.

If stage update succeeds but email sending fails, show:

`Application advanced to Initial Interview, but the email failed to send.`

Provide:

`Retry Email`

Do not silently roll back or hide the stage change.

Alternatively, before the action, provide a checkbox:

`Only update the stage if the email sends successfully.`

Use the simpler reliable behavior unless existing product requirements specify
otherwise.

PART 13 — AUTOMATIC APPLICATION CONFIRMATION
==================================================

The initial Application Received email may be automatic.

After a valid application is successfully saved:

1. Save application.
2. Attempt to queue/send Application Received email.
3. Continue the account flow normally.

Do not make the application submission fail because email sending fails.

If sending fails:

- application remains saved;
- record failed email status;
- make Retry available in the dashboard.

Later-stage emails remain recruiter-triggered through buttons.

==================================================
PART 14 — ERROR HANDLING
==================================================

Display clear outcomes.

Successful:

`Email sent successfully to m***@example.com.`

Failed:

`The application was updated, but the email could not be sent.`

Include a Retry action where appropriate.

Do not expose raw Microsoft Graph responses to the browser.

Log technical errors without logging full email content or unnecessary PII.

Every API response must be JSON.

Do not let `/api/...` errors fall through to the frontend HTML document.

PART 15 — SECURITY AND PRIVACY
==================================================

- Store Microsoft credentials only in Replit Secrets.
- Never expose Graph access tokens.
- Validate all email addresses.
- Sanitize HTML.
- Block script tags and dangerous URLs.
- Do not trust application IDs, emails, Talent IDs, stages, or roles from the
  frontend without server-side validation.
- Load applicant recipient data from the database.
- Avoid applicant PII in URLs.
- Avoid full email bodies in normal server logs.
- Add rate limiting to send and test-send endpoints.
- Prevent accidental duplicate sends.
- Keep an audit/communication record.
- Restrict external links to safe HTTP/HTTPS URLs.
- Add admin authorization TODO comments for the current temporary public-admin
  phase.
