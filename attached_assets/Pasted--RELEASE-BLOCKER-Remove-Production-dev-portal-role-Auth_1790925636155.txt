# RELEASE BLOCKER — Remove Production `dev_portal_role` Authentication Bypass

We are addressing ONE release blocker discovered by the MVP release-readiness verification.

This is not a feature task.

Do not modify Priorities 1–6 unless required by this specific authentication correction.

Do not begin a broad security refactor.

---

## Confirmed Finding

Release-readiness inspection found that:

`client/src/components/ProtectedRoute.tsx`

contains logic around lines approximately 22–30 that accepts a browser-controlled:

`dev_portal_role`

before normal authentication checks.

The branch remains present in the fresh production frontend bundle.

This must be investigated and corrected before publication.

Important:

The finding currently establishes a **frontend route-guard bypass**.

It does NOT by itself establish backend/API authorization bypass.

Do not exaggerate the finding.

# PHASE 2 — DETERMINE INTENDED DEVELOPMENT BEHAVIOR

Determine why `dev_portal_role` exists.

Identify whether current developers/tests rely on it.

If development preview legitimately needs a role simulation mechanism, preserve it ONLY in a way that cannot execute in a production build/runtime.

Prefer existing environment/build-mode conventions already used by the application.

Do not introduce another production-accessible bypass.

---

# PHASE 3 — IMPLEMENT MINIMAL FIX

The production application must NEVER trust:

`dev_portal_role`

or another browser-controlled development role override as authentication/authorization.

Production `ProtectedRoute` behavior must derive access from the legitimate authenticated user/session.

Choose the smallest implementation consistent with the existing architecture.

If development-role simulation must remain, guard it so it is provably development-only and excluded/unreachable in production.

Do not weaken backend authorization.

Do not redesign the entire authentication system.
