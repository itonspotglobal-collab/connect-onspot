Improve the existing OnSpot / `connect-onspot` notification system so repeated chat messages do not spam the Notification Bell.

## CURRENT PROBLEM

Messaging works correctly, but every individual incoming chat message currently creates its own Bell notification.

Example:

Talent sends Client 5 messages in a short period.

Current Bell:

```text id="flq9xb"
New message
You have a new message.

New message
You have a new message.

New message
You have a new message.

New message
You have a new message.

New message
You have a new message.
```

This is noisy and looks like notification spam.

---

# REQUIRED RESULT

Compress consecutive/recent unread message notifications from the SAME conversation into ONE notification card.

Example:

Talent sends Client 3 messages.

Instead of 3 notification cards, show:

```text id="uu6n3z"
New messages
Valu Testu sent 3 messages.
```

or:

```text id="48gqdt"
3 new messages
Valu Testu sent you 3 messages.
```

If job context is available:

```text id="favwvo"
New messages
Valu Testu sent 3 messages about Social Media Manager.
```

Use safe display names.

---

# IMPORTANT SCOPE

This change applies to message-notification aggregation for:

* Client accounts
* Talent accounts
* Admin accounts IF Admin receives normal `new_message` notifications as a participant

Do NOT alter unrelated notification types.

Examples that must remain independent:

* Application update
* New application received
* Application withdrawn
* Offer received
* Offer accepted
* Offer declined
* Admin alerts
* other system notifications

Only aggregate repeated:

`new_message`

notifications.

---

# DO NOT AGGREGATE THE ACTUAL MESSAGES

This is critical.

If a user sends:

```text id="pjj6yj"
Hello
Are you available?
Can we discuss the role?
```

the messages table must still contain THREE messages.

The receiver's unread message count must still be:

`3`

The thread should still display all three messages.

Delivered / Read state must still work per message.

Only the **Bell notification representation** should be compressed.

---

# KEEP MESSAGE BADGES NUMERIC

Do not change:

* Client sidebar Messages count
* Client dropdown Messages count
* Talent dropdown Messages count
* Talent page Messages count
* Job Submission Message count
* Reach the Client count
* thread unread count

If 3 messages are unread:

those message-specific indicators should still show:

`3`

Even if the Bell contains only ONE grouped notification card.

---

# BELL RED DOT

The Bell itself was intentionally changed to a red dot instead of a number.

Preserve that.

If one or more unread notifications exist:

show red dot.

Do not bring back a number on the Bell icon.

# AGGREGATION KEY

Group message notifications by:

1. recipient
2. canonical message thread
3. notification type = `new_message`

Do NOT group different threads together.

Example:

Client A sends 3 messages in Thread A.

Client B sends 2 messages in Thread B.

Talent should see TWO Bell cards:

```text id="bcn59v"
Client A sent 3 messages.
Client B sent 2 messages.
```

NOT:

```text id="h43sfr"
You have 5 new messages.
```

unless product design intentionally wants a global summary.

For this task, preserve thread/person context.

---

# SAME PERSON, DIFFERENT JOB THREADS

If the same Talent/Client has two separate valid threads:

Thread A:
Social Media Manager

Thread B:
Virtual Assistant

Do NOT blindly combine them by sender name.

Aggregate by canonical `threadId`.

This prevents unrelated job conversations from being mixed.

---

# TIME / UNREAD WINDOW

Aggregation should primarily apply while the previous message notification for that thread is still unread.

Preferred behavior:

When a new message arrives:

1. find existing unread `new_message` notification for:

   * same recipient
   * same thread
2. if found:
   update that notification instead of inserting another row
3. increment grouped message count
4. refresh notification timestamp
5. keep it unread
6. move it to the top of the notification list

If no unread grouped notification exists:

create a new one.

---

# AFTER USER READS THE THREAD

Once the recipient opens the thread and the corresponding message notification is marked read:

future messages should create a NEW notification group.

Example:

Client sends 3 messages.

Notification:

`Client sent 3 messages.`

Talent opens and reads thread.

Notification becomes read.

Later Client sends 2 more messages.

Create a new unread notification:

`Client sent 2 messages.`

Do not update the old read notification.

---

# AFTER USER READS ONLY THE NOTIFICATION

Audit current Notification Bell behavior.

If clicking the notification opens the message thread and marks the thread read:

group becomes read as part of that flow.

If notification can be manually marked read without opening the thread:

follow existing read semantics carefully.

Do not let a read notification continue accumulating future messages.

Only aggregate into an existing UNREAD message notification.

---

# BACKEND-FIRST IMPLEMENTATION

Do not solve this only by visually grouping duplicate rows in React.

Preferred:

aggregate at notification creation/persistence time.

This gives consistent behavior across:

* Client
* Talent
* Admin
* refresh
* logout/login
* multiple devices

The database should ideally contain one current unread notification group per recipient/thread.

# RECOMMENDED HELPER

Create a reusable backend helper conceptually like:

```ts id="465xqk"
upsertNewMessageNotification({
  recipientUserId,
  senderUserId,
  threadId,
  senderDisplayName,
  subject,
})
```

This helper should:

1. search for an existing unread `new_message` notification
2. same recipient
3. same `threadId`
4. if found:

   * increment message count
   * update text
   * update timestamp
5. otherwise:

   * create first notification with count = 1

Use the application's existing storage abstraction.

Do not duplicate SQL in multiple routes.

# WHERE TO STORE THE GROUP COUNT

Audit the existing notifications schema.

Prefer the least invasive compatible option.

Possible safe approaches:

### Option A — metadata/json field already exists

If notifications already support metadata, store:

```json id="n4hzug"

  "messageCount": 3,
  "threadId": "...",
  "senderUserId": "..."
}
```

Preferred if available.

### Option B — derive count from structured notification data

If there is an existing metadata/data column, use it.

### Option C — minimal schema addition

Only if no suitable metadata exists, add a minimal nullable integer such as:

`group_count`

or similar.

Do NOT add schema changes unless necessary.

Do not encode core logic by parsing human-readable notification text.

# NOTIFICATION ORDER

When the existing group is updated with another incoming message:

move it to the top by updating:

`updatedAt`

or whichever sortable timestamp the Bell uses.

Example:

Valu sent 1 message

`Valu Testu sent you 2 messages.`
`Just now`

and be at top.

# CONCURRENT MESSAGES / RACE SAFETY

Protect against rapid sends.

Example:

3 messages arrive almost simultaneously.

Do not accidentally create:

* group count 1
* group count 1
* group count 1

Use an atomic update/upsert or transaction/locking strategy where practical.

Final result:

ONE notification with count = 3.

---

# DUPLICATE REQUEST SAFETY

If the same message POST is retried and existing message-creation logic prevents duplicate messages:

do not increment grouped notification twice.

Aggregation should correspond to successfully persisted unique message events.

Do not let transport retries inflate the count.

The grouped Bell notification should become read.

Do not leave:

`Valu sent 5 messages`

as unread after the user has read those messages.
