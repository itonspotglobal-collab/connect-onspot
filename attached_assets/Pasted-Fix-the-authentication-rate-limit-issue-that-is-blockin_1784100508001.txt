Fix the authentication rate-limit issue that is blocking valid Client login after password reset.



Current behavior:

- Client signup works.

- Password reset now works.

- Logging in with the newly reset password still fails.

- Browser console shows:



POST /api/login → 429 Too Many Requests



- UI shows:

  “Too many login/signup attempts. Please try again later.”



This is not currently an invalid-password issue. The login request is being rejected by the rate limiter before authentication runs.



Known current configuration:

- Authentication limiter allows approximately 10 requests per IP per 15 minutes.

- During testing, signup, login, and password reset requests quickly exhaust the same limit.

- Replit users may share or appear behind the same proxy/IP, making IP-only limiting unreliable.



Do not remove rate limiting entirely.

Do not weaken password authentication.

Fix the limiter so valid users are not locked out unnecessarily.

PHASE 3 — SPLIT THE AUTH LIMITERS



Do not use one shared counter for login, signup, and password reset.



Create separate limiters:



Login limiter

Signup limiter

Forgot-password limiter

Reset-password limiter



Suggested development/staging defaults:

Signup:

Forgot password:

Reset password:



validate by reset token

Use environment variables:

PHASE 4 — LIMIT FAILED LOGINS, NOT ALL LOGIN REQUESTS



Where supported, configure the login limiter so successful logins do not count:



skipSuccessfulRequests: true



A correct login should not move the user closer to being blocked.



Do not use skipFailedRequests: true, because failed attempts are what should be limited.



If the library cannot reset counters reliably, document the behavior and use a custom key/store safely.



PHASE 5 — USE A BETTER LIMIT KEY



An IP-only key is not sufficient behind Replit/shared networks.



For login, use a normalized combination such as:



const normalizedEmail =

  typeof req.body?.email === "string"

    ? req.body.email.trim().toLowerCase()

    : "unknown";



return `${req.ip}:${normalizedEmail}`;



This prevents one user’s repeated attempts from blocking every other user on the same IP.



Do not reveal whether an email exists.



For authenticated routes, use user ID where appropriate.



PHASE 6 — USE A SHARED STORE IN PRODUCTION



Check whether the current rate limiter uses the default in-memory store.



The in-memory store:



resets on server restart

does not coordinate across multiple instances

can produce inconsistent behavior



For a single Replit instance, it may be acceptable temporarily.



Document the limitation.



If the deployment uses multiple instances, use a shared store backed by PostgreSQL or another existing shared service.



Do not add Redis unless clearly necessary.
