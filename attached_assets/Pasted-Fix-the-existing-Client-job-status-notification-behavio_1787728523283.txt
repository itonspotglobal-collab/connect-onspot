Fix the existing Client job-status notification behavior.

The current implementation successfully creates a notification the FIRST time a Client job is approved, but subsequent status changes do not create notifications.

Observed test:

```text
Pending
→ Admin Approves
→ Client receives "Job post approved" ✅

Approved
→ Admin Unapproves
→ Client receives nothing ❌

Pending
→ Admin Approves again
→ Client receives nothing ❌
```

Also add notification support for:

```text
Pending
→ Admin Rejects
→ Client must receive rejection notification
```

This behavior is incorrect.

---

# Required principle

Notifications must represent **approval-status transition events**, not a once-per-job notification.

Do NOT globally deduplicate a notification only because:

```text
same jobId
same notification type
```

A single job can legitimately move through multiple approval states over time.

Each real state change must create a new notification.

---

# Required transitions

At minimum support:

```text
pending → approved
approved → pending
pending → rejected
rejected → pending
rejected → approved
approved → rejected
```

Only implement transitions that the current Admin workflow actually permits.

For every successful status transition, create the appropriate Client notification.

---

# 1. Approved notification

When:

```text
previousApprovalStatus !== "approved"
newApprovalStatus === "approved"
```

create:

Title:

```text
Job post approved
```

Message:

```text
Your job post “{{job_title}}” has been approved and is now live.
```

Example:

```text
Job post approved

Your job post “Testpost” has been approved and is now live.
```

This should happen EVERY TIME the job enters the approved state.

Example:

```text
pending → approved
```

creates notification #1.

Then:

```text
approved → pending → approved
```

must create another NEW approval notification.

Do not suppress it because an older approval notification already exists.

---

# 2. Unapproved / moved back to pending notification

When Admin uses the existing:

```text
Unapprove
```

action and the status changes:

```text
approved → pending
```

create a new Client notification.

Recommended title:

```text
Job post moved back to review
```

Recommended message:

```text
Your job post “{{job_title}}” has been moved back to Pending Approval and is no longer publicly visible.
```

Example:

```text
Job post moved back to review

Your job post “Testpost” has been moved back to Pending Approval and is no longer publicly visible.
```

Use wording consistent with the existing product UI.

Do not imply the job was deleted.

---

# 3. Rejected notification

When:

```text
pending → rejected
```

create:

Title:

```text
Job post rejected
```

Message:

```text
Your job post “{{job_title}}” was not approved.
```

If the Admin provided a rejection reason and the existing workflow safely stores it, include it:

```text
Your job post “Testpost” was not approved.

Reason: {{rejection_reason}}
```

Only expose the existing Admin rejection reason.

Do not expose internal logs, IDs, or unrelated Admin notes.

---

# 4. Re-approved after rejection

If the Admin later changes:

```text
rejected → approved
```

create a NEW approval notification:

```text
Job post approved

Your job post “{{job_title}}” has been approved and is now live.
```

Do not suppress this because the job may have been approved in the past.


# Correct duplicate protection

We still need protection against accidental duplicate notifications from the SAME status-change request.

Example:

Admin clicks Approve once.

The backend request is retried accidentally.

Do NOT generate:

```text
Job post approved
Job post approved
```

twice for one single transition.

The correct distinction is:

```text
same state transition request
→ prevent duplicate

future independent transition back into same status
→ create new notification
```

---

# Recommended implementation

Capture the old status BEFORE updating:

```ts
const previousStatus = job.approvalStatus;
```

Perform the update.

Then:

```ts
if (previousStatus !== newStatus) {
  await createJobApprovalStatusNotification({
    job,
    previousStatus,
    newStatus,
  });
}
```

The helper should map transitions/statuses to notification content.

For example:

```ts
function buildJobApprovalNotification(
  oldStatus: string,
  newStatus: string,
  jobTitle: string,
  rejectionReason?: string,
) {
  switch (newStatus) {
    case "approved":
      return {
        type: "job_approved",
        title: "Job post approved",
        message: `Your job post “${jobTitle}” has been approved and is now live.`,
      };

    case "pending":
      return {
        type: "job_pending",
        title: "Job post moved back to review",
        message: `Your job post “${jobTitle}” has been moved back to Pending Approval and is no longer publicly visible.`,
      };

    case "rejected":
      return {
        type: "job_rejected",
        title: "Job post rejected",
        message: rejectionReason
          ? `Your job post “${jobTitle}” was not approved. Reason: ${rejectionReason}`
          : `Your job post “${jobTitle}” was not approved.`,
      };
  }
}
```

Adapt this to the actual notification schema and supported type values.

Do not blindly add new enum values without checking the schema.

# Event identity / idempotency

If the notification architecture supports an event key/idempotency key, base it on the individual transition, not just the job.

For example:

```text
job:<jobId>:approval-transition:<oldStatus>:<newStatus>:<transitionTimestamp-or-eventId>
```

or preferably use the actual approval-history/status-change record ID if one exists.

Best case:

```text
job approval history record
        ↓
notification source_event_id = history.id
```

Then retries for the SAME history event are prevented, but a future:

```text
pending → approved
```

creates a different history/event ID and therefore another legitimate notification.

---

# Do not deduplicate using only these

Do NOT use only:

```text
jobId
type
userId
```

as the uniqueness key.

This would incorrectly suppress repeated legitimate approval transitions.

# Backend only

The notification must be created by the backend that performs the Admin status change.

Do not have the Admin frontend separately trigger a notification request.

Do not let the Client frontend infer job status changes and create notifications.

Required architecture:

```text
Admin action
   ↓
backend validates Admin
   ↓
backend loads job + old approval status
   ↓
backend changes status
   ↓
backend creates status-transition notification
   ↓
Client notification UI sees new record
```
