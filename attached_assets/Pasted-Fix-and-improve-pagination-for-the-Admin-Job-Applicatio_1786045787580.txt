Fix and improve pagination for the Admin Job Applications page:

```text
/admin/job-applications
```

The page must support hundreds or thousands of job applications without older applications disappearing.

## Current behavior

The page currently shows:

```text
TOTAL       20
SUBMITTED   20
```

and the URL contains:

```text
/admin/job-applications?limit=20
```

The current frontend uses:

```ts
const LIMIT = 20;
```

This is acceptable as a **page size only**.

It must NOT mean that the system can only contain or expose 20 applications.

The required behavior is:

```text
Maximum displayed per page = 20
Total applications = no artificial limit
```

If there are:

```text
1,000 applications
```

the page should show:

```text
TOTAL 1,000
```

and provide:

```text
50 pages
```

at 20 applications per page.

---

# Existing implementation

Inspect:

```text
client/src/pages/AdminJobApplications.tsx
```

The page already has:

```ts
const [page, setPage] = useState(...);
const LIMIT = 20;
```

and builds:

```ts
?page=${page}&limit=${LIMIT}
```

The response type is currently approximately:

```ts
interface ListResponse {
  items: Application[];
  total: number;
  page: number;
  limit: number;
}
```

It also calculates:

```ts
const totalPages = listData
  ? Math.ceil(listData.total / LIMIT)
  : 1;
```

Keep that pagination concept, but verify the backend is returning the **true filtered total before LIMIT/OFFSET**.

# 2. Count BEFORE pagination

The backend must calculate:

```text
total matching applications
```

before applying:

```text
LIMIT 20
OFFSET ...
```

Correct sequence:

```text
all applications
↓
apply search/filter conditions
↓
COUNT matching applications
↓
sort
↓
LIMIT/OFFSET
↓
return current page + total
```

Incorrect:

```text
all applications
↓
take first 20
↓
count those 20
↓
return total = 20
```

If using SQL, the logic should be equivalent to two queries.

Count query:

```sql
SELECT COUNT(*)
FROM job_applications
WHERE ...filters...;
```

Page query:

```sql
SELECT *
FROM job_applications
WHERE ...same filters...
ORDER BY submitted_at DESC, id DESC
LIMIT 20
OFFSET $offset;
```

For page 3:

```ts
offset = (3 - 1) * 20;
// 40
```

# 16. Important issue with the Job filter dropdown

Inspect this existing code path carefully.

The Job Applications page retrieves the Job dropdown options from:

```text
/api/admin/jobs
```

and currently extracts:

```ts
data.items
```

If `/api/admin/jobs` itself is paginated to 25 jobs, this dropdown may only contain the first 25 jobs.

That would cause the "All jobs" filter to be incomplete when there are 100+ posted jobs.

Fix this deliberately.

Do NOT assume:

```text
/api/admin/jobs
```

returns every job.

Either:

1. create/use a lightweight endpoint specifically for job-filter options that returns all required `{ id, title }` values, or
2. implement a searchable server-backed job selector, or
3. deliberately retrieve all job options through pagination.

Preferred scalable option:

```text
GET /api/admin/jobs/options?search=...
```

returning lightweight:

```json
[
  {
    "id": "...",
    "title": "Virtual Assistant"
  }
]
```

Do not load full job objects merely to populate the filter.
