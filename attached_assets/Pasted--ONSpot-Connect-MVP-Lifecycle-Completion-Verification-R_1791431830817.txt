# ONSpot Connect — MVP Lifecycle Completion, Verification & Release Readiness

## Project

Repository: `itonspotglobal-collab/connect-onspot`

Goal: Complete and verify the ONSpot Connect MVP so that real Clients and Talents can complete the full workforce lifecycle, from onboarding and hiring through time tracking, invoicing, and formal engagement termination.

**IMPORTANT: Inspect the current repository before changing anything. Several issues from previous audits have already been addressed. Do not blindly reimplement existing features.**

Work against the latest available source and identify the current commit SHA before starting.

## Non-negotiable requirements

1. Preserve all existing working features and business logic.
2. Reuse existing APIs, components, database tables, and services.
3. Do not introduce duplicate implementations or parallel workflows.
4. Do not replace real functionality with mocked, simulated, or hardcoded results.
5. Do not modify historical financial records or production user data.
6. Do not introduce new payment-provider integrations.
7. Never expose production secrets or credentials.
8. Use the existing authentication and role authorization patterns.
9. Implement only confirmed missing or defective functionality.
10. Run relevant automated tests and report results.
11. Do not claim production functionality is verified without actually testing it.
12. Do not deploy automatically.

# PRIORITY 1 — Complete and verify contract termination lifecycle

## Current implementation

Inspect:

- `client/src/App.tsx`
- `client/src/pages/ContractEndings.tsx`
- `server/routes/contractTerminations.ts`
- Existing termination-related tests
- Related invoice, timesheet, and billing services

The current source already appears to mount:

- `/client/contract-endings`
- `/talent/contract-endings`

It also contains backend termination request, approval, rejection, effective end-date, and invoice-rebuild logic.

## Required work

Verify the entire workflow for both Client and Talent.

### Client workflow

A Client must be able to:

1. Open Contract End Requests from Client navigation.
2. View their eligible active signed contracts.
3. Select a contract.
4. Specify an effective termination date.
5. Enter a termination reason.
6. Submit a request.
7. See a clear success confirmation.
8. Review pending, approved, and rejected requests.
9. See the approved effective end date.

### Talent workflow

A Talent must be able to complete the equivalent process for their own eligible contracts.

### Admin workflow

An authorized Admin must be able to:

1. View pending termination requests.
2. Review the contract, requester, proposed date, and reason.
3. Approve or reject a request.
4. Record the decision and reason.
5. See the resulting contract state.

### Billing integrity

Verify that approval:

- Updates the correct `hiring_contracts` record.
- Preserves approved effective end dates.
- Correctly recalculates eligible draft invoices.
- Applies existing proration rules for Guaranteed contracts.
- Respects Tracked contract timesheet boundaries.
- Does not alter locked or sent financial records improperly.
- Prevents duplicate termination requests.
- Rejects invalid or backdated dates.
- Prevents further billable activity outside the approved engagement period.

Do not rewrite established termination calculations unless a failing test demonstrates a defect.

## Acceptance criteria

Client and Talent can request termination, Admin can decide the request, and the resulting contract, timesheet, and billing states remain consistent.

- OUT OF SCOPE — intentionally excluded from MVP

## Phase B — Targeted implementation

Fix only confirmed code defects.

For each fix:

1. Explain the root cause.
2. Identify the affected files.
3. Implement the smallest safe change.
4. Add or update regression tests.
5. Run relevant tests.

## Phase C — End-to-end verification

Verify the full lifecycle:

Talent onboarding → Job application → Interview → Offer → Signed contract → Clock-in/out → Timesheet → Invoice → Contract termination → Final billing.

Distinguish automated test evidence from authenticated staging UAT.

## Phase D — Final report

Provide a comprehensive but concise MVP readiness report containing:

1. Current commit SHA.
2. Issues already fixed before this task.
3. Issues discovered during this task.
4. Exact files changed and why.
5. Tests executed and results.
6. Features verified end to end.
7. Features requiring manual UAT.
8. External configuration blockers.
9. Remaining MVP blockers.
10. Final MVP readiness assessment.

Use these statuses:

- PASS

## Definition of done

The MVP is functionally ready when:

- Clients and Talents can formally request engagement termination.
- Admin can process termination requests.
- Contract-ending billing rules work correctly.
- Client engagement dashboards accurately reflect modern activity.
- Talent onboarding and uploads persist correctly.
- No fake LinkedIn or assessment data can be presented as real.
- Primary Client navigation has no dead links.
- Critical email and storage dependencies are verified or explicitly identified as release blockers.
- Existing working hiring, timesheet, invoicing, and payment-ledger functionality remains intact.

**Start with Phase A. Present the audit findings before making code changes. After the audit, proceed only with confirmed code fixes and their tests. Do not deploy or modify production data.**
