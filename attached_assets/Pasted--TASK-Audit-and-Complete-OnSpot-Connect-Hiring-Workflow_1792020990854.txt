# TASK: Audit and Complete OnSpot Connect Hiring Workflow — Mandatory Pre-Offer Invoice Payment

## PROJECT
Repository: `itonspotglobal-collab/connect-onspot`

Implement the missing **Pre-Offer Invoice and Payment Verification** process into the existing Client-to-Talent hiring pipeline.

**IMPORTANT: This is an existing production-oriented application. Do not rebuild the hiring pipeline, introduce duplicate application records, replace existing contract services, or break currently functioning processes.**

First perform a thorough audit of the current implementation. Reuse existing functionality wherever possible and implement only missing requirements.

Do not modify the Talent OnSpot Vetting Quiz module. It is still under development.

## 1. REQUIRED BUSINESS WORKFLOW

The intended process is:

1. Client creates a job posting.
2. Admin reviews and approves the job.
3. The approved job becomes available for talent applications or Client invitations.
4. Talent applies or accepts an invitation.
5. Client reviews the talent application.
6. Client shortlists the talent.
7. Client conducts an interview.
8. Client decides the talent is **Ready for Offer**.
9. System generates a pre-offer hiring invoice for that Client and selected Talent/application.
10. Client receives an invoice notification and payment instructions.
11. Client pays the invoice.
12. The payment is verified and the invoice becomes `paid`.
13. Only after verified payment may the Client send the formal offer.
14. Talent reviews, accepts, declines, or counteroffers according to the existing workflow.
15. After an accepted offer, authorized parties prepare and send the hiring contract.
16. Talent and all required Client/Organization/OnSpot representatives sign the contract.
17. Only after all required signatures are complete does the system mark the Talent as `Hired`.
18. The existing hired-talent, deposit, timesheet, invoice, payout, and team workflows continue unchanged.

**Critical rule: A Client cannot create or send a formal hiring offer unless the corresponding pre-offer hiring invoice has been verified as paid.**

The invoice must be paid **before offer creation**, not merely before contract signing.

## 3. READY FOR OFFER ACTION

Introduce a **Ready for Offer** action within the existing Client hiring pipeline, where eligible.

When selected:

1. Validate Client ownership of the original application.
2. Verify the application is eligible under the existing formal hiring guards.
3. Reuse the existing interview and stage eligibility rules; do not introduce a new mandatory interview where the system currently allows a legitimate direct offer.
4. Record that the Client intends to proceed with an offer.
5. Initialize the pre-offer invoice process.
6. Do not send an offer yet.

The action must be idempotent. Repeated clicks must not generate duplicate active invoices.

If the selected Talent already has a valid paid pre-offer invoice for the same eligible hiring attempt, reuse that payment authorization rather than charging twice.

## 4. PRE-OFFER INVOICE CREATION

Implement a clearly distinguished `hiring_pre_offer` invoice type or a dedicated pre-offer invoice entity, whichever fits the existing schema safely.

Associate each invoice with:

- Original `job_submissions.id`
- Job ID
- Client ID
- Talent ID
- Invoice number
- Fee description
- Amount and currency
- Invoice status
- Issue date and due date
- Payment method
- Payment reference
- Verified payment timestamp
- Verifying Admin or payment provider identity
- Created/updated timestamps

Do not hardcode the invoice amount.

The invoice amount, currency, fee basis, tax treatment, and due date must come from an explicitly configured and authorized billing policy. If the required pricing is not configured, prevent invoice issuance with a clear message rather than defaulting to zero or inventing a charge.

Preserve the existing offer economic snapshots, commission calculations, and recurring billing architecture.

**Do not confuse this pre-offer invoice with monthly Client invoices, Talent invoices, or security deposits.**

Existing sent financial records must not be rewritten.

## 5. PAYMENT AND VERIFICATION

Reuse existing payment instructions and invoice presentation where appropriate.

Support the currently available payment methods without assuming a fully integrated payment gateway exists.

For manual payment:

1. Client receives invoice and payment instructions.
2. Client may submit payment reference or proof for review.
3. Invoice becomes `verification_pending`.
4. An authorized Admin verifies the actual payment.
5. Admin records an audit trail and marks the invoice `paid`.
6. Only then is the offer unlocked.

For payment gateway integration, if a real existing verified integration is available:

- Verify provider signatures and payment transaction state server-side.
- Match amount, currency, recipient, and invoice identity.
- Make webhook handling idempotent.
- Never accept the Client's frontend declaration as proof of payment.

A submitted screenshot, external transaction ID, or success URL is not sufficient to mark an invoice paid.

Use explicit invoice statuses such as:

`draft`, `issued`, `verification_pending`, `paid`, `overdue`, `void`, and `payment_failed` where applicable.

Use additive schema changes and preserve historical billing data.

## 6. MANDATORY OFFER PAYMENT GUARD

This is the most important part.

Update all relevant backend offer creation and sending paths to require a verified paid pre-offer invoice for the original submission.

The guard must check:

- Correct Client
- Correct job
- Correct Talent
- Correct original application/submission
- Correct invoice type
- Correct hiring attempt
- Paid status
- Verified amount and currency
- Invoice not voided, refunded, invalidated, or otherwise ineligible

If payment is missing:

Return a clear `409` conflict with an appropriate error code such as:

`PRE_OFFER_PAYMENT_REQUIRED`

Do not rely solely on frontend button disabling.

The rule must apply to regular Client offers and any Admin-assisted route capable of creating a Client hiring offer. Admins must not bypass the payment requirement simply because they have elevated privileges.

Retain existing authorization, offer expiry, duplicate-offer prevention, and Talent response rules.

If an already-paid invoice is later refunded, do not silently remove or rewrite an already accepted offer or signed contract. Record the financial exception for authorized review.

Handle concurrent requests with appropriate transactions and database constraints so multiple offers or invoices cannot be incorrectly created.
