# Fix Find Work Category Filtering by Aligning It With Job Function

You are working inside the existing **OnSpot Global / connect-onspot** codebase.

Investigate and fix the mismatch between:

* **Function** in Admin Create/Edit Job
* **Category** filters on `/find-work/jobs`

The Admin job form currently calls this field:

**Function**

while the public Find Work page calls the same taxonomy:

**Category**

This is confusing and may also be contributing to the current filtering bug.

Do not add a second Admin field.

The intended model should be:

```text
Admin: Function
        ↓
canonical jobFunction
        ↓
Find Work: Category filter
```

In other words:

**Function is the underlying job classification.**

The public Find Work page may continue to label it **Category** for UX purposes.

---

# Current Important Finding

Inspect:

`client/src/pages/JobFormPage.tsx`

The current Admin job payload already does:

```ts
jobFunction: formData.jobFunction.trim(),
category: formData.jobFunction.trim(),
```

Therefore, new jobs created through the current Admin form should normally save the selected Function into both fields.

Do NOT remove this behavior until the backend/data model has been reviewed.

The problem is more likely that:

1. legacy jobs do not have both fields populated consistently, OR
2. `/api/jobs/search` filters only `category`, OR
3. stored values use older variations, OR
4. the filter taxonomy and saved Function taxonomy have drifted apart.

---

# 2. Keep `category` for Backward Compatibility

Do NOT immediately delete the existing:

```ts
category
```

database field.

It may still be used by:

* legacy jobs
* APIs
* old components
* imports
* recommendation logic

For now:

```text
jobFunction = canonical
category = compatibility mirror / fallback
```

New and edited jobs should continue saving both:

```ts
jobFunction: selectedFunction,

```

until a separate migration removes the redundancy.

---

# 3. Fix `/api/jobs/search`

The public Find Work category filter must match against BOTH:

```ts
job.jobFunction
```

and:

```ts
job.category
```

Do not filter only against `category`.

Conceptually:

```ts
const selectedCategory = normalizeFilterValue(req.query.category);

const match =
  normalizeFilterValue(job.jobFunction) === selectedCategory ||
  normalizeFilterValue(job.category) === selectedCategory;
```

If the backend uses SQL/Drizzle, implement the equivalent OR condition there.

Example conceptually:

```ts
or(
  ilike(jobs.jobFunction, selectedCategory),
  ilike(jobs.category, selectedCategory)
)
```

Use actual schema field names and parameterized queries.

---

# 4. Normalize Before Comparing

Do not depend on exact formatting.

Add/reuse:

```ts
function normalizeJobFunction(value?: string | null): string {
  return (value ?? "")
    .trim()
    .toLowerCase()
    .replace(/&/g, "and")
    .replace(/[^a-z0-9]+/g, " ")
    .replace(/\s+/g, " ")
    .trim();
}
```

This should make values such as:

```text
Finance & Accounting
Finance and Accounting
finance-accounting
```

comparable.

Do not mutate stored database values.

Normalize only during matching.

# 6. Backfill Legacy Jobs

If database inspection confirms records such as:

```text
jobFunction = "Customer Support"
category = null
```

or:

```text
jobFunction = "Information Technology (IT)"
category = "Other"
```

create a safe migration/backfill.

Preferred rule:

```text
If jobFunction is non-empty:
    use jobFunction as the canonical category mirror
```

Potential SQL concept:

```sql
UPDATE jobs
SET category = job_function
WHERE job_function IS NOT NULL
  AND TRIM(job_function) <> ''
  AND (
    category IS NULL
    OR TRIM(category) = ''
  );
```

Do not overwrite meaningful old category data blindly unless the taxonomy migration is intentional.

Backend fallback must still remain even after a backfill.

The Admin screen should remain simple.

# 9. Optional Public Label Rename

It is acceptable to keep the public filter heading:

**CATEGORY**

because that is understandable to job seekers.

But internally the selected value should represent:

```text
jobFunction
```

If you want to make terminology completely consistent, changing the public label to:

**JOB FUNCTION**

is also acceptable, but this is optional.

Do not make the filter bug dependent on a cosmetic rename.

---

# 10. Filter Query Naming

For minimal regression risk, it is okay for the frontend to continue sending:

```text
?category=Customer Support
```

as long as the backend interprets that as:

> filter by job classification/function

and checks both fields.

Alternatively, a future cleanup could rename it to:

```text
?jobFunction=Customer Support
```

but do NOT perform a broad API rename unless all callers are updated.

For this task, backward compatibility is preferred.

---

# 11. Group Navigation Filters

The existing Find Work page also uses grouped navigation mappings such as:

```text
Development & IT
```

that may map to multiple functions.

Those should match against `jobFunction` as well.

Example:

```text
Development & IT
→ Engineering
OR Information Technology (IT)
```

Do not make grouped filters depend only on the old category column.

---

# 12. Search Query Logic

When category/function filtering is active:

```text
selected Function
AND
other filters
```

must apply.

Example:

```text
Function = Customer Support
Location = Remote
Contract = Full Time
```

must return jobs matching all three.

Do not OR unrelated filters together.

---

# 13. Filter Before Pagination

Apply jobFunction/category filtering before:

```text
LIMIT
OFFSET
```

Then calculate:

```text
meta.total
meta.totalPages
```

from the filtered query.

Otherwise the page may incorrectly show zero matches.
