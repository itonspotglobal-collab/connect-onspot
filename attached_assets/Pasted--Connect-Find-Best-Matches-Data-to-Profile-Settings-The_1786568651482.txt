# Connect Find Best Matches Data to Profile Settings

The redirect issue is now fixed and Talent Profile is accessible.

The next issue is synchronization between:

- Find Best Matches
- Talent Profile Settings
- Talent Profile

Find Best Matches already collects a lot of Talent information during onboarding. That data must populate the matching fields in Profile Settings automatically.

Do NOT create a second copy of the data in frontend state.

The Candidate database record must remain the single source of truth.

==================================================
GOAL
==================================================

After a Talent completes or partially completes Find Best Matches:

Find Best Matches
    ↓
Candidate DB
    ↓
Profile Settings
    ↓
Talent Profile

Profile Settings should automatically show the same saved information.

If the user later updates the information in Profile Settings:

Profile Settings
    ↓
Candidate DB
    ↓
Find Best Matches / Talent Profile

All three views must stay synchronized.

==================================================
CURRENT PROBLEM
==================================================

Find Best Matches has already gathered fields such as:

- Full Name
- Email
- Phone Number
- Location
- Target Job Position
- Job Category
- Years of Experience
- Seniority
- Core Skills
- Secondary Skills
- Summary
- Resume
- Preferences

But Profile Settings still shows empty/default fields, for example:

Basic Information:
- Profile Photo empty
- First Name partly populated
- Last Name
- Phone
- Location placeholder
- Languages empty

Professional Details:
- Professional Title empty
- Bio empty
- hourly rate default

Skills & Expertise:
- no skills selected

Documents:
- Resume appears missing

This means either:

1. Find Best Matches is not persisting all these values to the Candidate row/document store, OR
2. Profile Settings is not mapping persisted Candidate fields into its form correctly.

Investigate both.

==================================================
1. USE ONE CANONICAL CANDIDATE RECORD
==================================================

Inspect:

client/src/pages/FindBestMatches.tsx
client/src/pages/ProfileSettings.tsx
client/src/hooks/useCandidateProfileSettings.ts
client/src/pages/TalentProfile.tsx
client/src/lib/profileCompletion.ts
server/routes.ts
server/storage.ts
shared/schema.ts

Verify that both Find Best Matches and Profile Settings resolve the SAME:

candidateId

and read/write the SAME Candidate DB row.

Do not allow:

Find Best Matches -> Candidate A
Settings -> legacy Profile row

or:

Find Best Matches -> local/session state
Settings -> Candidate DB

Everything reusable must converge on Candidate.

==================================================
2. CREATE AN EXPLICIT FIELD MAPPING
==================================================

Define one mapping between Find Best Matches fields and Profile Settings fields.

Use the actual schema names, but conceptually:

Find Best Matches                 Candidate / Settings
-------------------------------------------------------
Full Name                      -> firstName + lastName / fullName
Email                          -> email
Phone Number                   -> phone
Location                       -> location
Target Job Position            -> targetPosition / Professional Title
Job Category                   -> jobCategory
Years of Experience            -> yearsOfExperience
Seniority                      -> seniority
Core Skills                    -> coreSkills
Secondary Skills               -> secondarySkills
Summary                        -> summary / Professional Bio
Resume                         -> persisted resume document
Preferences                    -> preferences
Work Setup                     -> preferences.workSetup
Availability                   -> availability if applicable

Do not let each page invent its own translation.

Create a shared helper if useful, for example:

candidateToProfileSettingsForm(candidate, documents)

and:

findBestMatchesToCandidatePayload(profile)

Expected mapping:

First Name
<- candidate.firstName

Last Name
<- candidate.lastName

Phone Number
<- candidate.phone

Location
<- candidate.location

Languages
<- candidate.languages OR candidate.preferences.languages

Timezone
<- candidate.timezone OR candidate.preferences.timezone
depending on actual schema

Do NOT re-split fullName if firstName and lastName already exist.

Fallback parsing is only for old Candidate rows.

==================================================
5. SKILLS & EXPERTISE MAPPING
==================================================

Find Best Matches already gathers:

coreSkills
secondarySkills

Profile Settings Skills & Expertise must use these same Candidate fields.

Do not use a disconnected legacy:

Recommended behavior:

Settings selected skills =
unique combination of:
- coreSkills
- secondarySkills

When Settings saves skill changes:

update Candidate coreSkills / secondarySkills using the same model used by Talent Profile.

Do not allow:

JavaScript, React, Data Entry

while Settings says:

No skills selected yet.

==================================================
6. DOCUMENTS — RESUME MUST BE SHARED
==================================================

This is especially important.

If Resume was uploaded in Find Best Matches:

Profile Settings -> Documents

must recognize the same persisted Resume.

Do NOT require another upload.

The Documents section should show something like:

Resume / CV

✓ Frenzy_Legaspi_Resume.pdf

[View]
[Replace]
[Remove]

instead of:

Upload Resume

when a resume already exists.

Video Introduction is NOT part of Find Best Matches, so it can remain empty unless the user uploaded one elsewhere.

Do not try to hydrate a file input with a remote file.

Use persisted document metadata:

{
  id,
  fileName,
  fileUrl,
  uploadedAt
}

7. FIND BEST MATCHES MUST ACTUALLY SAVE ALL REUSABLE FIELDS
==================================================

Audit every Find Best Matches step.

Do not only persist data at the final screen if intermediate data is reusable.

When the Talent confirms profile information, save it to Candidate.

Example fields:

phone
location
targetPosition
jobCategory
yearsOfExperience
seniority
coreSkills

summary

At final completion, save any remaining values and set:

Do not leave reusable fields only in local React state.

==================================================
8. SETTINGS MUST HYDRATE FROM CANDIDATE ON MOUNT
==================================================

When /settings loads:

1. resolve authenticated Candidate
2. fetch Candidate
3. fetch persisted Candidate documents
4. map Candidate into Settings form
5. only then render populated values

Avoid this sequence:

render defaults
-> overwrite with auth user
-> never apply Candidate

Prefer:

Candidate data
-> Settings form defaults

==================================================
9. DO NOT OVERWRITE USER EDITS DURING ASYNC LOAD
==================================================

If the Candidate fetch completes after the user has already started typing:

do not overwrite fields they manually changed.

Use a hydration guard such as:

hasHydratedRef

or initialize/reset the form once when Candidate data becomes available.

Example:

useEffect(() => {
  if (!candidate || hasHydrated.current) return;

  form.reset(
    candidateToProfileSettingsForm(candidate, documents)
  );

  hasHydrated.current = true;
}, [candidate, documents]);

Adapt to the actual form library.

12. LANGUAGE HANDLING
==================================================

Find Best Matches may not currently collect Languages.

If not, leave Settings Languages independent.

But if Candidate already has languages persisted:

Settings must populate them.

Do not erase existing Languages when Find Best Matches saves other fields.

All Candidate PATCH operations must merge safely.

Example:

existing.preferences = {
  languages: ["English"],
  timezone: "Asia/Manila",
  workSetup: "remote"
}

Find Best Matches updates workSetup.

Do NOT replace preferences with:

{
  workSetup: "remote"
}

and lose languages/timezone.

Merge nested preferences safely.
