Fix the existing Client-facing talent name privacy masking.

This issue has been attempted multiple times but is still incorrect.

DO NOT patch only the frontend display.

DO NOT infer surname initials from the second word in `fullName`.

The required privacy rule is:

```text
FIRST GIVEN NAME + LAST NAME INITIAL
```

Examples:

```text
John Benedict Acosta
→ John A.

Aaron Tristan Dela Cruz
→ Aaron D.

Julie Santos
→ Julie S.
```

The middle/given names after the first given name must NOT be displayed.

For the screenshot examples:

```text
John Benedict A.
```

must become:

```text
John A.
```

and:

```text
Aaron Tristan D.
```

must become:

```text
Aaron D.
```

---

# Current root problem

Inspect:

```text
server/lib/clientSearchSanitize.ts
```

The current sanitizer derives the masked name from:

```ts
const rawName = candidate.fullName ?? candidate.full_name;
const parts = rawName.split(/\s+/);
```

and currently uses logic based on:

```ts
parts[0]
parts[1]
```

This is NOT a reliable way to identify a surname.

A person's second token may be a middle/given name.

Example:

```text
John Benedict Acosta
```

Using `parts[1]` produces:

```text
John B.
```

which is incorrect.

The desired value is:

```text
John A.
```

Fix the masking in:

Do not rely on React components to hide extra names after the API response has already exposed them.

Important:



# Handle last names with prefixes correctly

Do not strip legitimate surname prefixes.

Examples:

```text
lastName = "Dela Cruz"
→ D.

lastName = "De Leon"
→ D.

lastName = "Van Dyke"
→ V.

lastName = "O'Brien"
→ O.

lastName = "Santos-Reyes"
→ S.
```

Use the first visible alphabetic character of the stored surname.

Do NOT take the final word of a multi-word surname if a structured lastName field already exists.

# Full-name fallback only when structured fields are unavailable

Some legacy records may have only:

```text
fullName
```

or:

```text
full_name
```

Do not break these records.

If structured `firstName` and `lastName` are genuinely unavailable, implement a conservative fallback.

Before deciding the fallback, inspect how legacy `fullName` is constructed in this project.

Do NOT blindly assume:

```ts
parts[parts.length - 1]
```

is always correct if existing values may already be masked, for example:

```text
John Benedict A.
```

or:

```text
Aaron Tristan D.
```

If the input is already in a masked form ending with a one-letter surname initial:

```text
John Benedict A.
```

the normalized output should become:

```text
John A.
```

Example fallback handling:

```text
"John Benedict A."
→ first visible given name = John
→ existing surname initial = A
→ "John A."
```

```text
"Aaron Tristan D."
→ "Aaron D."
```

```text
"Julie S."
→ "Julie S."
```

If input is a full unmasked name:

```text
"John Benedict Acosta"
```

and no structured fields exist, the legacy fallback may use:

```text
first token + last token initial
```

which yields:

```text
John A.
```

But prefer structured fields whenever available.

# Create ONE shared masking helper

Do not duplicate this logic between:

```ts
sanitizeSearchCandidate
sanitizeFullProfileForClient
```

Create one helper, for example:

```ts
function maskClientTalentName(candidate: Record<string, any>): string
```

Then use it from both sanitizers.

Example structure:

```ts
function maskClientTalentName(candidate: Record<string, any>): string {
  // 1. structured first/last name
  // 2. legacy already-masked name
  // 3. legacy full-name fallback
  // 4. single-name fallback
}
```

This prevents the two endpoints from displaying different names.
