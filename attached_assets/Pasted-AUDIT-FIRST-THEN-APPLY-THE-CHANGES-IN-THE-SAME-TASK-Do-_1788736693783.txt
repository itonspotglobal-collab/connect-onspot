# TEST SCENARIO

Current scenario:

1. Client invites Talent to a role.
2. Client also proposes an interview time.
3. Talent sees:

   * Role Invitation
   * Interview proposal
4. Talent accepts the Role Invitation.
5. Talent may accept the proposed interview time or suggest another time.

Current problems:

CLIENT SIDE

1. Client receives NO notification when Talent accepts the Role Invitation.
2. There is no detailed popup/modal when Client clicks that acceptance notification.
3. Client receives NO notification when Talent proposes/reschedules the interview.
4. Client needs one clear popup/modal showing:

   * Talent accepted the Role Invitation
   * current interview schedule/status
   * latest proposed/confirmed time

TALENT SIDE

5. The Interview section is currently visible before the Talent has accepted the Role Invitation.

The Interview section should only become visible/actionable AFTER the Talent accepts the Role Invitation.

# PHASE 2 — IMPLEMENT AFTER AUDIT

After the audit, implement the following.

# A. CLIENT NOTIFICATION — TALENT ACCEPTED ROLE INVITATION

When Talent successfully accepts a Client Role Invitation:

Create a Client notification.

Suggested notification type:

Use an existing canonical invitation notification type if one already exists.

If none exists, add a focused type such as:

`talent_invitation_accepted`

Do not use notification title text as the only event identity.

Recipient:

The Client who owns the job/invitation.

Resolve through the existing relationship:

invitation/submission
→ job
→ jobs.client_id
→ Client user

Do not infer Client by company name.

Suggested title:

`Talent accepted your invitation`

Suggested message:

`{{talent_name}} accepted your invitation for {{job_title}}.`

If there is already an interview proposal associated with that invitation, it is fine for the notification metadata to include the interview ID/submission ID so the popup can load current schedule information.

Use the existing notification event-key/idempotency mechanism.

Conceptual event key:

`talent-invitation-accepted:{submissionId}`

or use the existing canonical event-key pattern.

Exactly one acceptance notification per actual acceptance transition.

Repeated API retries must not duplicate it.

# B. CLIENT NOTIFICATION — TALENT RESCHEDULED / PROPOSED ANOTHER INTERVIEW TIME

When Talent uses:

`Suggest another time`

or otherwise creates a Talent counter-proposal/reschedule:

Create a Client notification.

Use existing interview proposal history.

Suggested notification type:

Reuse an existing interview-rescheduled / proposal notification type if available.

Otherwise add a focused canonical type such as:

`interview_reschedule_proposed`

Suggested title:

`Talent proposed a new interview time`

Suggested message:

`{{talent_name}} proposed a new interview time for {{job_title}}.`

Notification metadata should contain enough trusted identifiers to load:

* interviewId
* submissionId
* jobId if already available

Do NOT embed the entire schedule as authoritative notification text if the popup can load the current interview record.

Use event-key/idempotency.

Each genuinely new proposal may generate one notification.

Do not suppress later legitimate counter-proposals merely because an earlier one already notified the Client.

The event key should identify the proposal, for example conceptually:

`interview-proposal:{proposalId}`

Preferred V1:
