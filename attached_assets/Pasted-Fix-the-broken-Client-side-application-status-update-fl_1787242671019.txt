# IMPORTANT ARCHITECTURE RULE

The Client status workflow and Admin status+email workflow are NOT the same flow.

They must remain separate.

## Client flow

Client selects status:

```text

→ status history created
→ Talent notification created
→ Admin notification created
```

* ApplicantEmailComposer
* Admin email templates
* status pending state
* Admin-only email workflow

## Admin flow

Admin:

```text
select status
→ compose/send email
→ only after email succeeds
→ status changes
→ Talent notified
```

Do not accidentally reuse the Admin endpoint/helper in the Client route.

# IMPORTANT TRANSACTION DESIGN

The DB-critical operations are:

* application status
* status history

Notification creation can remain in the same transaction if the notification writes are reliable and all required recipients exist.

However, do not allow optional recipient-resolution joins to make the core update fail.

A safe pattern is:

```text
BEGIN

lock submission row
authorize
validate transition
update status
insert history

resolve notification recipients safely
insert valid notifications

COMMIT
```

If notification lookup itself is complex/nullable, resolve it before or after the locked query without invalid SQL.
