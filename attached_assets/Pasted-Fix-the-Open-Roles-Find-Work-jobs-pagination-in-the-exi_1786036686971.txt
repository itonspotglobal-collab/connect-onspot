Fix the Open Roles / Find Work jobs pagination in the existing project.

### Current issue

The application can have more than 25 open job roles, but the Find Work / Open Roles page only displays the first 25.

Example:

* 50 roles are posted and open.
* Only 25 appear on the page.
* If 10 of the visible roles are deleted, some previously hidden roles become visible.
* This indicates that the API is paginated with a default page size of 25, but the frontend is only loading page 1.

The project already has pagination utilities in:

`server/lib/paginate.ts`

The existing pagination response contains:

```ts
{
  items: Job[],
  meta: {
    page: number,
    pageSize: number,
    total: number,
    totalPages: number
  }
}
```

The default page size is already:

```ts
DEFAULT_PAGE_SIZE = 25
```

Do NOT increase the page size to 50, 100, or 200 just to show all records.

Instead, implement proper pagination.

### Required behavior

Display a maximum of **25 job roles per page**.

Examples:

* 1–25 jobs → Page 1 only
* 26–50 jobs → Page 1 and Page 2
* 51–75 jobs → Page 1, Page 2, Page 3
* 76–100 jobs → 4 pages

For 50 open roles:

**Page 1**
Jobs 1–25

**Page 2**
Jobs 26–50

All open roles must remain accessible. Do not hide, truncate, or discard roles after the first 25.

### API usage

Update the frontend request to use:

```text
/api/jobs/search?status=open&page={currentPage}&pageSize=25
```

For example:

```text
/api/jobs/search?status=open&page=1&pageSize=25
/api/jobs/search?status=open&page=2&pageSize=25
```

Use the API's existing `meta.totalPages`, `meta.total`, `meta.page`, and `meta.pageSize` values rather than calculating the total number of server pages from only the returned 25 records.

### FindWorkAllJobs.tsx

Update:

`client/src/pages/FindWorkAllJobs.tsx`

Currently the page calls approximately:

```ts
fetch("/api/jobs/search?status=open")
```

and extracts:

```ts
data.items
```

Change this so the component keeps a `currentPage` state:

```ts
const [currentPage, setCurrentPage] = useState(1);
const PAGE_SIZE = 25;
```

Include the page in the React Query key:

```ts
queryKey: [
  "/api/jobs/search",
  {
    status: "open",
    page: currentPage,
    pageSize: PAGE_SIZE,
  },
]
```

Fetch:

```ts
/api/jobs/search?status=open&page=${currentPage}&pageSize=${PAGE_SIZE}
```

Keep the complete response instead of throwing away `meta`.

Use a type similar to:

```ts
interface PaginatedJobsResponse {
  items: Job[];
  meta: {
    page: number;
    pageSize: number;
    total: number;
    totalPages: number;
  };
}
```

Then obtain:

```ts
const openJobs = data?.items ?? [];
const totalPages = data?.meta?.totalPages ?? 1;
const totalJobs = data?.meta?.total ?? 0;
```

### Pagination UI

At the bottom of the job results, add pagination controls consistent with the existing UI/design system.

Example:

```text
← Previous    1  2  3  4    Next →
```

Requirements:

* Disable Previous on page 1.
* Disable Next on the last page.
* Highlight the active page.
* Clicking a page number loads that page.
* Clicking Previous loads `currentPage - 1`.
* Clicking Next loads `currentPage + 1`.
* Scroll back to the jobs results section after changing pages.
* Keep the existing responsive/mobile styling.
* Do not perform a full browser refresh.

For many pages, do not render dozens of buttons. Use a compact pagination such as:

```text
1 2 3 ... 10
```

or

```text
1 ... 4 5 6 ... 10
```

### Filtering and searching

Be careful with the existing filters in `FindWorkAllJobs.tsx`.

The page currently performs search, category, location, contract type, salary, and sorting on the jobs returned by the API.

Do NOT create behavior where filtering only searches the current 25 jobs if the expected behavior is to search/filter all open jobs.

Inspect the existing `/api/jobs/search` endpoint and move applicable filters to query parameters/server-side filtering before pagination where possible.

Correct sequence should be:

```text
all open jobs
      ↓
search/filter
      ↓
sort
      ↓
calculate total
      ↓
paginate into groups of 25
      ↓
return requested page
```

NOT:

```text
all open jobs
      ↓
take first 25
      ↓
filter those 25
```

This is important so a role on page 2 can still be found by search/filtering.

Whenever search or filter values change, reset:

```ts
setCurrentPage(1);
```

### URL state

Prefer keeping the current page in the URL so pagination survives refresh/back-navigation.

Example:

```text
/find-work/jobs?page=1
/find-work/jobs?page=2
```

Preserve existing query parameters such as:

```text
?category=design
```

so the result can become:

```text
/find-work/jobs?category=design&page=2
```

Do not overwrite or remove the existing category parameter when the page changes.

### Edge cases

Handle these cases:

1. Exactly 25 jobs

   * only Page 1.

2. 26 jobs

   * Page 1 has 25.
   * Page 2 has 1.

3. 50 jobs

   * exactly two pages.

4. 51 jobs

   * three pages.

5. A job is deleted while the user is on the last page.

   * If the current page becomes greater than `totalPages`, automatically move to the new last valid page.

6. New roles are posted.

   * They should become available according to the existing sorting order without replacing/hiding older records permanently.

7. Zero jobs

   * Preserve the existing empty-state UI.

8. Loading a different page

   * Preserve the current layout and preferably retain previous page data while fetching to prevent layout flashing.
