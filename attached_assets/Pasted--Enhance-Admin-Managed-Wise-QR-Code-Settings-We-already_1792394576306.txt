# Enhance Admin-Managed Wise QR Code Settings

We already implemented a manual Wise payment system in OnSpot, including QR code configuration, receipt submission, and Super Admin verification.

I want authorized admins to be able to change or replace the Wise QR code anytime through the Admin Dashboard, without modifying code or redeploying the application.

Please enhance the existing **Admin Ledger → Manual Wise payments** functionality.

## Requirements

### 1. Admin QR management

Provide an intuitive interface where authorized administrators can:

- View the currently active Wise QR code.
- Upload a new QR code (PNG, JPG, or WebP).
- Preview the new QR before saving.
- Replace the existing QR code.
- Edit the recipient name, payment instructions, and supported currencies.
- Save changes as a draft.
- Activate the new QR configuration after confirming its receiving details.
- View previous QR configurations.
- Restore a previous configuration when necessary.

Reuse the existing configuration tables, storage, and endpoints where possible. Do not build a duplicate payment settings system.

### 2. Safe activation

Uploading a new QR code must not automatically make it active.

Require an authorized Super Admin to:

1. Review the uploaded QR image.
2. Confirm the correct Wise receiving account.
3. Confirm supported currencies.
4. Review the payment instructions.
5. Explicitly activate the configuration.

Keep the existing active QR available until the replacement is successfully activated.

If the active configuration is invalid or revoked, allow an authorized Super Admin to deactivate it immediately.

### 3. Version history and audit trail

Maintain a history containing:

- QR image reference
- Recipient name
- Supported currencies
- Payment instructions
- Uploaded by
- Uploaded date
- Activated by
- Activation date
- Previous version
- Deactivation or replacement reason

Do not overwrite or delete historical configurations referenced by issued invoices or payment submissions.

Restoring a previous configuration must create a new reviewed activation event rather than silently changing historical records.

### 4. Customer payment screens

All incoming payment screens must automatically use the correct active QR configuration.

This includes:

- Inquiry payments
- Pre-offer hiring fees
- Client invoices
- Monthly billing statements
- Security deposits
- Deposit top-ups

Do not display the collection QR code for outgoing talent payouts.

When an admin activates a new QR configuration:

- New eligible payment instructions should use the new configuration.
- Existing issued invoices and submitted payment proofs must preserve their historical payment destination/instruction snapshot where applicable.
- Customer screens must not mix an old invoice's recipient instructions with a new QR code.
- Unsupported currencies must not display an incompatible QR.

### 5. Security

- Restrict QR configuration changes to authorized administrators.
- Require Super Admin approval for activation.
- Validate uploaded image formats, file content, and size.
- Use persistent storage.
- Prevent unauthorized access to configuration-changing endpoints.
- Prevent two simultaneous activations from creating conflicting active versions.
- Preserve an audit trail for all changes.

### 6. Testing

Test:

1. Admin uploads a replacement QR.
2. Preview displays the correct image.
3. Draft changes do not affect customer payments.
4. Super Admin activates a new version.
5. Customer screens display the correct configuration.
6. Historical invoices retain the correct original payment instructions.
7. Unauthorized users cannot change the QR.
8. Old configurations can be reviewed and safely restored.
9. QR configuration persists after application restart.
10. Existing payment verification workflows continue working.

### 7. Restrictions

- Do not change billing calculations.
- Do not modify existing payment amounts.
- Do not implement Wise API integration.
- Do not automatically verify payments.
- Do not delete payment history.
- Do not deploy to production yet.

Before implementing, inspect the existing QR replacement feature and explain what is already supported versus what needs enhancement.

Implement only the missing functionality and provide a summary of changed files, tests, and configuration instructions.
