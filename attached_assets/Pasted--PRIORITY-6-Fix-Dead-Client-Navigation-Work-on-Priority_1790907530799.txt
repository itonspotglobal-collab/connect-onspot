## PRIORITY 6 — Fix Dead Client Navigation

Work on **Priority 6 only**.

This is the final item in the current MVP functional-gap list.

Do not begin security work or unrelated backlog items after completing it.

---

# Problem

Previous source inspection identified Client-facing navigation links pointing to:

`/contracts`

and:

`/payments`

but those destinations appeared to have no corresponding usable Client routes/pages.

This creates dead navigation where authenticated Clients can click a legitimate-looking navigation item and reach:

- a 404,
- route fallback,
- blank/unrelated page,
- or another invalid state.

The objective is:

> **Every visible Client navigation item must lead to an intentional, usable Client destination.**

Do NOT build new Contracts or Payments modules merely to make these links work.

First determine whether these links are:

1. genuinely dead,
2. stale aliases for functionality that already exists elsewhere,
3. missing route registrations for existing pages,
4. or intentionally planned but not yet implemented.

Then apply the smallest correct MVP fix.

---

# PHASE 1 — AUDIT ALL CLIENT NAVIGATION

Before modifying code, identify every navigation surface available to the Client role.

Search for:

- `/contracts`
- `/payments`
- `Contracts`
- `Payments`
- Client sidebar
- Client navbar
- mobile navigation
- dropdown menus
- dashboard quick links
- breadcrumbs
- CTA buttons
- `navigate(...)`
- `<Link>`
- `<NavLink>`
- route constants/configuration

Audit all Client-facing navigation, not just one sidebar component.

Produce a map:

```text
Visible Client navigation item
→ target path
→ matching App route/router
→ destination component
→ valid/dead
```

---

# PHASE 2 — TRACE `/contracts`

Search the complete application for:

`/contracts`

Determine:

- where the Client link appears;
- whether a route exists;
- whether a page/component already exists;
- whether a different current page provides the intended contract functionality;
- whether contract management is now represented through another route such as team/hiring/contract-ending functionality;
- whether `/contracts` belongs to another role or obsolete architecture.

Do not assume it should simply be deleted until this is established.

If a legitimate current Client destination already provides the intended functionality, determine whether changing the link to that destination would be clearer than removing it.

Do not create a new Contracts page under Priority 6.

---

# PHASE 3 — TRACE `/payments`

Perform the same audit for:

`/payments`

Determine:

- where the link appears;
- whether a matching Client route exists;
- whether an existing billing/invoice/payment page is the actual current destination;
- whether `/payments` is legacy/dead;
- whether the path belongs to another role;
- whether there is currently any usable Client financial UI that this navigation item should target.

Be particularly careful here because previous audits established multiple financial paths in the repository.

Do NOT assume that:

`Payments`

means:

`Invoices`

or:

`Billing`

without evidence from the existing Client product flow.

Do not change financial behavior.

---

# PHASE 4 — AUDIT THE CLIENT ROUTER

Trace Client routing in:

`client/src/App.tsx`

and any relevant Client layout/router components.

Produce the current route map for authenticated Clients.

At minimum identify routes for existing functionality such as:

- Client dashboard
- Team
- Jobs
- candidates/applicants if applicable
- hiring/offers if applicable
- contract endings
- invoices/billing if applicable
- profile/settings
- other visible Client destinations

Use the actual application routes.

Do not invent paths based on naming conventions.

---

# PHASE 5 — CHOOSE THE SMALLEST FIX

For each dead navigation item, use this decision tree.

## Case A — Exact route exists but outer routing is missing

If an existing legitimate Client page is already implemented and only route mounting is missing:

add the minimal route registration.

Do not duplicate the page.

## Case B — Functionality exists under a different current route

If the intended functionality clearly exists elsewhere:

update the stale link to the legitimate existing destination.

Only do this when product intent is supported by the existing application.

## Case C — No implemented Client functionality exists

Remove the navigation item.

Do not create a placeholder page.

Do not redirect to an unrelated page.

Do not create a fake dashboard.

Do not add:

`Coming Soon`

unless the application already intentionally uses disabled/coming-soon navigation and there is a strong reason to preserve discoverability.

For MVP, prefer removing navigation to unavailable functionality.

---

# IMPORTANT — ROLE ISOLATION

Do not solve a dead Client link by routing Clients to an Admin or Talent page.

Verify that every retained destination is genuinely appropriate for the Client role.

Preserve existing authentication and authorization.

---

# OPTIONAL BACKWARD-COMPATIBILITY QUESTION

If `/contracts` or `/payments` may have been externally bookmarked/shared in the past, inspect whether the application has an established pattern for legacy-route redirects.

Do not add redirects automatically.

Only add a redirect if:

1. there is a clearly equivalent modern destination; and
2. doing so does not misrepresent functionality.

Otherwise allow the normal route-not-found behavior after removing the dead navigation link.

---

# REGRESSION TESTS

Add/update tests covering at minimum:

1. Every visible Client primary navigation destination maps to a valid Client route.

2. No visible Client navigation item targets a known dead route.

3. `/contracts` is either:
   - valid and intentionally mounted,
   - redirected to a proven equivalent,
   - or absent from Client navigation.

4. `/payments` is either:
   - valid and intentionally mounted,
   - redirected to a proven equivalent,
   - or absent from Client navigation.

5. Client contract-ending navigation remains functional.

6. Client Team Dashboard navigation remains functional.

7. Existing Jobs navigation remains functional.

8. Existing Client financial navigation, if any legitimate one exists, remains functional.

9. Mobile/responsive Client navigation matches desktop behavior where applicable.

10. Client cannot gain access to Admin/Talent destinations because of the navigation changes.

11. Priority 3 Team Dashboard routing remains intact.

12. Priority 4/5 Get Hired changes are unaffected where shared routing/layout code is touched.

---

# NAVIGATION CONSISTENCY CHECK

Inspect whether desktop and mobile Client navigation are defined separately.

If they are:

ensure the same dead-link fix is applied consistently.

Do not leave:

`Contracts`

or:

`Payments`

available on mobile while removing it on desktop, or vice versa.

Also inspect active-state matching so changing/removing a destination does not cause another navigation item to appear incorrectly selected.
