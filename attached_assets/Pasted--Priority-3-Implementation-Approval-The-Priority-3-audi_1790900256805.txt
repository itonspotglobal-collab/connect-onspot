# APPROVED PRODUCT SEMANTICS

## 1. Weekly Hours means RECORDED WORKED HOURS

The Client Team Dashboard's:

- Weekly Hours
- Hours logged
- daily activity bars
- logged-this-week presentation

should represent **recorded work activity**, NOT approved/billable hours.

Do not change this metric to timesheet-approved hours.

Do not use `timesheet_revisions` as the primary source for this dashboard metric.

Approved timesheet revisions remain the billing/invoicing source of truth where already implemented.

The Team Dashboard and Billing intentionally answer different questions:

**Team Dashboard:** How much recorded work/activity does this Talent have?

**Billing:** What reviewed/approved hours are financially billable?

Preserve that distinction.

---

# 2. PRESERVE LEGACY AND MODERN SOURCES SEPARATELY

Do NOT replace `time_entries` globally.

Use source separation.

### Legacy engagement

For verified legacy engagements/contracts:

`legacy contract → time_entries`

Continue using the existing legacy source.

### Modern Tracked engagement

For modern Tracked `hiring_contracts`:

`hiring_contract → clock_sessions`

Use modern recorded clock activity.

### Modern Guaranteed engagement

Guaranteed contracts do not require clock attendance.

Do NOT display `0 hours` in a way that implies the Talent failed to work.

Use an appropriate non-attendance representation such as:

`Not tracked`

or equivalent UI wording consistent with the existing design.

---

# 3. DO NOT DOUBLE COUNT

This is mandatory.

The audit established that modern worked time can have multiple representations:

`clock_session`
→ `timesheet revision snapshot`
→ potentially later revision
→ invoice

These are NOT additive.

For the Team Dashboard recorded-hours metric:

Use the selected recorded-time representation only.

Do NOT add:

`clock_sessions + timesheet_revisions`

Do NOT add:

`clock_sessions + invoice hours`

Do NOT add multiple timesheet revisions.

Legacy and modern sources must remain explicitly separated by engagement provenance.

Do not attempt to detect duplicates by matching timestamps.

---

# 4. MODERN CLOCK SESSION RULES

For modern Tracked contracts, calculate dashboard hours from appropriate completed/effective clock intervals.

Do not unrestrictedly sum all `clock_sessions`.

Correctly handle:

- completed sessions
- open sessions
- stale/missed-clock-out sessions
- reviewed exceptions
- effective reviewed end times where applicable
- sessions crossing midnight
- sessions crossing week boundaries
- contract start/end boundaries

Open sessions must NOT accumulate unlimited elapsed time into Weekly Hours.

If an open/unresolved session cannot safely contribute a finalized recorded duration, exclude it from the completed-hours total and represent its state separately if the existing UI supports doing so safely.

Do not silently fabricate an end timestamp.

---

# 5. REPORTING TIMEZONE

For Team Dashboard work-activity presentation, use the **contract/work timezone** where the modern contract provides one.

This dashboard represents work activity, not invoice-period accounting.

Do not change existing billing/invoice timezone rules.

Do not change the America/New_York invoice-period behavior discovered during the audit.

For legacy engagements where no equivalent work timezone exists, preserve existing behavior unless there is already a reliable timezone source.

Document the fallback explicitly.

Week boundaries must be deterministic.

The week remains:

`Monday → Sunday`

but intervals must be correctly clipped to the relevant reporting week.

Do not assign an entire cross-boundary session to its start day.

Example:

If a session crosses midnight, allocate the appropriate duration to each day.

If a session crosses Monday 00:00, count only the portion inside the current reporting week.

---

# 6. MODERN LATEST ACTIVITY

For modern Tracked engagements, use modern clock activity for the existing `Last active` concept.

Use appropriate:

`clock_sessions.started_at`

and/or:

`clock_sessions.ended_at`

timestamps.

Do NOT mix unrelated events such as:

- Admin timesheet approval
- invoice generation
- contract signing

into `Last active` if that would imply Talent attendance.

Those events are different semantics.

Preserve legacy latest activity for legacy engagements.

---

# 7. ONLINE / AWAY / OFFLINE

Audit the current fallback while implementing.

The audit found that the existing fallback can rely on recent/open legacy entries.

For modern Tracked engagements, update the fallback only if the modern clock state provides an equivalent trustworthy signal.

Do not redesign presence globally.

Do not claim someone is Online merely because historical clock activity exists.

If `profiles.availability` remains the primary explicit status, preserve it.

---

# 8. GUARANTEED CONTRACTS

Guaranteed billing does not require clock attendance.

Therefore do not present missing clock sessions as:

`0 hours`

if that communicates that the Talent performed zero work.

Use a clear non-tracked state such as:

`Not tracked`

for the hours/activity metric where appropriate.

Do not change Guaranteed billing behavior.
