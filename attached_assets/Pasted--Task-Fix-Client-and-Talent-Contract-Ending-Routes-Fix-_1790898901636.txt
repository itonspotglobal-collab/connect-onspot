## Task: Fix Client and Talent Contract-Ending Routes

Fix **Priority 1 only**. Do not work on other MVP gaps, security issues, refactors, or unrelated cleanup.

### Problem

The backend contract-termination functionality is already implemented. Do **not** rebuild or redesign the termination backend.

The frontend already contains these nested routes:

- `/client/contract-endings` → `ContractEndings` with `role="client"`
- `/talent/contract-endings` → `ContractEndings` with `role="talent"`

However, these routes are only declared inside `ClientRouter` and `TalentRouter`.

The outer `AppContent` `<Switch>` in:

`client/src/App.tsx`

does not currently mount these URL paths, so the request never reaches the appropriate nested router.

As a result:

- `/client/contract-endings` currently falls through instead of reaching `ClientRouter`.
- `/talent/contract-endings` currently falls through instead of reaching `TalentRouter`.

The Admin contract-ending route is already reachable. Use the existing routing architecture as the reference, but preserve the correct role-specific Client and Talent layouts/authentication behavior.

---

## Required Fix

### 1. Fix the outer routing

In `client/src/App.tsx`, update the outer `AppContent` route table so that:

`/client/contract-endings`

is mounted through the existing `ClientRouter`.

And:

`/talent/contract-endings`

is mounted through the existing `TalentRouter`.

Do **not** duplicate the `ContractEndings` page directly in the outer router if routing through the existing role router is the established architecture.

The intended flow should be:

Client:

`AppContent`
→ `/client/contract-endings`
→ `ClientRouter`
→ existing `<Route path="/client/contract-endings" ...>`
→ `<ContractEndings role="client" />`

Talent:

`AppContent`
→ `/talent/contract-endings`
→ `TalentRouter`
→ existing `<Route path="/talent/contract-endings" ...>`
→ `<ContractEndings role="talent" />`

Preserve all existing authentication and role protections.

Do not make these routes public.

### 2. Audit the existing ContractEndings component

After making the routes reachable, inspect the existing `ContractEndings` implementation.

Confirm that the Client version calls the existing real Client contract-termination API and that the Talent version calls the existing real Talent contract-termination API.

Trace the requests all the way to the registered backend handlers.

Do not create replacement endpoints if working endpoints already exist.

Do not mock termination responses.

Do not replace real API calls with fake/sample data.

### 3. Do not modify termination business logic unless a genuine wiring bug is discovered

The backend termination system already contains business rules around areas such as:

- effective end dates
- proration
- locked-ledger protection
- role/ownership validation
- termination request persistence
- Admin review/decision flow

This task is primarily a **routing fix**.

Do not rewrite, simplify, bypass, or remove those protections.

If you discover a separate backend defect while testing, document it first rather than silently redesigning the termination workflow.
