Remodel the existing Create Job / Edit Job experience.

This is primarily a UI/UX redesign. Do NOT rewrite or remove existing job functionality.

The current implementation uses a popup/modal such as:

JobFormModal.tsx

Replace the modal experience with a dedicated, full-page job form inspired by the attached post-job.html mockup.

Main objective

Make posting and editing jobs much simpler for non-technical users.

Think:

LinkedIn-style simplicity
+
OnSpot branding
+
existing OnSpot job functionality

The form currently contains many fields at once and feels overwhelming.

Break it into a guided step-by-step experience.

1. New routes

Instead of opening JobFormModal.tsx, navigate to dedicated pages.

Use routes similar to:

/admin/find-work/jobs/new

for creating a job, and:

/admin/find-work/jobs/:jobId/edit

for editing.

Keep:

/admin/find-work

as the Job Management dashboard.

Clicking:

+ Add New Job

should navigate to the new Create Job page.

Clicking:

Edit

on an existing job should navigate to the Edit Job page.

Do not open JobFormModal.tsx anymore once the new page implementation is complete.

2. Do NOT change business logic

This redesign must preserve all current functionality.

Reuse the existing:

job schema
create/update APIs
validation
approval workflow
pending/approved/declined logic
open/closed status
public /find-work/jobs behavior
video introduction requirement
salary/rate fields
company confidentiality
role descriptions
requirements
schedule
equipment requirements
benefits
success profile
existing rich text editors

Do not create duplicate database fields simply because the UI has changed.

This task is mostly a change in presentation and navigation.

3. Four-step workflow

Use this exact high-level structure:

1. Basics
2. Description
3. Requirements
4. Review

Display a clear progress indicator at the top.

Example:

━━━━━━━   ───────   ───────   ───────
① Basics   ② Description   ③ Requirements   ④ Review

Completed steps should visually use the OnSpot purple accent.

Users should be able to click completed steps to go back.

Do not let users skip forward if required fields from an earlier step are invalid.

8. Create vs Edit behavior

The same page/component architecture should support both modes.

Suggested structure:

JobFormPage
├── JobFormHeader
├── JobFormStepper
├── JobBasicsStep
├── JobDescriptionStep
├── JobRequirementsStep
├── JobReviewStep
└── JobFormFooter

Create mode:

blank/default form
→ final action: Submit for Approval

Edit mode:

fetch existing job
→ populate all steps
→ final action: Update Job

Keep the current approval rules.

If editing an approved job currently affects approval status, preserve whatever existing business rule is already implemented.

Do not invent a new approval behavior as part of this redesign.

9. Persistent bottom navigation

Add a sticky/fixed footer navigation like the mockup.

Example:

Step 2 of 4

                Back      Continue

On the final step:

Create:

Back       Submit for Approval

Edit:

Back       Update Job

Keep the navigation visible while the user scrolls.

Ensure the page has enough bottom padding so the footer does not cover form fields.

10. Save & Exit

Add:

Save & exit

in the top-right area.

If the project currently supports drafts, use the existing draft functionality.

If drafts are NOT currently supported, do not invent a new backend draft system without confirmation.

Instead either:

preserve form state during navigation if the app already supports it, or
provide Cancel / Exit with an unsaved-changes confirmation.

Do not silently lose user-entered data.

Do not copy LinkedIn branding.

Copy only the simplicity/usability concept.

Use the existing OnSpot visual identity from the homepage.

Reference the homepage's:

purple/indigo brand colors
typography hierarchy
rounded cards/buttons
clean white surfaces
subtle borders
soft purple highlights
existing OnSpot logo/header

12. Typography

Follow the existing homepage typography wherever possible.

Keep:

large friendly page heading
strong but simple section headings
readable labels
muted helper descriptions
obvious required indicators

Avoid excessive uppercase headings and overly technical wording.

Rewrite labels/helper text for clarity where necessary, but do not change the underlying meaning of fields.

Improve wording where the current labels are too technical.

For example:

Professional Role Name

can become:

Job title

with helper text:

Use the title candidates are most likely to search for.

Keep the underlying database field unchanged.

Likewise simplify other UI labels without renaming database/API properties unnecessarily.

14. Use chips where appropriate

Hybrid
On-site

For complicated or long option lists, keep Select/dropdown components.

15. Responsive design

The page must work well on:

large desktop
MacBook/laptop
tablet
mobile

Main content should have a comfortable max-width around:

720–800px

Desktop should not become excessively wide.

On mobile:

stack multi-column fields
keep progress understandable
keep Back/Continue accessible
avoid horizontal scrolling
16. Validation

Validate each step before Continue.

When validation fails:

stay on the same step
highlight invalid fields
scroll/focus to the first invalid field
show simple human-readable messages

Do not wait until Step 4 to reveal all errors.

Preserve backend validation as the final source of truth.

17. Form state

Moving:

Basics
→ Description
→ Requirements
→ Back

must NOT clear previously entered data.

Keep one shared form state across all four steps.

Avoid creating separate independent forms that lose state.

18. Existing data compatibility

Existing job records must load correctly in the new Edit Job page.

There should be no migration purely because of this UI redesign.

Verify all existing fields from JobFormModal.tsx are represented somewhere in the new flow.

Do not accidentally remove a field because it is not visible in the first step.

Optional/advanced fields can be collapsed, but their functionality must remain.

19. Return navigation

After:

successful create
successful update
cancel/exit

return the user to:

/admin/find-work

Preserve success/error toast behavior already used by the app.
