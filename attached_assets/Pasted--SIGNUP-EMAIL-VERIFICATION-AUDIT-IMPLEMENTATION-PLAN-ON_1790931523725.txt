# PHASE 4 — PROPOSE SERVER-SIDE VERIFICATION MODEL

Design the smallest robust implementation consistent with the existing architecture.

Preferred properties:

### Verification code

Use a cryptographically secure random code.

A six-digit numeric code is acceptable for UX provided rate limiting and expiry are enforced.

Example presentation:

`123456`

Do NOT store the plaintext verification code persistently.

Store a secure hash/HMAC representation suitable for verification.

Never log the plaintext code in production.

### Expiration

Recommended default:

`10 minutes`

Determine whether the repository already has conventions that suggest another value.

### Single use

Successful verification must invalidate/consume the challenge.

### Resend

A resend should invalidate or supersede the previous active code.

Recommend an appropriate resend cooldown.

### Attempts

Recommend a maximum number of incorrect verification attempts.

After the limit, require a new code.

### Rate limiting

Consider limits by:

- email;
- IP/request source where supported;
- verification challenge;
- resend frequency.

Use existing rate-limit infrastructure if present.

Do not invent an entirely separate framework if the application already has one.
