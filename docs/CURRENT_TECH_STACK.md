## Status labels and evidence limits

All feature status labels in this document use exactly these meanings:

| Label | Meaning in this audit |
|---|---|
| **LIVE** | The currently reachable UI or registered API path has implemented behavior using real storage/service logic. This is a source classification only; it does **not** mean production operation, external configuration, delivery, or business outcome was verified. |
| **PARTIAL/STUBBED** | Some real behavior exists, but the path is conditional, incomplete, mixed with local heuristics/fallbacks, has a contract mismatch, lacks a required provider step, or has a material security/reachability limitation. |
| **LEGACY/DEAD** | A path is unmounted, shadowed, only retained for compatibility, or has no current workflow writer. Retained legacy records and schemas are not thereby deleted. |

An API can qualify as **LIVE backend capability** while its UI journey is unreachable. That alone does not make the user journey LIVE. Installed dependencies, declared schema, route components nested under an unmounted router, environment-variable names, deployment metadata, and historical test output do not establish a working end-to-end feature.

### Server and startup

Express 4.21.2 serves API routes and static/client assets. TypeScript source runs through `tsx` in development; deployment bundles the server entry and migration runner with esbuild. The workspace Node version observed during the audit was **v22.22.0**; `.replit` declares Node 22. Production Node version is unknown, and `package.json` does not set an `engines` range. Package dependency version strings are source declarations, not an observation of installed or deployed versions.

The source build packages `vite build`, esbuild outputs for `server/index.ts` and `scripts/run-migrations.ts`, and a copy of `scripts/migration-reconciliation.sql` into `dist`. The configured deployment starts `NODE_ENV=production node dist/run-migrations.js`, then starts `NODE_ENV=production node dist/index.js`; Express listens on the configured port (5000 in `.replit`). [`package.json`](../package.json#L9-L11), [`.replit`](../.replit#L9-L19)

Publish's managed-PostgreSQL schema comparison/synchronization is a **separate** operation from both artifact building and the startup SQL runner. A prior project-specific observed Publish sequence places the schema sync before application startup; this does not establish a universal ordering relative to build, and managed-PostgreSQL sync rules are conditional on that platform configuration. The actual local reference is [`database-migrations-on-publish.md`](../.local/skills/database/references/database-migrations-on-publish.md); official references are [Replit development and production databases](https://docs.replit.com/features/data-and-storage/development-and-production) and [Replit troubleshooting](https://docs.replit.com/build/troubleshooting). Publish schema sync and startup SQL are distinct committed mutations: a failed startup or promotion does not roll back DDL already applied by the earlier sync, or migrations `0018`–`0020` already completed. An older published build may remain serving if a new promotion fails. `npm run db:push` is a separate Drizzle Kit script, not the actual deployment migration pipeline.

An earlier port-wait failure was downstream of an SQL collision, not a root cause to fix by changing the port. See [`.replit`](../.replit#L9-L19), [`package.json`](../package.json#L6-L17), and the local Publish reference above.

### Database clients and storage abstraction

The application has two active PostgreSQL access paths pointed at `DATABASE_URL` in source:

- [`server/db.ts`](../server/db.ts#L1-L15) creates a Neon serverless `Pool` and Drizzle database. It is used by much of the application.
- [`server/db.js`](../server/db.js#L1-L10) creates a separate `pg` pool. Active services import it, including the email companion, interview-email, formal pipeline guard, and hiring-contract services. It is not merely a dead alternate implementation.

The platform/driver evidence supports saying “PostgreSQL accessed through Neon and `pg` clients”; it does **not** establish the database hosting provider. No provider should be inferred from the driver package. The project-specific Publish path has historically performed a managed-PostgreSQL sync, but that conditional platform behavior is not a basis to infer hosting ownership from the Neon driver.

[`DbStorage` extends `MemStorage`](../server/storage.ts#L2778-L2791). Individual overrides determine persistence. For example, messages, notifications, Vanessa logs, and LegalOps trials have database-backed implementations ([`server/storage.ts`](../server/storage.ts#L2795-L2825), [`server/storage.ts`](../server/storage.ts#L2985-L3005), [`server/storage.ts`](../server/storage.ts#L3752-L3862), [`server/storage.ts`](../server/storage.ts#L4116-L4148)); review methods and LinkedIn profile methods instead use in-process Maps and have no corresponding `DbStorage` persistence override ([`server/storage.ts`](../server/storage.ts#L1738-L1763), [`server/storage.ts`](../server/storage.ts#L1998-L2037)). A declared database table does not prove that a particular API method uses it.

## Migrations, publish, and database risk

### Custom migration lifecycle

There are **30 SQL migration files, numbered `0002` through `0031`**. The custom runner scans `.sql` files in lexical order, requires `DATABASE_URL`, creates `app_schema_migrations`, and uses a per-migration-ID PostgreSQL advisory transaction lock before checking the ledger and applying pending SQL ([`scripts/run-migrations.ts`](../scripts/run-migrations.ts#L23-L46), [`scripts/run-migrations.ts`](../scripts/run-migrations.ts#L89-L143)).

Important behavior and limits:

1. **Grandfathered baseline is not a fresh-database initializer.** If `jobs` already exists, the runner assumes all on-disk migration IDs through `0010` are already applied and records missing ledger entries. That is a compatibility assumption about prior migration work, not verification that every baseline object exists. Migration `0010` is explicitly a no-op preserving legacy freelance tables. The versioned files beginning at `0002` do not, by themselves, document a complete fresh-schema construction path; Publish/Drizzle schema synchronization and application DDL also participate. [`scripts/run-migrations.ts`](../scripts/run-migrations.ts#L48-L86), [`migrations/0010_remove_legacy_freelance_tables.sql`](../migrations/0010_remove_legacy_freelance_tables.sql#L1-L11)
2. **Per-ID locking is not global serialization.** The advisory lock is keyed by migration ID, so it prevents duplicate concurrent execution of the same ID, not all migrations from different IDs running concurrently across independent runners.
3. **Transaction guarantees are weaker for self-transactional SQL.** The runner starts an outer transaction, but older migration SQL can contain its own `BEGIN`/`COMMIT`. An inner commit can commit work before the outer ledger bookkeeping; it does not guarantee that the entire migration plus ledger insertion is atomic under one outer transaction. [`scripts/run-migrations.ts`](../scripts/run-migrations.ts#L96-L103), [`scripts/run-migrations.ts`](../scripts/run-migrations.ts#L129-L141)
4. **Pending financial migrations use reconciliation helpers.** For IDs matching `0018`–`0031`, the runner loads `migration-reconciliation.sql` into the same session/transaction, runs the migration, calls `finish_reconciliation()`, then writes the ledger ID. The build copies this helper into `dist`. This is a pending-migration guard, not a catalog query or repair of already-recorded migrations. [`scripts/run-migrations.ts`](../scripts/run-migrations.ts#L118-L141), [`package.json`](../package.json#L9-L11)
5. **`db:push` is not the deployed SQL runner.** The configured deployment starts with the custom runner after Publish's separate schema synchronization, not by invoking `npm run db:push`. Do not collapse these mechanisms into one step.

## Security, reliability, and scaling limits

- **Route monolith:** `server/routes.ts` is 25,632 lines and contains many unrelated API routes and business flows. Some billing, termination, and candidate-media logic has been extracted into modules, but the main route file remains a large change-impact surface.
- **Instance-local state:** storage methods implemented by `MemStorage`, Maps used for some review/LinkedIn paths, process-local caches, and in-memory rate-limit state are not shared durable state across autoscale instances. Candidate-list caching is in-process over DB-backed candidates; it does not replace database persistence. [`server/storage.ts`](../server/storage.ts#L1738-L1763), [`server/storage.ts`](../server/storage.ts#L1998-L2037), [`server/routes.ts`](../server/routes.ts#L7720-L7753), [`server/routes.ts`](../server/routes.ts#L1080-L1087)
- **Local uploads:** inquiry payment proof writes to `public/payment-proofs` rather than the object-storage service, creating a persistence/availability risk in autoscale. Source inspection cannot establish whether the runtime filesystem is persistent. [`server/routes.ts`](../server/routes.ts#L14103-L14113)
- **No automated hiring payout rail:** billing models include provider-neutral references and internal payout states, but manual `externalRef` bookkeeping and scheduled payout rows are not a transfer to a bank/payment provider. [`server/routes.ts`](../server/routes.ts#L22546-L22703), [`talentInvoices.ts`](../server/routes/talentInvoices.ts#L346-L391)
- **In-process cron duplication:** invoice automation is not controlled by the main background-jobs flag, and several cleanup jobs are unguarded. Autoscale replica ownership must be managed operationally; the source does not enforce one worker.
- **Authorization is not uniform:** the conditional admin bypass and unauthenticated inquiry/culture/image routes described above are concrete source-level exposure risks. UI route guards do not secure an API by themselves.
- **Token placement:** Talent frontend code uses a localStorage-backed candidate session in some paths. Local storage is accessible to script executing in the page and should not be treated as a server-side session boundary. [`client/src/App.tsx`](../client/src/App.tsx#L423-L452)
- **Deployment/schema drift:** Publish schema sync, ad-hoc DDL, and the custom migration ledger can describe different portions of schema lifecycle. Only an authorized current catalog/ledger review can resolve actual drift; this audit did not do one.
