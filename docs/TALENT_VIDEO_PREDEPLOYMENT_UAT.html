Talent Video Upload and Job Application Submission

Pre-deployment audit and verification · 20 October 2026 · No deployment authorized or performed

Development verification passes for the corrected flows. This is not published-production certification. The authenticated browser UAT uses the actual application frontend, production route implementations, normal password login, disposable seeded accounts, disposable PostgreSQL, and real private object storage. It does not use customer accounts or the application's existing database.

1. Root causes and relationship between the reports

  1. Original profile HTTP 413 — confirmed infrastructure rejection. A previous safe 63 MiB multipart probe against a nonexistent candidate reached Express in development and returned JSON 401. The same unauthenticated probe against the published host returned Google Frontend HTML 413 before Express. Multer already allowed 200 MiB. Raising its limit would not solve this. The exact ingress threshold was not measured.
  2. Job application had a separate affected upload path. Source tracing confirmed that JobApplyPage still appended the video file to the final POST /api/jobs/:jobId/apply multipart body. The profile fix had not changed that path. It was exposed to the same published large-request architecture, but the historic application failure was not separately reproduced against production.
  3. Settings recordings had another separate multipart path. Supplemental authenticated recording UAT found that Profile Settings file selection used direct storage while its recording-save handler still posted multipart to the legacy candidate-video endpoint. That handler now shares the direct uploader and retains the recording on failure. The corrected recording/save/refresh/delete browser scenario passes.
  4. Recording/selection race — reproduced in authenticated browser UAT. File validation ran after an artificial 300 ms timeout. Advancing immediately after a recording could persist the previous profile video instead of the new recording. Validation is now synchronous and clears the previous selection before accepting a new file. The immediate-advance recorded-submission regression passes.
  5. Misleading submission progress. A 2.5-second timer changed the UI to “Saving” regardless of transfer completion. Real transfer progress and verified completion now control that state.
  6. Unavailable jobs could remain on “Preparing your application…”. A failed job lookup never completed Talent prefill, while the spinner masked the lookup error. The error is now visible and the browser regression passes.
  7. Historical media deletion risk. Profile deletion previously deleted its storage object even when an application retained that URL. It now clears the profile fields while preserving objects referenced by submitted applications. Replacement continues retaining old committed media.

The first two reports share an infrastructure risk, but the application also had independent workflow defects. The original user's complete historical failure cannot be reconstructed without their original request/logs; this report does not claim otherwise.

3. What changed

  • Added authenticated, job-scoped direct video upload initiation, verification, cancellation and submission receipts using the existing storage provider.
  • Generalized the existing private-video storage adapter to separate profile and application namespaces. Signed PUTs can write only quarantine; final publication is generation-pinned.
  • Application submission now awaits upload verification, submits a scoped receipt, stores the correct video reference and original filename, and rejects missing/foreign/wrong-job/expired references.
  • Added synchronous double-click prevention and database-backed retry idempotency without schema changes. Intentional new repeat applications still use a new form key.
  • Added application recording with browser-supported MIME selection, local preview, retry-preserved file, a two-minute stop limit and track/object-URL cleanup.
  • Removed the file-validation timer and stale prior-video selection race. Added a clear unavailable-job error path.
  • Retained history when removing profile media. Rollback cleans request-owned attachments; uncertain database acknowledgement is reconciled before deleting potentially committed media.
  • Removed simulated progress and the obsolete generic-upload path from standalone EnhancedVideoIntroduction.
  • No UI redesign, new storage provider, Base64 video transport, application database conversion, global request-limit increase, production migration, or deployment.

6. Deployment architecture and remaining risks

  • Large video bytes bypass application ingress. Only small JSON authorization/verification requests and ordinary final form fields reach Express. Signed storage transfers accept the tested 200 MiB maximum.
  • Private storage configuration: the published runtime must have the correct PRIVATE_OBJECT_DIR, sidecar/provider access, signing/copy/metadata/delete permissions and the intended production bucket. The successful development-storage run does not prove that production uses the same configuration.
  • Authentication: published frontend and backend must share the intended production JWT signing configuration. No test secret or seeded account must be copied to production.
  • CORS: real Chromium-to-storage transfers succeeded from the isolated local frontend; the earlier transport check accepted the development preview origin. The actual published origin and its production-storage binding still require release-environment verification.
  • Legacy cached clients: old multipart video requests can still hit the Google Frontend limit. Release frontend and backend together and verify a fresh client session after an approved publish. The compatibility endpoint is not a workaround for old large-body clients.
  • Validation: the exact accepted boundary is 209,715,200 bytes (200 MiB; UI calls this “200 MB”). Actual object size/type and container signatures are checked. This is not comprehensive codec transcoding, malware scanning or validation of every frame.
  • Abandoned uploads: failed/cancelled transfers are removed best effort; expired quarantine cleanup is bounded and triggered by new initiations. It is not a continuously scheduled provider lifecycle policy. Historical committed media is deliberately retained when needed by applications.
  • Ambiguous database failures: if commit state cannot be read back, media may be retained for reconciliation rather than deleting a potentially committed application/profile attachment. This is intentional data-preservation behavior.
  • Performance: legacy authenticated playback may fetch a video into a browser Blob. Physical low-memory/mobile playback and long/slow-network behavior remain to be verified.
