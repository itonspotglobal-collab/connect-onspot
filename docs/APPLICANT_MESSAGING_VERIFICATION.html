Client → Applicant Messaging: Fix and Verification

21 October 2026 · Development verification · No automatic deployment

Result: the original 403 was reproduced through the actual Client Job Submissions button against the original registered route. The fixed route opens an authorized direct applicant's conversation, and the browser Client/Talent send-and-reply flow passes. There are no application schema changes or production migrations.

1. Confirmed root cause and failing request

POST /api/applications/:applicationId/message-thread rejected ordinary applications because its helper contained:

if (submission.workflow_type !== "client_invitation") {
  return { status: 403, error: "Conversation is not available for this application." };
}

Genuine applicants use workflow_type='application'. A job-owning Client therefore received 403 even for a valid, linked Talent with status new. The frontend hid every error behind “Unable to open conversation. Please try again.” It did not reveal the policy restriction.

Policy decision: after being informed of the existing restriction, the owner explicitly authorized job owners to message Talent who applied directly to their own jobs. This fix implements that application-scoped permission; it does not silently remove the generic invitation gate.

2. Flow and account mapping audit

  1. client/src/pages/ClientProfile.tsx, JobSubmissionsSection, loads GET /api/client/job-submissions and renders each applicant's Message button.
  2. The button sends the submission's ID in the path to POST /api/applications/:applicationId/message-thread. It does not submit a Client, candidate or Talent participant ID.
  3. Existing authenticateJWT normalizes the signed-in session to a canonical users.id. Only Client and Talent roles can use this bridge.
  4. The server reads the exact job_submissions row and its jobs row. jobs.client_id determines the authorized job owner; client_profiles.id is not a messaging participant.
  5. job_submissions.talent_id references users.id, not candidates.id. The fixture deliberately uses different candidate and user IDs. No foreign key or existing identifier was rewritten.
  6. Explicit Talent IDs must resolve to a user with role Talent. Legacy email matching remains available only when talent_id is null, and must also resolve to a Talent user. A present but invalid/non-Talent ID can no longer silently fall back to a different user via the application email.
  7. Creation/reuse uses message_threads. Actual message bodies and read state use messages. Existing policy consent uses user_policy_acceptances; grouped alerts use notifications.
  8. The server returns a valid threadId. The Client navigates to the existing Messages interface; both participants load their authorized thread list and history.

3. Fixes implemented

  • Allow genuine Talent-initiated application rows as well as existing formal client_invitation rows. Continue rejecting silent client_shortlist records.
  • Require a canonical Client job owner and a canonical Talent account. Participants and job context are always derived server-side.
  • Retain the existing positive stage allow-list for starting new conversations. Existing authorized history remains reusable under the previous behavior.
  • Serialize creation with the existing pair/job transaction advisory lock. Prefer an existing job-specific thread, then the established direct channel; create only if neither exists.
  • After acquiring the creation lock, reread and share-lock the job/application rows. Reject changed ownership, assignment or workflow and evaluate the latest stage rather than stale pre-lock data.
  • Preserve sender enforcement, participant checks, messaging-policy consent, contact redaction, name masking, message history and notification behavior.
  • Add a synchronous frontend in-flight guard in addition to the existing loading/disabled state. The browser double-click test confirms exactly one API request.
  • Reject empty/invalid success payloads rather than navigating to an empty conversation. Invalidate the thread list after success and display meaningful API error text, with a safe fallback for non-JSON infrastructure errors.

The generic POST /api/message-threads remains invitation-only. Other direct-message, invitation acceptance, hiring status, privacy and identity-reveal policies were not broadened.
